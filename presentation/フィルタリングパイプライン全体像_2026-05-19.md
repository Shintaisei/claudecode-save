# フィルタリングパイプライン全体像

作成日: 2026-05-19

---

## 1. 結論：パイプラインは途中で2つに分岐している

全体は **5段階** だが、段階3以降に **2つのルート** があり、
それぞれ異なる目的に向かっている。

```
[段階1] First Pass   セッション単位の異常検知
            ↓
[段階2] Second Pass  チャンク（100 event）単位の再ランキング
            ↓
        ┌───────────────────────────────────────────┐
        │               ここで分岐                   │
        └──────────┬─────────────────┬──────────────┘
                   ↓                 ↓
           【ルートA】           【ルートB】
        LOF micro-chunk路線    Security+Sysmon路線
        
        段階3: third pass      段階3: review queue構築
               microchunk             (Sysmonと突合せ)
        段階4: LOF上位を        段階4: third pass
               解析                    (review windowsベース)
                               段階5: Sysmon 100ログ選定
```

**問題の核心：ルートBには方法論上の弱点がある（後述）**

---

## 2. 各段階の詳細

---

### 段階1: First Pass — セッション単位の異常検知

**スクリプト:** `train_atlasv2_iforest.py` → `run_atlasv2_single_stage_loop.py`

**何をしているか:**

```
全セッション（数百本）
        ↓
IsolationForest（n-gram TF-IDF ベクトル化）
        ↓
benign validation の p95/p99 パーセンタイルで閾値決定
        ↓
閾値超えのセッションを「陽性（要調査）」として出力
```

**フィルタリングの軸:** セッション全体の n-gram 構成の珍しさ  
**粒度:** セッション単位（1セッション = 数百〜数千 event）  
**出力:** `first-pass results.json`（陽性セッションのリスト + スコア）

---

### 段階2: Second Pass — チャンク単位の再ランキング

**スクリプト:** `run_second_pass_rarity.py` または `run_second_pass_hybrid.py`

**何をしているか:**

```
段階1で陽性になったセッション
        ↓
100 event 単位の chunk に細断
        ↓
【rarity版】テンプレートの希少性スコアで再ランキング
【hybrid版】プロセス名の希少性 + スコアの時系列勾配で再ランキング
        ↓
top-K chunk（デフォルト上位10本）を出力
```

**フィルタリングの軸:** chunk 内のテンプレート or プロセスの珍しさ  
**粒度:** chunk 単位（100 event）  
**出力:** `second-pass results.json`（top_chunks：各 chunk のスコア + attack/normal 内訳）

---

### 段階3以降（分岐）

ここから目的によって2つのルートに分かれる。

---

## 3. ルートA：LOF micro-chunk 路線（攻撃を含む文脈を保持）

**スクリプト:** `run_third_pass_microchunks.py`

**何をしているか:**

```
second-pass top-K chunk（100 event × 10本 = 1,000 event）
        ↓
さらに 10 event 単位の micro-chunk に細断
        ↓
LOF / OCSVM / Rarity の3モデルで micro-chunk を再ランキング
        ↓
top-10 micro-chunk（= 100 event）を出力
        ↓
各 micro-chunk の attack / normal 内訳を確認
```

**フィルタリングの軸:** micro-chunk 内の異常度（LOF スコア等）  
**粒度:** micro-chunk 単位（10 event）  
**特徴:** attack event を含む chunk も除外せず、スコア順にそのまま並べる

**出力結果（S3 の例）:**

```
top-10 micro-chunk の内訳

  rank 1: chunk330-micro5   attack 1 / normal 9   attack近傍
  rank 2: chunk325-micro2   attack 0 / normal 10  正常（payload.exe近傍）
  rank 3: chunk325-micro5   attack 3 / normal 7   attack近傍
  rank 4: chunk325-micro7   attack 3 / normal 7   attack近傍
  rank 5: chunk324-micro7   attack 3 / normal 7   attack近傍
  rank 6: chunk204-micro2   attack 0 / normal 10  正常候補（repmgr.exe）
  rank 7: chunk244-micro8   attack 0 / normal 10  正常候補（explorer.exe）
  rank 8: chunk325-micro8   attack 1 / normal 9   attack近傍
  rank 9: chunk203-micro5   attack 0 / normal 10  正常候補（repmgr.exe）
  rank 10: chunk203-micro7  attack 0 / normal 10  正常候補（winword.exe）
```

---

## 4. ルートB：Security+Sysmon 路線（Sysmon 100ログ選定）

**スクリプト:**  
`build_security_sysmon_review_queue.py` →  
`run_third_pass_review_windows.py` →  
`select_sysmon_usecase_candidates.py`

### 段階3-B: Review Queue 構築

```
first-pass + second-pass の結果
        ↓
Security セッションを 10分粒度に丸めて
Sysmon minute と突合せ
        ↓
各セッションに Sysmon minute 候補を紐付けたキューを生成
  sysmon_exact_user_minutes  ← 同一ホスト・ユーザー・10分枠
  sysmon_same_host_minutes   ← 同一ホスト・全ユーザー・10分枠
```

### 段階4-B: Third Pass（review windows ベース）

```
review queue の window を micro-chunk 化
        ↓
LOF / OCSVM / Rarity で再ランキング（ルートAと同じ手続き）
```

### 段階5-B: Sysmon 100ログ選定

```
micro-chunk 結果 + Sysmon JSONL を突合せ
        ↓
各 minute をプロセス名で4分類:
  attack_near       payload.exe, powershell.exe, mshta.exe,
                    regsvr32.exe, eqnedt32.exe が含まれる
  core_normal       excel.exe, mmc.exe, winword.exe,
                    upd.exe など（シナリオ別）が含まれる
  background_context  背景ホワイトリストのみ
  neutral_context   上記以外
        ↓
attack_near を除外
core_normal → neutral_context → background_context の優先度で積み上げ
100 event に達したら停止
```

**出力:** `selected_events.csv`（Sysmon 100ログ）

---

## 5. 2ルートの比較と問題点

| 観点 | ルートA（LOF micro-chunk） | ルートB（Sysmon100） |
|---|---|---|
| 攻撃の扱い | **保持**（attack chunk も対象に含む） | **除外**（attack_near minute を先に落とす） |
| FP の定義 | 攻撃を含む高スコア chunk の中の normal event | 怪しいセッション内の正常 minute |
| 因果の強さ | **強い**（検知が反応した chunk の内部を見ている） | **弱い**（攻撃を除外した後の正常ログ収集） |
| ログ種別 | Security ログ（EventID 4656/4663/4658 等） | Sysmon ログ（プロセス起動・ファイルアクセス等） |
| シナリオ | S3 で実施済み | S3/M4/M6/S4 で実施済み |

---

## 6. なぜルートBのFPストーリーは弱いか

ルートBの問題は「**攻撃を除外してから正常を選んでいる**」点にある。

```
本来の偽陽性（FP）の定義:
  「検知器が攻撃だと判断したが、実際には正常だったもの」
              ↑
  これが成立するためには「攻撃と正常が同じ文脈で検知されること」が必要

ルートBでやっていること:
  「検知器が反応したセッション内で、攻撃っぽいものを除いた残りを収集」
              ↑
  攻撃の除外が先に来るため、
  「検知が攻撃に反応したついでに正常も引っかかった」という説明ができない
```

**ルートAのストーリー（正しいFP説明）:**

```
LOF が chunk330 を高スコアで上位化
  → この chunk には attack 6件 + normal 94件が混在
  → 「攻撃が含まれているから高スコアになった chunk の中に、
     正常行動も一緒に上位化されていた」
  → この正常 94件が偽陽性 = 正常ユースケース候補
```

**ルートBのストーリー（FP説明として不完全）:**

```
Security 検知がセッション X を陽性判定
  → セッション X の中から攻撃 minute を除外
  → 残った正常 minute を 100ログとして収集
  → 「これらは正常だが、なぜ偽陽性になったのか」が説明できない
     （検知が反応した理由を先に取り除いているため）
```

---

## 7. 整理：各ルートの正しい使い方

| ルート | 使うべき場面 | 発表での位置づけ |
|---|---|---|
| **ルートA（LOF）** | 「偽陽性候補の選定」の主軸 | 偽陽性 = 攻撃近傍で一緒に上位化された正常行動として説明 |
| **ルートB（Sysmon100）** | 「正常行動のバリエーション収集」の補助 | 「候補のバリエーション拡充」として位置づけ直す |

---

## 8. 今後の方針（推奨）

1. **FP候補の主軸はルートA（LOF micro-chunk）で固める**
   - S3 の top-10 micro-chunk 内の normal event が主たる偽陽性候補
   - 「攻撃と共に上位化された正常行動」という説明が通る

2. **ルートBの100ログは「正常ユースケースのバリエーション」として扱い直す**
   - M4/M6/S4 の Sysmon100 は Office 操作・背景動作の正常例として有用
   - ただし「偽陽性」とは呼ばず「正常ユースケース候補の多様化」と呼ぶ

3. **発表構成への影響**
   - Slide 6（S3 結果）: ルートAの結果を軸に据える（現状の整理でOK）
   - Slide 7（複数シナリオ）: ルートBは「正常ユースケースの種類が広がる」という位置づけに修正
   - 「偽陽性」という語はルートAの文脈でのみ使う
