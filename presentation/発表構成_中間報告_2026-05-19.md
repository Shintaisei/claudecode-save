### Slide 1: 研究背景：インシデント分析の現状

**メッセージ:** アナリストの負荷は増大しており、ログのトリアージ自動化が求められている

**本文:**

- エンドポイントは大量のセキュリティログを継続的に生成する
- インシデント発生時、アナリストはこれを手動でトリアージし、攻撃の有無・範囲を判断する
- ログの量・速度・複雑さの増大により、人手対応には構造的な限界がある

**インシデント分析の典型的な流れ:**

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ アラート  │───▶│ ログ収集  │───▶│ 異常検知  │───▶│ 原因特定  │───▶│ 対応判断  │
│ 発生     │    │          │    │          │    │          │    │          │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
                                       │                │
                                       └────────────────┘
                                        ここが最も人手依存
```

**話者メモ:**
- 「異常検知 → 原因特定」の間でアナリストがログを一件ずつ確認するのが現状
- この負荷を下げるためのアプローチが本研究のモチベーション

---

### Slide 2: 先行研究と課題

**メッセージ:** 攻撃の検知は進んでいるが、偽陽性の正体（正常行動）は未整理

**先行研究の整理:**

| 対象 | 研究の蓄積 |
|---|---|
| 異常検知手法 | 多数（IsolationForest, LOF, Transformer系 etc.） |
| 攻撃ログの分類・分析 | MITRE ATT&CK等の整理が進む |
| **正常行動の定義・分類** | **ほぼ手付かず** |

**課題:**

```
異常検知の上位候補
        │
        ├─── attack（攻撃）     ◀ 既存研究が対象
        │
        └─── normal（正常）    ◀ 「何の正常行動か」が定義されていない
               = 偽陽性 (False Positive)
                      ↑
               ここが未整理
```

> **言いたいこと:** 偽陽性の存在は知られているが、「偽陽性の中身（正常行動のパターン）」を系統的に整理する手法がない

---

### Slide 3: 研究目的

**メッセージ:** 正常行動のユースケースを定義することで、偽陽性分析を自動化支援する

**研究目的（1文）:**

> **インシデント分析自動化支援に向けて、異常検知で上位化した sequence から正常行動パターンを復元し、偽陽性化しやすい正常行動ユースケースを定義する。**

**3つの貢献:**

1. 異常検知出力（sequence）を直接の入力として使う分析フローの設計
2. sequence 内の正常行動を系統的に分類するユースケース候補の選定
3. 正解データの試作による評価軸の整備

---

### Slide 4: 提案システム全体像

**メッセージ:** 異常検知→sequence観察→ユースケース定義という一貫したフローを構成する

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        提案システム概要                                   │
│                                                                         │
│  [入力]                [処理]                      [出力]               │
│                                                                         │
│  ATLAS v2             ┌─────────────┐             正常行動              │
│  エンドポイント  ───▶  │ 異常検知     │ ───▶       ユースケース定義        │
│  ログ                 │ (LOF)       │             ・対象プロセス          │
│                       └──────┬──────┘             ・発火条件             │
│                              │ 高スコア            ・イベント列パターン    │
│                              ▼ sequence                                 │
│                       ┌─────────────┐                                   │
│                       │ sequence 内  │                                   │
│                       │ 正常候補抽出 │                                   │
│                       └──────┬──────┘                                   │
│                              │                                          │
│                              ▼                                          │
│                       ┌─────────────┐                                   │
│                       │ ユースケース  │                                   │
│                       │ 候補の分類   │  ◀── 本発表ではここまで完了        │
│                       └─────────────┘                                   │
│                                                                         │
│  ※ 行動復元（CLOUSEAU拡張版）は設計段階                                   │
└─────────────────────────────────────────────────────────────────────────┘
```

**なぜ sequence を入力単位にするか:**

```
従来のアプローチ（粒度のズレ）         本研究のアプローチ（粒度の一致）

  異常検知 ──▶ sequence単位で出力       異常検知 ──▶ sequence単位で出力
       ↓                                     ↓
  後段分析 ◀── 個別ログを再収集          後段分析 ◀── sequence をそのまま入力
               （粒度のズレ）                         （粒度が一致）
```

- 「なぜその候補を見るか」→「高スコア sequence だから」と一貫して答えられる
- 周辺文脈ごと観察できるため、「なぜ偽陽性になったか」を説明しやすい

### Slide 5: 実験設定

**メッセージ:** ATLAS v2 の 4 シナリオを対象に、LOF を用いた sequence ランキングを実施

**データセット: ATLAS v2**

| 項目 | 内容 |
|---|---|
| ログ種別 | Windows Security Audit Log (EventID 4656/4663/4658 等) |
| 攻撃シナリオ | 実際の攻撃シーケンスを含む |
| 使用シナリオ | **S3 / M4 / M6 / S4** |

**シナリオ特性の概要:**

```
S3 ──── 攻撃イベントを含む。正常と攻撃が混在した構造
M4 ──── 攻撃なし。Office 業務操作が中心
M6 ──── 攻撃なし。Office + バックグラウンド管理の混成
S4 ──── 攻撃なし。スキャン・更新・WMI 系の背景動作が中心
```

**異常検知パイプライン:**

```
生ログ
  │
  ▼
[前処理] 100 event / chunk 単位に分割
  │
  ▼
[LOF 異常検知] chunk 単位でスコアリング
  │
  ▼
[top10 chunk 選出] 1,000 events を分析対象に
  │
  ▼
[10 event micro-chunk に再分割]
  │
  ▼
[rarity ベースで top10 micro-chunk 選出] 100 events が最終観察対象
```

**注意:** S3 は既存の LOF third pass の系譜。M4/M6/S4 は同形式への再構成（完全同一手法ではない）

### Slide 6: 結果①：S3 における偽陽性候補の整理

**メッセージ:** top10 micro-chunk 100 events から 60 events の偽陽性候補を抽出し、説明力の高い 40 events を特定した

#### 6-1. 100 events の内訳

```
top10 micro-chunk（100 events）

  ┌─────────────────────────────────────────────────────┐
  │                     100 events                      │
  │                                                     │
  │  ┌───────────┐  ┌─────────────────┐  ┌───────────┐ │
  │  │  attack   │  │  label=0 かつ   │  │  label=0  │ │
  │  │  label=1  │  │ payload.exe     │  │  非payload│ │
  │  │  11 件    │  │  29 件          │  │  60 件    │ │
  │  └───────────┘  └─────────────────┘  └─────┬─────┘ │
  │                                             │       │
  └─────────────────────────────────────────────┼───────┘
                                                │
                                      偽陽性候補の母集団
                                      （"60ログ"）
```

#### 6-2. 60ログの内部構造

```
60ログ（label=0 かつ 非payload）

  attack 近傍の正常側（20件）          説明力の高い正常候補（40件）
  ┌────────────────────────┐          ┌─────────────────────────────────┐
  │ seq 1,2,3,4,5,8        │          │ seq 6: repmgr.exe ×6            │
  │                        │          │        tpautoconnect ×4         │
  │ tpautoconnect.exe の   │          │        → 文書関連アクセス         │
  │ 単発・短列が中心        │          │                                 │
  │                        │          │ seq 7: explorer.exe ×3          │
  │ payload.exe 近傍に      │          │        tpautoconnect ×7         │
  │ 付随した背景 event      │          │        → ファイル参照・画面操作  │
  │ → 独立ユースケースに    │          │                                 │
  │   はしにくい            │          │ seq 9: repmgr.exe ×1            │
  └────────────────────────┘          │        tpautoconnect ×9         │
                                      │        → 文書関連アクセス（補強）│
                                      │                                 │
                                      │ seq 10: winword.exe ×1          │
                                      │         tpautoconnect ×9        │
                                      │         → 文書閲覧              │
                                      └─────────────────────────────────┘
```

#### 6-3. S3 から得られた正常ユースケース候補（3系統）

| 系統 | 代表プロセス | EventID パターン | 読み |
|---|---|---|---|
| 文書関連アクセス | `repmgr.exe` | 4656 → 4663 → 4658 | 文書オブジェクトへのアクセス連鎖 |
| ファイル参照・画面操作 | `explorer.exe` | 4656 → 4663 → 4656 | ユーザのファイル操作 |
| 文書閲覧 | `winword.exe` | 4658 → 4656 → ... | 文書を開く動作 |

**背景:** 全シーケンスに共通して `tpautoconnect.exe` の反復（4656/4663/4658）が存在するが、これは背景ノイズとして切り分け、上記3系統を主体とする

### Slide 7: 結果②：複数シナリオへの展開

**メッセージ:** M4 / M6 / S4 に展開すると、正常ユースケース候補の種類が大きく増える

#### 7-1. 4シナリオ横断の 10×10 比較

                 │  attack 19件    │       normal 81件          │
                 └─────────────────────────────────────────────┘
  
                 ┌─────────────────────────────────────────────┐
  M4             │░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
                 │                 normal 100件                 │
                 └─────────────────────────────────────────────┘
  
                 ┌─────────────────────────────────────────────┐
  M6             │░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
                 │                 normal 100件                 │
                 └─────────────────────────────────────────────┘
  
                 ┌─────────────────────────────────────────────┐
  S4             │░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
                 │                 normal 100件                 │
                 └─────────────────────────────────────────────┘

  ███ = attack    ░░░ = normal
```

- **S3 のみ** top10 micro の段階で attack が混在（19件）
- **M4 / M6 / S4** は top10 micro の時点で 100% normal

#### 7-2. シナリオごとに増えた正常候補の型

```
正常ユースケース候補マップ

  ユーザ操作色が強い
        ▲
        │
        │   M4 ●───── excel.exe（業務ファイル操作）
        │       └──── mmc.exe, consent.exe（管理操作）
        │
        │   M6 ●───── excel.exe（業務操作）
        │       └──── wmiapsrv.exe（背景管理）
        │
        │   S3 ●───── repmgr / explorer / winword（文書・ファイル操作）
        │              ※ attack-near 文脈の中から抽出
        │
        │   S4 ●───── scanhost.exe, upd.exe（スキャン・更新）
        │       └──── wmiapsrv.exe（WMI管理）
        │
  背景動作色が強い
        ▼
```

#### 7-3. 各シナリオの発表における役割

| シナリオ | 発表での位置づけ | 主要プロセス |
|---|---|---|
| **M4**（主ケース） | 業務操作の代表例。説明力が最も高い | excel.exe, mmc.exe, consent.exe |
| **M6**（補強ケース） | Office + 背景管理の混成。実環境らしさを加える | excel.exe, wmiapsrv.exe |
| **S4**（対照ケース） | 背景動作型 normal の代表。ユーザ操作との対比に使う | upd.exe, scanhost.exe, wmiapsrv.exe |
| **S3**（境界ケース） | 攻撃近傍でも正常候補を拾えることを示す | repmgr.exe, explorer.exe, winword.exe |

**言えること:**
- S3 単独だと `tpautoconnect.exe` 反復に偏り、ユースケースの種類が限られる
- M4 / M6 / S4 を足すと Office 系・管理系・背景動作系が増え、**件数だけでなくユースケースの種類が広がる**

**今後の課題:**

```
現在地                       次のステップ
  │
  ▼
[ユースケース候補の選定] ──▶ [正常行動の定義確定]
  （完了）                          │
                                    ▼
                         [CLOUSEAUベース復元手法の実装]
