# 100ログ選定手法の解説

作成日: 2026-05-19

---

## 1. 概要

この選定は「Security ログの異常検知出力を起点に、Sysmon ログで正常行動の文脈を確認し、
シナリオごとに 100 イベントの正常ユースケース候補を揃える」という手順で行われている。

---

## 2. 全体フロー

```
┌──────────────────────────────────────────────────────────────────┐
│ Step 1: Security ログ 異常検知                                     │
│                                                                  │
│  生ログ ──▶ first pass (coarse) ──▶ second pass ──▶ review queue │
│             IsolationForest 等        絞り込み       候補セッション群 │
└──────────────────────────────┬───────────────────────────────────┘
                               │ 候補セッション (host|user|10分粒度)
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│ Step 2: Sysmon minute への変換                                    │
│                                                                  │
│  候補セッション                                                    │
│      ├──▶ sysmon_exact_user_minutes   同一ホスト・ユーザー・10分枠 │
│      └──▶ sysmon_same_host_minutes    同一ホスト・全ユーザー・10分枠│
│                                                                  │
│  ※ Security の bucket を 10分単位に丸めて Sysmon と突合せる        │

│  2. core_normal      ─ preferred_normal プロセスが入っている       │

│  4. neutral_context  ─ 上記のいずれでもない                       │
```

## 3. Step 2: Security → Sysmon minute への変換

Security ログと Sysmon ログは別のイベントソースなので、**時刻を 10 分粒度に丸めてキーを揃えることで突合せる**。

```
Security セッション: win-32-h1 | aalsahee | 20220719T2238Z
                                              ↓ 10分フロア
突合せキー (exact):  win-32-h1 | aalsahee | 20220719T2230Z
突合せキー (host):   win-32-h1 |           | 20220719T2230Z
```

- `exact_user_minutes`: 同一ホスト・同一ユーザーの Sysmon minute
- `same_host_minutes`: 同一ホストの全ユーザーの Sysmon minute（ギャップ補完用）

→ Security 異常検知が「この時間帯・このホストが怪しい」と言っている窓を、
  Sysmon の分単位ログで覗き込む形になっている

## 4. Step 3: minute の 4 分類ロジック

minute の分類は、**その minute に含まれるプロセス名（Image）で決まる**。

```python
def classify_bucket(images: set[str], config: dict) -> str:
    if images & config["suspicious"]:
        return "attack_near"          # ← 最優先で除外
    if images & config["preferred_normal"]:
        return "core_normal"          # ← 正常候補の核
    if images and images <= config["background"]:
        return "background_context"   # ← 背景動作のみ
    return "neutral_context"          # ← 判断保留
```

### 分類に使うプロセスリスト

```
【suspicious（attack_near 判定）】
  payload.exe, powershell.exe, mshta.exe, regsvr32.exe, eqnedt32.exe
  → 既知の攻撃ツール or 悪用されやすいインタープリタ

【preferred_normal（core_normal 判定）—シナリオ別】
  M4: excel.exe, mmc.exe, winword.exe
  M6: excel.exe, winword.exe
  S4: upd.exe, winword.exe, mmc.exe
  S3: explorer.exe, winword.exe
  → 業務操作・管理操作の代表プロセス

【background（background_context 判定）】
  repwmiutils.exe, searchprotocolhost.exe, searchfilterhost.exe,
  dllhost.exe, conhost.exe, svchost.exe, wmiapsrv.exe ... など
  → OS/サービス系のバックグラウンド動作
```

### 分類の優先順位の意味

| 優先度 | 分類 | 意味 |
|---|---|---|
| 1（最優先除外） | attack_near | suspicious が1件でもあれば問答無用で除外 |
| 2（採用優先） | core_normal | preferred_normal が含まれる → 正常ユースケース候補の核 |
| 3（補完用） | background_context | 背景動作のみ → 核が足りないときの充填材 |
| 4（判断保留） | neutral_context | 上記以外 → 充填材として使うが優先度は低い |

---

## 5. Step 4: 100 イベントへのギャップフィル

```
分類済み minute を優先度順に並べる

  core_normal       →  先に選ぶ
  neutral_context   →  次に選ぶ
  background_context →  その次
  attack_near       →  スキップ（使わない）

minute を1つずつ取り出し、含まれるイベントを積み上げる
イベント数合計が 100 に達したら終了

（1 minute のイベント数は可変なので、最後の minute は途中で切れることがある）
```

**「core_normal minute が少なくても 100 ログにできる」のは、
background_context や neutral_context の minute でギャップを埋めているから。**

## 6. シナリオ別の選定結果と読み

```
シナリオ別 core_normal minute 数と採用判断

  M4 ────────────── core_normal: 3 minute ──── 正式採用
  │                  mmc.exe / excel.exe / winword.exe
  │                  → 業務操作 + 管理操作の主体が揃っている

  S4 ────────────── core_normal: 1 minute ──── 正式採用
  │                  upd.exe / repwmiutils.exe
  │                  → 更新・同期系の核は1本だが、
  │                    背景文脈が揃っており説明可能

  M6 ────────────── core_normal: 1 minute ──── 条件付き採用
  │                  excel.exe（1 minute のみ）
  │                  → 主役が弱い。100ログの大半は背景文脈埋め
  │                  → 補助ケース・比較用として使う

  S3 ────────────── core_normal: 0 minute ──── 見送り
                     core_normal が1本も取れなかった
                     → 正常ユースケースの主体が不在
                     → 攻撃近傍の対照例として別途使用
```

---

## 7. この手法で保証されること・保証されないこと

**保証されること:**

- 100 ログ中に `payload.exe` など既知攻撃プロセスは含まれない
- `core_normal minute` を持つシナリオは、正常の主体プロセスが少なくとも 1 minute 分ある
- Security 異常検知が反応した時間帯・ホストから選んでいる（脈絡がある）

**保証されないこと:**

- 100 ログ全件が core_normal プロセスで占められるわけではない
  → 特に M6・S4 は background_context が大半
- Sysmon と Security でイベント粒度が異なるため、完全な 1 対 1 対応はない
- 「正常である」という証明ではなく、「attack label のないプロセスが主体である」という消去法的な選定

---

## 8. 発表での説明のしかた

```
【選定方法の短い説明】

Security ログの異常検知で上位化したセッションを起点に、
同一時間帯・同一ホストの Sysmon ログを突合せた。
各 1 分窓を「攻撃近傍（payload.exe 等を含む）」か
「正常系（Excel・MMC・Word 等を含む）」かで分類し、
攻撃近傍を除外した上で優先度順に 100 イベントを選定した。

最終的に正式採用となったのは S4 と M4、補助ケースとして M6 を使用する。
S3 は正常主体プロセスが確保できなかったため正常ユースケースから除外し、
攻撃近傍との対照例として扱う。
```
