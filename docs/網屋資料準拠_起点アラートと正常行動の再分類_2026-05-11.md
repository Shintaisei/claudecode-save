# 網屋資料準拠 起点アラートと正常行動の再分類

更新日: 2026-05-11

## 1. 目的

この文書は、[0417_網屋資料確認_小松崎.pdf](/c:/Users/komat/OneDrive/Desktop/ATLAS以外のデータセット/0417_網屋資料確認_小松崎.pdf:1) の定義に合わせて、現在のユースケース整理をやり直すためのもの。

今回の見直しで最も重要なのは次の 2 点。

1. **起点アラート** と **正常行動** は別軸である
2. 現在の ATLAS 系抽出結果は、まだ `高特異性起点` を直接は与えていない

したがって、これまでの process ベースの 9 マスは、そのままでは PDF の定義とずれていた。
ここではまず PDF の定義を固定し、その後に現データをその定義へ写像する。

## 2. PDF に基づく定義

### 2.1 起点アラートの種類

PDF 5 ページの定義は次。

| 起点アラートの種類 | 探索上の性質 | 典型例 |
| --- | --- | --- |
| `高特異性起点` | 候補を狭く保ちやすく，探索を始めやすい | 特定ファイル，特定 URL |
| `中特異性起点` | 追加条件があれば使えるが，単独では分岐しやすい | 不審IP，端末 |
| `低特異性起点` | 候補が拡散しやすく，行動境界も切りにくい | 宛先IP単独，共有サーバ |

ここでの本質は、**起点アラートの特異性は process 名の珍しさではなく、候補空間をどれだけ狭められるか** で決まること。

### 2.2 正常行動の種類

PDF 6 ページの定義は次。

| 正常行動の種類 | 復元上の性質 | 典型例 |
| --- | --- | --- |
| `単発操作型` | 境界が比較的明瞭で，主体・対象を切り出しやすい | Web閲覧，添付取得 |
| `手続型` | 複数操作が連なり，まとまりとしては追えるが，境界がやや曖昧 | メール受信→添付取得→文書閲覧 |
| `背景動作型` | 常駐・周期・副作用が混ざりやすく，境界も主体も切りにくい | SearchIndexer，OSメンテナンス |

ここでの本質は、**正常行動の型は process 名ではなく、主体・行為・対象・連鎖の切り出しやすさで決める** こと。

## 3. 何がずれていたか

前回までの整理では、`explorer.exe` や `repmgr.exe` のような process 候補をそのまま
`高 x 単発操作型` のように置いていた。

しかし PDF の定義に忠実に言うと、これは 2 つの意味で混線していた。

1. `explorer.exe` は **正常行動候補** であって、起点アラートの種類そのものではない
2. `high / medium / low` は process の見やすさではなく、**起点として与えられる情報の絞り込み能力** を指す

つまり、`explorer.exe` が見えたから高特異性、ではない。
`特定ファイルを開いた explorer.exe` まで分かれば高特異性になり得るが、
現状の抽出結果はそこまで持っていない。

## 4. 現在のデータで本当に得られている起点情報

### 4.1 直接得られている属性

現在の review CSV から機械的に取れる属性は次。

- host
- 主体
- session 時刻
- process 名
- Event ID
- `ObjectType=file`
- 10 event 窓の process 構成
- `sequence rank`
- `micro rank`
- LOF score

### 4.2 直接は得られていない属性

今回の分析で `fields_json` のキーを確認したところ、主要キーは
`Provider`, `Channel`, `EventID`, `ProcessName`, `ObjectType` にほぼ限られていた。

特に重要なのは次。

- `ObjectName` は `0` 件
- 特定 URL を表す属性も `0` 件
- 特定ファイルパスで高特異性起点を作れる材料は、現 review 出力には無い

つまり、**今の抽出結果は process 中心の異常 micro-chunk であって、PDF で言う「特定ファイル」「特定URL」起点はまだ復元できていない**。

## 5. PDF 定義に基づく再分類ルール

### 5.1 起点アラート側の分類ルール

今回は次のルールで置き直す。

#### `高特異性起点`

次のどれかが必要。

- 特定ファイルパス
- 特定URL / ドメイン
- 特定レジストリキー
- 特定タスク名
- 特定サービス名

現状の review 出力だけでは、ここに直接置けるものは **ない**。

#### `中特異性起点`

次のような条件で限定すれば追えるもの。

- `host + user/session + process + local time window`
- 10 event 窓で process 切替点が見える
- 周辺 micro-chunk を見ればまとまりが追えそう

今回の `explorer.exe / winword.exe / repmgr.exe / firefox.exe` は基本的にここ。

#### `低特異性起点`

次のように候補空間が広すぎるもの。

- 背景サービス単独
- host 側サービス文脈だけ
- 同型窓が大量反復
- 対象オブジェクトが見えない

今回の `spoolsv.exe / tpautoconnsvc.exe / repwmiutils.exe` は基本的にここ。

### 5.2 正常行動側の分類ルール

#### `単発操作型`

- 対話ユーザ文脈
- 同一窓で process 数が少ない
- その process を見れば、何をしていたかの方向性が比較的言いやすい

対象:
- `explorer.exe`
- `winword.exe`
- `firefox.exe`

#### `手続型`

- まとまりとしては追えそうだが、単独 event だけでは完結しない
- 前後の process や近傍 micro が必要

対象:
- `repmgr.exe`

#### `背景動作型`

- 主体が `win-32-h1$`
- 常駐/反復/副作用が中心
- 同型 micro が大量に出現
- 行為の境界が切りにくい

対象:
- `repwmiutils.exe`
- `spoolsv.exe`
- `tpautoconnsvc.exe`

ここで重要なのは、`repwmiutils.exe` は前回やや「手続型」寄りに置いていたが、
PDF の定義に忠実に見ると **背景動作型へ寄せる方が妥当** という点。
理由は、主体が `win-32-h1$` であり、10 event 窓すべて同一 process の反復で、対象オブジェクトも切れていないため。

## 7. この再分類から言えること

### 7.1 いま本当に持っているのは「中心評価領域 + 破綻領域」

PDF 7 ページの仮説表に照らすと、現在のデータは次を比較する形になっている。

- `中特異性起点 x 単発操作型`
  - `explorer.exe`, `winword.exe`, `firefox.exe`
- `中特異性起点 x 手続型`
  - `repmgr.exe`
- `低特異性起点 x 背景動作型`
  - `repwmiutils.exe`, `spoolsv.exe`, `tpautoconnsvc.exe`

これはちょうど、

- 条件付きで成立しやすい領域
- 中心的な評価領域
- 最も破綻しやすい領域

を押さえている。

### 7.2 逆に、左上はまだ取れていない

現在の出力だけでは、

- 特定ファイル
- 特定 URL
- 特定タスク名

のような高特異性起点が取れていないため、PDF でいう左上はまだ埋まっていない。

これは弱点ではあるが、同時に **実験での限界点** でもある。
つまり、

> process レベルの異常 micro-chunk だけからでは、起点アラート特異性を高く保てない

という限界そのものが、次の実験で検証すべき点になる。

## 8. 研究の主張をどう修正するか

前回までの

> 高特異性帯に `explorer.exe / winword.exe / repmgr.exe`

という言い方は撤回した方がよい。

代わりに、次のように言うのが PDF と整合的。

> 本研究で現在抽出できているのは、異常検知で上位化した process 中心の micro-chunk である。これらは特定ファイルや特定URLを直接含まないため、高特異性起点ではなく、主として中特異性起点から低特異性起点に相当する。一方で、正常行動側では単発操作型・手続型・背景動作型への分化が観察できるため、起点特異性の不足がどの型でどの程度ボトルネックになるかを比較する実験系として意味がある。

## 9. これから追加でやるべき分析

PDF 定義に本当に沿わせるには、次の順が自然。

1. `ObjectName` やファイルパスを元ログから再取得する
2. `firefox.exe` について browser artifact や domain を復元する
3. タスク名、サービス名、ファイル名が取れたケースを `高特異性起点` として新設する
4. 現在の process-only 候補は `中特異性/低特異性` として残す

## 10. 現時点の結論

### 10.1 できていること

- 正常行動の型の分化
  - 単発操作型
  - 手続型
  - 背景動作型
- 中特異性起点から低特異性起点における成立/破綻比較

### 10.2 まだできていないこと

- 高特異性起点の確保
- 特定ファイル/URL を伴う起点定義

### 10.3 実験上の限界として言えること

> 現在の異常検知出力は、正常行動の型分類には使えるが、起点アラートの高特異性化には十分ではない。したがって、process 中心の異常窓だけでどこまで復元できるか、どこで破綻するかが、本実験系の本質的限界点になる。
