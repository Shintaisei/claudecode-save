# ATLAS v2 S3 最終正常候補の行動復元と研究分類

更新日: 2026-05-04

## 1. この分析の目的

ここまでの異常検知フローで、S3 の attack day から

- coarse sequence
- second-pass review window
- high-confidence seed

まで絞り込みを行った。  
この段階の次の問いは、

**最終候補として残った normal-dominant seed から、研究で使える正常行動を復元できるか**

である。

今回の分析では、最終候補に残った正常寄りログを

- `主体`
- `行為`
- `対象`
- `連鎖`

の観点で復元し、そのうえで研究で使っている分類

- `単発操作型 / 手続型 / 背景動作型`
- `正常 / 正常寄り / 判断不能 / 要追加調査`

へ落とし込む。

## 2. 使った入力

最終的に normal 行動分析へ回したのは、high-confidence seed のうち normal 比率が高い帯である。

参照:
- [security_sysmon_high_confidence_seed_s3/results.json](/c:/Users/komat/OneDrive/Desktop/ATLAS以外のデータセット/analysis_data/model_runs/security_sysmon_high_confidence_seed_s3/results.json:1)
- [normal_behavior_analysis_s3/results.json](/c:/Users/komat/OneDrive/Desktop/ATLAS以外のデータセット/analysis_data/model_runs/normal_behavior_analysis_s3/results.json:1)

全体像は次の通りである。

- high-confidence seed 全体: `6 window / 3,000 event`
- 内訳: `attack=195 / normal=2,805`
- normal 比率 `95%` 以上の normal-dominant seed: `5 window / 2,300 event`
- normal-dominant 内訳: `attack=40 / normal=2,260`

## 3. まず全体の見立て

最終候補として残った normal-dominant seed は、window 単位では 5 本ある。  
ただし、行動として見ると次の 3 つの塊にまとまる。

1. `regsvr32.exe` 中心の file access 手続
2. `powershell.exe` 中心の script-driven file access 手続
3. `payload.exe` 中心の高密度 file access 手続

この 3 つは、研究分類へ落とすとすべて同じ意味ではない。

- `regsvr32.exe` と `powershell.exe` は、attack-near normal context としてかなり使いやすい
- `payload.exe` は normal 比率自体は高いが、主体の意味づけが弱く、正常と断定しにくい

したがって、**最終候補 5 本 = 5 つの独立した正常行動** ではなく、  
**3 種類の行動クラスターにまとまり、そのうち 2 クラスターが研究用の正常候補として強い**

と解釈するのが自然である。

## 4. 復元ケース A: `regsvr32.exe` 中心の手続型行動

### 4.1 対応する seed

- `chunk 181-183`: `300 event`, `attack 1`, `normal 299`, `normal_ratio 99.7%`
- `chunk 251-252`: `200 event`, `attack 1`, `normal 199`, `normal_ratio 99.5%`

### 4.2 主体・行為・対象・連鎖

- 主体
  `regsvr32.exe`
- 行為
  file object への反復アクセス
- 対象
  `ObjectType=file`
- 連鎖
  `regsvr32.exe` の周辺に `repmgr.exe`, `eqnedt32.exe`, `taskhost.exe`, `csrss.exe` が見える

### 4.3 根拠

normal 側で優勢だった EventID は主に次である。

- `4656`
- `4658`
- `4663`

また normal 側の主要 process は

- `regsvr32.exe`
- `repmgr.exe`
- `eqnedt32.exe`
- `taskhost.exe`
- `csrss.exe`

である。

つまり、単発の process start/stop だけではなく、

- `regsvr32.exe` が連続して file にアクセスし
- その近傍に複数の周辺 process が混じる

という、一定のまとまりを持った手続として読める。

### 4.4 行動復元

この帯は、

**ユーザー作業帯の中で、`regsvr32.exe` を中心に複数ファイルへ連続アクセスが発生し、周辺で `eqnedt32.exe` や `taskhost.exe` も動いている手続型行動**

として復元できる。

ここで重要なのは、`regsvr32.exe` 自体は LOLBin として攻撃にも使われやすい点である。  
そのため pure benign と断定はしにくいが、今回残っているイベント列自体はほぼ normal であり、周辺 process も含めて「攻撃近傍にある正常寄りの手続」として扱う余地がある。

### 4.5 研究分類

- 行動種別: `手続型`
- 判定: `正常寄り`

### 4.6 この判定にした理由

`単発操作型` ではなく `手続型` とした理由は、

- file access が数百 event 規模で持続している
- 周辺 process が複数見えている
- 1 回の閲覧やクリックではなく、連続処理として読める

ためである。

また `正常` ではなく `正常寄り` とした理由は、

- 主体が `regsvr32.exe` で攻撃にも使われやすい
- attack day の近傍で出ている
- attack event は少量だが 0 ではない

ためである。

### 4.7 研究利用価値

このケースは、**「攻撃にも見えやすいが、実際には大半が正常イベントで構成される管理・補助処理」** の例として使いやすい。  
false positive 研究や、正常寄り手続型の境界事例として特に有用である。

## 5. 復元ケース B: `powershell.exe` 中心の手続型行動

### 5.1 対応する seed

- `chunk 271-274`: `400 event`, `attack 3`, `normal 397`, `normal_ratio 99.2%`
- `chunk 295-298`: `400 event`, `attack 1`, `normal 399`, `normal_ratio 99.8%`

### 5.2 主体・行為・対象・連鎖

- 主体
  `powershell.exe`
- 行為
  script-driven な連続 file access
- 対象
  `ObjectType=file`
- 連鎖
  周辺に `csrss.exe`, `vmtoolsd.exe` が見える

### 5.3 根拠

normal 側で主要だった EventID は

- `4656`
- `4658`
- `4663`

であり、テンプレート上も

- `ProcessName=powershell.exe | ObjectType=file`

が大半を占める。

つまり、PowerShell を主体として

- file を開く
- file へアクセスする
- handle を閉じる

が反復しており、単発のコマンド実行というよりは、まとまった処理の一部として読める。

### 5.4 行動復元

この帯は、

**`powershell.exe` を主体にした連続 file access 手続であり、ユーザー文脈の中で script または自動化処理が動いている帯**

として復元できる。

周辺に `vmtoolsd.exe` や `csrss.exe` が混じることから、完全な孤立プロセスではなく、ユーザーセッション／VM環境の中で動いていた可能性が高い。

### 5.5 研究分類

- 行動種別: `手続型`
- 判定: `正常寄り`

### 5.6 この判定にした理由

`PowerShell` は研究上とても重要である。  
理由は、攻撃でも正常管理・自動化でも使われる典型的な境界主体だからである。

今回の帯を `正常寄り` とした理由は、

- attack event は `1-3件` とごく少ない
- normal 比率が `99%` 前後で非常に高い
- event の大半が file access の反復で、破壊的操作や明確な侵害痕だけではない

ためである。

一方で `正常` と断定しなかったのは、

- `powershell.exe` 自体が攻撃チェーンの近傍にある
- attack-near context である

ためである。

### 5.7 研究利用価値

このケースは、**「攻撃にも正常にも見える PowerShell 行動を、どこまで正常文脈として説明できるか」** を見る中心例として使いやすい。  
今回の最終候補の中でも、研究分類へ最も落とし込みやすい正常寄り seed である。

## 6. 復元ケース C: `payload.exe` 中心の高密度 file access 行動

### 6.1 対応する seed

- `chunk 331-340`: `1000 event`, `attack 34`, `normal 966`, `normal_ratio 96.6%`

補足として、近接帯に

- `chunk 323-329`: `700 event`, `attack 155`, `normal 545`, `normal_ratio 77.9%`

がある。

### 6.2 主体・行為・対象・連鎖

- 主体
  `payload.exe`
- 行為
  非常に高密度な file access
- 対象
  `ObjectType=file`
- 連鎖
  周辺に `csrss.exe` が見える

### 6.3 根拠

この帯の normal 側でも、

- `ProcessName=payload.exe | ObjectType=file`

が圧倒的多数を占める。  
EventID も

- `4656`
- `4658`
- `4663`

に強く集中している。

つまり、「payload.exe が継続的に大量の file object へアクセスしている帯」であること自体はかなり明確である。

### 6.4 行動復元

この帯は、

**`payload.exe` を主体にした大規模な file access 手続**

として復元できる。  
ただし、ここでの問題は event の大半が normal ラベルであることではなく、**主体そのものが `payload.exe` である** 点である。

normal ラベルが多い理由は、

- Security の event-level ラベル付けが「その瞬間の攻撃判定」だけで付いている
- 同じ process の前後アクセスまで全て attack 扱いにはなっていない

可能性が高い。

したがって、この帯は

- normal event が多い
- だが意味的には正常行動候補としては弱い

という、研究上重要な境界事例である。

### 6.5 研究分類

- 行動種別: `手続型`
- 判定: `判断不能` もしくは `要追加調査`

### 6.6 この判定にした理由

`手続型` とした理由は、

- 数百〜千 event 規模のまとまった file access 連鎖
- 単発ではない継続的処理

だからである。

一方で `正常寄り` にしなかった理由は、

- 主体が `payload.exe`
- 近接帯の attack 密度がかなり高い
- 正常文脈ではなく、攻撃チェーンの連続部分の可能性が高い

ためである。

### 6.7 研究利用価値

このケースは、「正常候補として採用する」より、

- normal-dominant に見えても主体次第では採用できない
- event-level normal 比率だけでは正常行動と断定できない

ことを示す反例として有用である。

## 7. 今回の最終分類まとめ

最終候補として残った normal-dominant seed を、研究分類へまとめると次のようになる。

| ケース | 主体 | 代表 seed | 行動種別 | 判定 | 研究上の位置づけ |
| --- | --- | --- | --- | --- | --- |
| A | `regsvr32.exe` | `181-183`, `251-252` | 手続型 | 正常寄り | LOLBin 境界事例、管理・補助処理寄り |
| B | `powershell.exe` | `271-274`, `295-298` | 手続型 | 正常寄り | script / 自動化境界事例、中心分析対象 |
| C | `payload.exe` | `331-340` | 手続型 | 判断不能 / 要追加調査 | normal 比率は高いが主体が不自然な反例 |

## 8. 今回の結果を研究分類の観点で読む

今回の最終候補は、`単発操作型 / 背景動作型` よりも、かなり強く `手続型` に偏っている。

これは次の意味を持つ。

1. 今回の抽出フローは、attack-near な process 連鎖を残しやすい
2. そのため、単発の閲覧・クリックよりも、script / registration / payload 周辺の手続が残りやすい
3. 現時点の S3 では、「研究に使える正常候補」は主に `手続型` として得られている

逆に言うと、

- `単発操作型` の正常行動復元
- `背景動作型` の正常行動復元

は、今回の S3 最終候補からはあまり得られていない。

この点は限界でもあるが、同時に

**S3 の最終候補は「手続型正常行動の境界事例」を集中的に観察する材料として強い**

とも言える。

## 9. 今回ここまでで言えること

少なくとも今回の最終候補については、次の整理がかなり妥当である。

1. 残った正常寄りログは、単なるノイズではなく行動単位へ復元できる
2. 復元できた行動の中心は `手続型`
3. その中でも `powershell.exe` と `regsvr32.exe` は研究用正常候補としてかなり有望
4. `payload.exe` は normal 比率が高くても、主体の不自然さから採用保留にすべき
5. したがって「normal ratio が高い = 正常行動」ではなく、主体・行為・対象・連鎖まで見て分類する必要がある

## 10. 研究上の最終整理

今回の S3 では、最終候補として残った normal-dominant seed から、

- **採用候補**
  `powershell.exe` 手続 2 本
  `regsvr32.exe` 手続 2 本
- **保留候補**
  `payload.exe` 手続 1 本

という形で、研究分類へ落とし込める。

そのため、現時点での結論は次である。

**ATLAS v2 S3 の最終候補からは、attack-near normal context として使える手続型正常行動が複数復元できた。特に PowerShell 系と regsvr32 系は、正常寄りの手続型行動として研究に採用しやすい。**
