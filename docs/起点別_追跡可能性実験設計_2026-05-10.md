# 起点別の追跡可能性実験設計

更新日: 2026-05-10

## 1. この実験で見たいこと

- 異常検知で自然に上位化された起点から、後続ログをどこまで追跡できるか
- 追跡結果が `正常 / 攻撃 / 判定不能` のどれに落ちやすいか
- その差が、起点プロセスの種類によって説明できるか

## 2. 今回の実験対象

- 起点候補は `LOF top10 micro-chunk = 100 event` から抽出したものだけを使う
- `payload.exe` と `tpautoconnect.exe` は起点候補から外す
- 対象プロセスは次の3つ
  - `explorer.exe`
  - `winword.exe`
  - `repmgr.exe`

## 3. 実験の基本設計

### 3.1 単位

- 1 起点 = 1 event もしくは 1 micro-chunk
- まずは今回見つかった起点候補を全部採用する
- 各起点について、前後の関連ログを一定範囲で追う

### 3.2 評価したい軸

1. 起点の意味が明確か
2. 後続ログの追跡ルールを機械的に書けるか
3. 追跡結果を `正常 / 攻撃 / 判定不能` に分けやすいか
4. 人手解釈がどの程度必要か

### 3.3 最終分類

- `追跡可能`
  - ルールで後続候補をかなり安定して引ける
  - 結果の意味づけも比較的安定する
- `半追跡可能`
  - 後続は引けるが、意味づけに周辺文脈が必要
- `追跡困難`
  - 起点の意味が弱いか、後続候補が広がりすぎる

## 4. 候補ごとの分析

### 4.1 explorer.exe

- 見えている正常行動
  - ファイル参照
  - フォルダ操作
  - ファイル選択
- 今回の出現
  - `rank 7`
  - `3 event`
- 追跡しやすさ
  - 高い
- 追える後続の例
  - 同時間帯の `4656 / 4663 / 4658`
  - 同一ファイルや近接ファイルへのアクセス
  - 直後の `winword.exe` など文書アプリ起動
- 判定のしやすさ
  - `正常`: 単発のファイル操作で閉じる
  - `攻撃`: 直後に不自然なプロセスへ接続する
  - `判定不能`: ファイル操作だけ見えて、対象ファイルや後続アプリが不明
- 実験上の位置づけ
  - `単発操作型`
  - `追跡可能`
  - 自動化寄りの代表ケース

### 4.2 winword.exe

- 見えている正常行動
  - 文書閲覧
  - 文書オープン
- 今回の出現
  - `rank 10`
  - `1 event`
- 追跡しやすさ
  - 高い
- 追える後続の例
  - 直前の `explorer.exe`
  - 周辺の file access
  - 文書オープン後の関連プロセス
- 判定のしやすさ
  - `正常`: 文書閲覧として自然に閉じる
  - `攻撃`: 文書起点の異常な子プロセスや不自然な後続へつながる
  - `判定不能`: `winword.exe` 単独で、対象ファイルや後続が見えない
- 実験上の位置づけ
  - `単発操作型`
  - `追跡可能`
  - 自動化寄りだが、event 数は少ない

### 4.3 repmgr.exe

- 見えている正常行動
  - 文書関連アクセス
  - 文書処理の補助的な流れ
- 今回の出現
  - `rank 6, 9`
  - `5 event`
- 追跡しやすさ
  - 中くらい
- 追える後続の例
  - 周辺の file access
  - 近接する `winword.exe`
  - 同じ文書処理帯のアクセス連鎖
- 判定のしやすさ
  - `正常`: 文書関連アクセス連鎖として閉じる
  - `攻撃`: 後続で攻撃近傍プロセスへつながる
  - `判定不能`: 単独で意味が弱く、文書文脈が見えない
- 実験上の位置づけ
  - `手続型`
  - `半追跡可能`
  - 自動化と人手解釈の境界ケース

## 5. 起点別の仮説

| 起点 | 型 | 追跡可能性 | 自動化しやすさ | 判定不能の出やすさ | 実験での役割 |
| --- | --- | --- | --- | --- | --- |
| `explorer.exe` | 単発操作型 | `高` | `高` | `低` | 自動化可能ケースの代表 |
| `winword.exe` | 単発操作型 | `高` | `高` | `中` | 自動化可能ケースの補助例 |
| `repmgr.exe` | 手続型 | `中` | `中` | `高` | 半自動 / 判定不能が出る代表 |

## 6. 実験としての形

### 6.1 まずやること

- 3起点それぞれについて追跡ルールを固定する
- 各起点から前後の関連ログを引く
- その結果を `正常 / 攻撃 / 判定不能` に分類する

### 6.2 1件ごとの記録項目

- 起点プロセス
- 起点の rank
- 起点 event
- 引けた後続ログ数
- 後続に含まれた主要プロセス
- 最終判定
- 判定理由
- 人手介入の有無

### 6.3 実験結果として出したい表

| 起点 | 件数 | 追跡可能 | 半追跡可能 | 追跡困難 | 正常 | 攻撃 | 判定不能 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `explorer.exe` | `n` | `n` | `n` | `n` | `n` | `n` | `n` |
| `winword.exe` | `n` | `n` | `n` | `n` | `n` | `n` | `n` |
| `repmgr.exe` | `n` | `n` | `n` | `n` | `n` | `n` | `n` |

この形なら、

- 起点によって追跡可能性が違う
- 起点によって `判定不能` の出やすさが違う
- 自動化できるケースとできないケースが分かれる

をそのまま示せる。

## 7. 今回の研究目的に対するおすすめ

- 主結果は `9マス` よりも `追跡可能性` を前面に出す
- `explorer.exe` と `winword.exe` を自動化可能側
- `repmgr.exe` を半自動 / 判定不能側
- `tpautoconnect.exe` は背景ノイズの対照として扱う

この整理にすると、

- ユースケース候補はある程度整理できている
- 自動化できる / できないが明確
- しかもその差が起点の種類で説明できる

ので、実験としてかなりまとまりがよい。
