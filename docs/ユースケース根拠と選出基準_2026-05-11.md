# ユースケース根拠と選出基準

更新日: 2026-05-11

## 1. この文書の目的

この文書は、これまで抽出してきたユースケース候補について、次の 4 点を曖昧にせず明記するためのもの。

1. いつ、どのホスト・どの主体で出たログか
2. ログ上でどのような形で現れたか
3. 異常検知でどの程度「偽陽性候補」として上位化されたか
4. どの基準でユースケース候補として採用したか

重要なのは、**ログから直接言えること** と **そこからの解釈** を分けること。
本研究では、後者を勝手に膨らませず、前者に基づいてユースケース化する。

## 2. 先に結論

- 現時点の process 起点ユースケースは `7` 件
- ただし、粒度は「人間の画面操作そのもの」ではなく、**異常検知で上位化した sequence を起点に、その内部で局所的に現れる正常寄り process をユースケース化したもの**
- よって、`explorer.exe` を見て「ユーザがファイルを開いた」とまで断定するのではなく、
  **`aalsahee` セッション内で高スコア sequence が観察対象となり、その内部の 10 event 窓に `explorer.exe` による file object access 系イベントが 3 件現れた**
  という形で書くのが最も正確

## 3. この文書での用語

- `sequence rank`
  sequence を読む優先度としての順位
- `micro rank`
  sequence 内の局所窓を読む補助順位
- `偽陽性候補`
  attack label が `0` であるにもかかわらず異常検知で上位化した sequence 内の正常寄り窓
- `主体`
  session id の第 2 要素。たとえば `aalsahee` は対話ユーザ、`win-32-h1$` はホスト側サービス文脈

## 4. ログから直接言えることの範囲

今回の集計 CSV / JSON から直接確認できるのは主に次。

- `micro_chunk_id`
  例: `win-32-h1|aalsahee|20220719T1430Z|chunk244|micro08`
- ホスト名
  例: `win-32-h1`
- 主体
  例: `aalsahee`, `win-32-h1$`
- セッション時刻
  例: `20220719T1430Z`
- 出現 process
- Event ID
  主に `4656`, `4663`, `4658`, 一部 `4660`, `4690`
- `ObjectType=file` の有無
- 10 event 窓内での process 件数
- attack / normal の件数
- LOF score と順位

一方で、今回の review 出力には `ObjectName` や完全な操作対象ファイル名が十分残っていない。
したがって、以下は **解釈** として扱う。

- 「どの文書を開いたか」
- 「どの URL にアクセスしたか」
- 「ユーザがクリックしたのか、自動処理なのか」

## 5. ユースケースの採用基準

### 5.1 必須条件

候補をユースケースとして採用するには、次の 5 条件をすべて満たすことを必須にする。

1. **異常検知で上位化していること**
   - 観察対象となる high-score sequence に入っていること
   - 必要に応じて third pass の `micro-chunk` で局所根拠を補強できること
2. **attack label が `0` であること**
   - つまり、その 10 event 窓は attack event を含まない
3. **攻撃主体そのものではないこと**
   - `payload.exe` のような攻撃 process は除外
4. **ユースケースとして説明可能な process であること**
   - `explorer.exe`, `winword.exe`, `firefox.exe`, `repmgr.exe` など
   - `csrss.exe` のような system-side noise は原則除外
5. **同型候補の代表として使えること**
   - 同じ帯域に大量に反復出現する背景 process 群では、代表例を 1-2 件に圧縮する

### 5.2 補助条件

必須ではないが、優先度を上げる条件は次。

- 10 event 窓内で対象 process の出現件数が多い
- first appearance や process transition の位置で現れている
- 単発でも意味が取りやすい
- 追跡可能性の比較に使いやすい

### 5.3 除外基準

次のものはユースケース化しない。

- `payload.exe` のような攻撃 process
- `tpautoconnect.exe` のように、今回の benign 側で大量反復しすぎて比較軸を壊すノイズ
- `csrss.exe` のような system-side process
- 上位に出ていても意味づけが困難で、代表性も低いもの

## 6. 選出ロジック

今回の 7 件は、次の順で選んでいる。

1. 異常検知で高スコアとなった sequence 群を観察対象にする
2. sequence 内で `micro-chunk` を見て、何が異常スコアを押し上げたかを確認する
3. `payload.exe` と `tpautoconnect.exe` を除いた残り process を抽出する
4. `repmgr.exe / explorer.exe / winword.exe` を高スコア帯の core 候補とする
5. browser 帯と background 帯でも、上位 sequence の内部から `firefox.exe / repwmiutils.exe / spoolsv.exe / tpautoconnsvc.exe` を拾う
6. 同型が多い背景 process 群は代表ケースに圧縮する

要するに、**最初から 7 種を決めていたのではなく、異常検知で上がった高スコア sequence の内部から代表 process を残した**
ということが選出ロジックの核心。

### 7.2 `UC01 explorer.exe`

- 根拠データ
  - session: `win-32-h1|aalsahee|20220719T1430Z`
  - micro: `chunk244|micro08`
  - `sequence rank = 6`
  - `micro rank = 7`
  - `score = 9486381958.474821`
  - `attack / normal = 0 / 10`
  - top process: `tpautoconnect.exe:7, explorer.exe:3`
  - top event id: `4656:4, 4658:3, 4663:3`
- ログ上の直接事実
  - `explorer.exe` の出現は 3 件
  - すべて file access 系の Security イベント列の中にある
  - `docs/lof_top10_event_shortlist_2026-05-10/event_shortlist.md` では `chunk244 (rank 6)` の `offset 88-90` が `explorer.exe` の切り替わり地点として拾われている
- 行動解釈
  - 「対話ユーザ `aalsahee` のセッション内で、`explorer.exe` による局所的なファイル参照/操作が起きた窓」
  - ファイル名までは現出力から断定できないため、「単発ファイル操作型」と表現する
- 偽陽性としての強さ
  - top10 core の `micro rank 7`
  - normal-only なのに全体かなり上位
  - したがって、**強い偽陽性候補**

### 7.3 `UC02 winword.exe`

- 根拠データ
  - session: `win-32-h1|aalsahee|20220719T1430Z`
  - micro: `chunk203|micro07`
  - `sequence rank = 4`
  - `micro rank = 10`
  - `score = 7587739671.814433`
  - `attack / normal = 0 / 10`
  - top process: `tpautoconnect.exe:9, winword.exe:1`
- ログ上の直接事実
  - `winword.exe` は 1 件だけ
  - その 10 event 窓はほぼ `tpautoconnect.exe` で埋まっている
  - event shortlist では `chunk203 (rank 4)` の early offset に `winword.exe` の first process appearance がある
- 行動解釈
  - 「対話ユーザ `aalsahee` セッション内の文書閲覧/文書オープンに近い単発イベント」
  - ただし証拠量は少なく、`repmgr.exe` より弱い
- 偽陽性としての強さ
  - top10 core の最下位 `micro rank 10`
  - normal-only で残っているため候補にはするが、**補助的な偽陽性候補**

### 7.4 `UC03 repmgr.exe`

- 根拠データ
  - session: `win-32-h1|aalsahee|20220719T1430Z`
  - micro: `chunk204|micro02`
  - `sequence rank = 5`
  - `micro rank = 6`
  - `score = 9559029010.546871`
  - `attack / normal = 0 / 10`
  - top process: `tpautoconnect.exe:6, repmgr.exe:4`
  - 追加出現: `chunk203|micro05` にも `repmgr.exe:1`
- ログ上の直接事実
  - `repmgr.exe` が同一 10 event 窓に 4 件まとまって出る
  - Event ID は主に `4663`, `4656`, `4658`
  - `ObjectType=file` を伴う file access 系
- 行動解釈
  - 「文書関連オブジェクトに対する手続的アクセス連鎖」
  - 単発よりも、文書操作の流れの一部として読む方が自然
- 偽陽性としての強さ
  - top10 core の `micro rank 6`
  - `rank 6, 9` の 2 箇所にまたがって計 5 event 出る
  - したがって、**最も安定した手続型の偽陽性候補**

### 7.5 `UC04 firefox.exe`

- 根拠データ
  - session: `win-32-h1|aalsahee|20220719T1430Z`
  - micro: `chunk231|micro09`
  - `sequence rank = 44`
  - `micro rank = 52`
  - `score = 3.068800166621051`
  - `attack / normal = 0 / 10`
  - top process: `tpautoconnect.exe:4, vmtoolsd.exe:4, firefox.exe:2`
  - browser 帯 summary では `firefox.exe` の出現 rank は `52, 53, 54, 60`
- ログ上の直接事実
  - browser 帯の上位はほぼ `tpautoconnect.exe` で占有される
  - `firefox.exe` が意味ある形で最初に現れるのが `micro rank 52`
  - この窓では `firefox.exe` は 2 event
- 行動解釈
  - 「対話ユーザ `aalsahee` の browser 系 file access / artifact access」
  - ただし browser 単体ではなく、`vmtoolsd.exe` やノイズと混ざっている
- 偽陽性としての強さ
  - top10 core ほどは強くない
  - しかし browser 帯の中では代表性があり、**中程度の偽陽性候補**
  - 重要な知見は「browser 正常行動はノイズに埋もれやすい」こと

### 7.6 `UC05 repwmiutils.exe`

- 根拠データ
  - session: `win-32-h1|win-32-h1$|20220719T1430Z`
  - micro: `chunk101|micro03`
  - `sequence rank = 99`
  - `micro rank = 7`
  - `score = 7139584418.81725`
  - `attack / normal = 0 / 10`
  - top process: `repwmiutils.exe:10`
- ログ上の直接事実
  - 10 event すべて `repwmiutils.exe`
  - Event ID は `4656`, `4663`, `4658` の反復
  - 主体は対話ユーザではなく `win-32-h1$`
- 行動解釈
  - 「ホスト側サービス文脈での補助的・管理的 file access 反復」
  - 人の単発操作というより、背景寄りの手続処理
- 偽陽性としての強さ
  - second pass では `sequence rank 99` と低い
  - しかし background 帯に絞ると `micro rank 7` まで上がる
  - したがって、**背景帯の中では早く現れる非core 偽陽性候補**

### 7.7 `UC06 spoolsv.exe`

- 根拠データ
  - session: `win-32-h1|win-32-h1$|20220719T1420Z`
  - micro: `chunk003|micro07`
  - `sequence rank = 96`
  - `micro rank = 1`
  - `score = 9218450223.576645`
  - `attack / normal = 0 / 10`
  - top process: `spoolsv.exe:7, sysmon.exe:3`

  - `spoolsv.exe` が 7 件、`sysmon.exe` が 3 件
  - Event ID は主に `4656`, `4663`, `4658`
  - file object access の連続窓
- 行動解釈
  - 「印刷スプーラ/サービス系の背景動作が局所的に密に現れた窓」
  - 対話操作よりも、サービス反復の代表例
- 偽陽性としての強さ
  - background 帯では `micro rank 1`
  - normal-only なのに最上位
  - ただし意味解釈は弱いため、**強いが追跡困難な偽陽性候補**

### 7.8 `UC07 tpautoconnsvc.exe`

- 根拠データ
  - session: `win-32-h1|win-32-h1$|20220719T1420Z`
  - micro: `chunk003|micro02`
  - `sequence rank = 96`
  - `micro rank = 2`
  - `score = 8869773472.323963`
  - `attack / normal = 0 / 10`
  - top process: `tpautoconnsvc.exe:7, csrss.exe:2, -:1`
  - Event ID に `4660`, `4690` を含む
- ログ上の直接事実
  - `tpautoconnsvc.exe` が中心の background service 窓
  - file access 系に加えて handle 系イベントも混ざる
  - 主体は `win-32-h1$`
- 行動解釈
  - 「ホスト側サービスによる背景アクセス反復」
  - `spoolsv.exe` と並ぶ背景動作型
- 偽陽性としての強さ
  - background 帯 `micro rank 2`
  - 非常に上位だが、追跡上の意味づけは難しい
  - したがって、**強いが曖昧な偽陽性候補**

## 8. どの程度「偽陽性として出ているか」の整理

### 8.1 強い偽陽性候補

- `repmgr.exe`
  - top10 core の `micro rank 6`
- `explorer.exe`
  - top10 core の `micro rank 7`
- `spoolsv.exe`
  - background 帯の `micro rank 1`
- `tpautoconnsvc.exe`
  - background 帯の `micro rank 2`

### 8.2 中程度の偽陽性候補

- `winword.exe`
  - top10 core の `micro rank 10`
- `repwmiutils.exe`
  - background 帯の `micro rank 7`
- `firefox.exe`
  - browser 帯の `micro rank 52`
  - ただし browser 候補の中では最初期に意味を持つ

### 8.3 読み方の注意

`micro rank 52` の `firefox.exe` が弱く見えても、これは「全体で弱い」という意味ではない。
browser 帯は上位を `tpautoconnect.exe` が大量占有しているため、**browser 正常行動が上位で見えにくいこと自体が知見** になっている。

## 9. 9マスへの配置基準

今回の 9 マスは、主観で置くのではなく、以下で置く。

### 9.1 横軸: 正常行動タイプ

- `単発操作型`
  - 1 process だけでも意味が取りやすい
  - 例: `explorer.exe`, `winword.exe`, `firefox.exe`
- `手続型`
  - 文脈や連鎖の中で読む方が自然
  - 例: `repmgr.exe`, `repwmiutils.exe`
- `背景動作型`
  - サービスや反復動作が中心
  - 例: `spoolsv.exe`, `tpautoconnsvc.exe`

### 9.2 縦軸: 起点特異性

- `高`
  - top10 core に出てくる
  - 例: `explorer.exe`, `repmgr.exe`, `winword.exe`
- `中`
  - browser 帯または background 帯で代表的に出る
  - 例: `firefox.exe`, `repwmiutils.exe`, `spoolsv.exe`, `tpautoconnsvc.exe`
- `低`
  - 現時点では未採用
  - 理由: 今あるデータでは、研究価値よりノイズが勝つ

## 10. 研究として今後さらに必要なこと

この文書で process 単位のユースケース根拠はかなり明確になったが、次の 3 点はまだ不足している。

1. `ObjectName` を復元して、どのファイル/文書だったかを確定すること
2. 同一 session の前後 sequence / micro-chunk を見て、単発か連鎖かをさらに確定すること
3. `firefox.exe` について file だけでなく browser artifact や domain 側も合わせること

## 11. 発表や本文でそのまま使える短い主張

「本研究のユースケースは、正常ログを恣意的に選んだものではない。異常検知により上位化した高スコア sequence を母集団とし、その内部で局所的に現れる正常寄り process を、攻撃 process と反復ノイズを除外したうえで代表候補として残したものである。各候補については、ホスト・主体・時刻・順位・score・10 event 内の process 構成を根拠として明示できる。」
