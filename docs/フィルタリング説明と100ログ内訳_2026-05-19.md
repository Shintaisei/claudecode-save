# フィルタリングの仕組みと 100 ログの中身

作成日: 2026-05-19

---

## 1. 全体の流れ（5 段階）

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│   生ログ（Security + Sysmon）                                               │
│   数万件 〜 数十万件                                                         │
│         │                                                                   │
│         ▼                                                                   │
│  ┌─────────────────────────────────────────────────┐                       │
│  │  段階1: First Pass                               │                       │
│  │  IsolationForest でセッション単位に異常スコアを付ける│                       │
│  │  閾値（p99）を超えたセッションだけ残す             │                       │
│  │                                                 │                       │
│  │  入力: 全セッション（数百本）                     │                       │
│  │  出力: 陽性セッション（数十本）                   │                       │
│  └─────────────────────────────────────────────────┘                       │
│         │ ↓ 「怪しいセッション」だけ残る                                    │
│         ▼                                                                   │
│  ┌─────────────────────────────────────────────────┐                       │
│  │  段階2: Second Pass                              │                       │
│  │  陽性セッションを 100 event 単位の chunk に細断   │                       │
│  │  テンプレートの希少性でスコアを付けて再ランキング  │                       │
│  │                                                 │                       │
│  │  入力: 陽性セッション × N chunk                  │                       │
│  │  出力: top-10 chunk（= 1,000 event）             │                       │
│  └─────────────────────────────────────────────────┘                       │
│         │ ↓ 「最も珍しい 100 event の塊 10 本」に絞る                       │
│         ▼                                                                   │
│  ┌─────────────────────────────────────────────────┐                       │
│  │  段階3: Review Queue 構築                         │                       │
│  │  Security ログの時刻を 10 分単位に丸めて、         │                       │
│  │  Sysmon ログの分単位 (minute) と突合せる           │                       │
│  │                                                 │                       │
│  │  入力: top-10 chunk の時刻・ホスト情報            │                       │
│  │  出力: 各 chunk に対応する Sysmon minute 候補群   │                       │
│  └─────────────────────────────────────────────────┘                       │
│         │ ↓ Security の「怪しい時間帯」に対応する Sysmon の窓を特定         │
│         ▼                                                                   │
│  ┌─────────────────────────────────────────────────┐                       │
│  │  段階4: Minute の 4 分類                          │ ← ★ここが今回の核心   │
│  │  各 minute に含まれるプロセス名を見て分類         │                       │
│  │                                                 │                       │
│  │  ① attack_near     攻撃プロセスが 1 件でも含まれる│                       │
│  │  ② core_normal     業務プロセスが含まれる        │                       │
│  │  ③ neutral_context それ以外                     │                       │
│  │  ④ background_context 背景プロセスだけ           │                       │
│  └─────────────────────────────────────────────────┘                       │
│         │                                                                   │
│         ▼                                                                   │
│  ┌─────────────────────────────────────────────────┐                       │
│  │  段階5: 100 event へのギャップフィル              │ ← ★今回変えた部分     │
│  │  優先度順に minute を選んで 100 event になるまで  │                       │
│  │  積み上げる                                      │                       │
│  │                                                 │                       │
│  │  旧: core_normal → neutral → background         │                       │
│  │      attack_near は「スキップ」                  │                       │
│  │                                                 │                       │
│  │  新: core_normal → attack_near → neutral → bg   │                       │
│  │      attack_near を 2 番目に優先して「含める」    │                       │
│  └─────────────────────────────────────────────────┘                       │
│         │                                                                   │
│         ▼                                                                   │
│   100 event（各シナリオの最終出力）                                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. 段階4「4分類」の判定ロジック詳細

```
1 つの minute（= 1 分間のイベント群）に含まれるプロセス名を確認する

            プロセス名セットを確認
                   │
         ┌─────────▼─────────┐
         │ suspicious に含まれる？│
         │                   │
         │ payload.exe        │
         │ powershell.exe     │
         │ mshta.exe          │
         │ regsvr32.exe       │
         │ eqnedt32.exe       │
         └─────────┬──────────┘
              YES ↓        NO ↓
         ┌──────────┐  ┌─────────────────────────┐
         │attack_near│  │ preferred_normal に含まれる？│
         └──────────┘  │                         │
                       │ m4: excel, mmc, winword  │
                       │ m6: excel, winword       │
                       │ s4: upd, winword, mmc    │
                       │ s3: explorer, winword    │
                       └────────┬────────────────┘
                           YES ↓       NO ↓
                       ┌──────────┐  ┌──────────────────────┐
                       │core_normal│  │ すべて background か？│
                       └──────────┘  │                      │
                                     │ repwmiutils, conhost │
                                     │ dllhost, schtasks 等 │
                                     └────────┬─────────────┘
                                        YES ↓       NO ↓
                                     ┌──────────┐ ┌──────────────┐
                                     │background│ │neutral_context│
                                     │_context  │ └──────────────┘
                                     └──────────┘
```

**ポイント：** `suspicious` の判定が最優先。1 プロセスでも含んでいれば即 `attack_near` になる。

## 3. 段階5「100 event への積み上げ」

```
分類済み minute を優先度順に並べる
（旧: attack_near は除外 → 新: attack_near を 2 番目に優先）

  ┌────────────────────────────────────────────────────────────┐
  │ 優先度 1: core_normal   ← 業務プロセスを含む分を先に取る    │
  │ 優先度 2: attack_near   ← 攻撃プロセスを含む分を次に取る    │  ← ★変更点
  │ 優先度 3: neutral       ← 判断保留の分で埋める             │
  │ 優先度 4: background    ← 背景処理だけで最後に埋める        │
  └────────────────────────────────────────────────────────────┘

minute を 1 つずつ取り出し、そのイベントを積み上げていく。
100 event に達したら終了。

  0 events
  ──────────────────────────────────────────────────
  │ core_normal minute を追加 (+29)
  29 events
  ──────────────────────────────────────────────────
  │ attack_near minute を追加 (+8)  ← 攻撃＋正常が混在
  37 events
  ──────────────────────────────────────────────────
  │ neutral minute を追加 (+23, +10 ...)
  100 events  ← 完了
```

## 5. なぜこの割合が重要か

```
「100 ログ中の attack 割合が小さい」ことの意味

  ┌──────────────────────────────────────────────────────────────┐
  │                                                              │
  │  異常検知が「怪しい」と判定したセッションの中を見ると、      │
  │  実際には attack 事象はごくわずか（3〜9%）だった。           │
  │                                                              │
  │  残り 91〜97% は正常プロセスによる正常な処理。               │
  │                                                              │
  │  この 91〜97% が「偽陽性候補」= 正常ユースケース候補。       │
  │                                                              │
  │  ただし attack と同じ minute に混在しているものは           │
  │  「攻撃の文脈の中で一緒に検知された正常行動」として           │
  │  より強い偽陽性の説明ができる。                              │
  │                                                              │
  └──────────────────────────────────────────────────────────────┘
```

| シナリオ | attack | normal | FP の質 |
|---|---:|---:|---|
| M4 | 4 (4%) | 96 (96%) | payload 実行時のシェル処理が FP |
| **M6** | **3 (3%)** | **97 (97%)** | **Word 攻撃時の Word 正常処理が FP（最も説明しやすい）** |
| S4 | 9 (9%) | 91 (91%) | スクリプト攻撃時の業務・サービス処理が FP |
| S3 | 5 (5%) | 95 (95%) | payload 実行時のシェル処理が FP（業務主体なし） |
