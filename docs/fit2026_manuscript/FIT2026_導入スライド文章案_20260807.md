作成日: 2026-08-07  
用途: FIT2026発表資料の導入部。研究結果へ入る前に、聞き手が「問題、行動復元、対象領域、ユースケース、検証範囲」を順番に理解できるようにする。  
位置づけ: `FIT2026_資料作成の核_行動復元の成立条件と失敗条件_20260807.md`および`FIT2026_ユースケースの立ち位置と検証範囲_20260807.md`を、発表で話せる文章へ展開したもの。  

## この導入部の設計方針

導入では、いきなりCLOUSEAU、ATT&CK、評価指標を説明しない。聞き手が最初に理解すべきことは、セキュリティアラートが出た後に何を判断する必要があり、なぜ単一ログでは判断できず、どのような情報を行動列として復元する必要があるかである。

その理解を作った後で、侵入初期へ着目する理由、正常行動を含める理由、今回のユースケースが代表する範囲、公的体系との対応を説明する。最後に、本研究が評価する問いへ接続する。

各スライドでは箇条書きを中心にせず、画面には一つの主張と具体例を置く。詳細は発表者が文章として説明し、最後の一文で次のスライドへ論理的に接続する。

## スライド1：そもそも何が問題なのか

### タイトル

> セキュリティアラートだけでは、端末上で何が起きたかを説明できない

### 画面に載せる文章

> EDRのアラートは調査の開始点である。対応を決めるためには、アラートの前後で、どのprocessが何を起動し、何を変更し、どこへ通信したかを明らかにする必要がある。

画面の右側には、次のような短い問いを図として置く。

```text
PowerShellの外部通信を検知
            ↓
誰が起動したのか？
何が実行されたのか？
どこまで行動が続いたのか？
どの端末・通信を止めるべきか？
```

### 発表時に話す文章

SOCでは、EDRなどのセキュリティ製品が疑わしいprocess実行やnetwork通信を検出すると、アラートが発生します。しかし、アラートが発生したことは調査の終了を意味しません。むしろ、そこから調査が始まります。

例えば、PowerShellが外部へ通信したというアラートが発生したとします。この情報だけでは、そのPowerShellをユーザーが起動したのか、Wordやmshtaなどの別processが起動したのかは分かりません。また、PowerShellがその後にcmdやpayloadを起動したのか、外部通信以外にfileやregistryを変更したのかも分かりません。

実際のインシデント対応では、どの端末を隔離するか、どのprocessを停止するか、どの通信先を遮断するか、他の端末にも同じ痕跡がないかを判断する必要があります。そのためには、アラート名を読むだけではなく、アラートの前後で発生した行動をログから調査しなければなりません。

本研究が扱うのは、アラートが攻撃かどうかを単純に分類する問題ではありません。アラートを起点として、その端末上で実際に何が起きたのかを明らかにする問題です。

### 次のスライドへの接続

> それでは、アラートに対応するログを一件見つければ、端末上の行動を説明できるのでしょうか。実際には、単一のログだけでは攻撃と正常行動を区別できないという問題があります。

## スライド2：なぜ単一ログだけでは判断できないのか

### タイトル

> 攻撃と正常行動は、同じ種類のログとして観測される

### 画面に載せる文章

```text
攻撃の例
mshta → PowerShell → cmd → payload → 外部通信

正常の例
explorer → cmd → batch → Python → HTTP server
```

> 目的は異なっていても、どちらもprocess生成、script実行、network通信として記録される。

### 発表時に話す文章

端末ログにPowerShell、cmd、Python、network connectionが記録されていても、それだけで攻撃とは判断できません。これらは攻撃者が利用する一方で、開発者、管理者、正規アプリケーションも日常的に利用するからです。

左側は、今回の攻撃ケースに含まれる行動の例です。mshtaがPowerShellを起動し、PowerShellがcmdを起動し、cmdがpayloadを起動し、最後にpayloadが外部へ通信します。これは攻撃の実行と後続展開を表すchainです。

右側は、今回の正常ケースに含まれる行動の例です。ユーザー操作を起点としてexplorerがcmdを起動し、cmdがbatch fileを実行し、そのbatch fileからPythonのHTTP serverが起動します。これは開発・検証のための正常行動です。

両者の目的は異なります。しかしログを一件ずつ見ると、どちらにもcmdの実行、scriptの実行、子processの生成、network動作が記録されます。したがって、「PowerShellが動いた」「cmdが子processを起動した」「network通信が発生した」という一件のログだけでは、その行動が攻撃なのか正常なのかを十分に説明できません。

MicrosoftのSysmon公式資料でも、各イベントは悪性を直接示すアラートではなく、process実行、network通信、file操作、configuration変更などの観測された行動であると説明されています。意味は、複数のイベントを時系列や因果関係として関連付けたときに生じます。

つまり必要なのは、疑わしいログを一件見つけることではありません。誰が何を起動し、そのprocessが次に何を行い、どこへつながったのかを、一つの行動列として確認することです。

### 次のスライドへの接続

> そこで本研究では、複数のログを関連付け、端末上の行動を証拠付きのchainとして構成する処理を「行動復元」と定義します。

## スライド3：本研究でいう「行動復元」とは何か

### タイトル

> 行動復元とは、複数ログから証拠付きの行動列を構成することである

### 画面に載せる文章

```text
単一ログの説明
「PowerShellが実行された」

             ↓ 行動復元

mshtaがPowerShellを起動した
PowerShellがcmdを起動した
cmdがpayloadを起動した
payloadが外部へ通信した
```

> 各行動を「主体・行為・対象・証拠・順序」で確認する。

### 発表時に話す文章

本研究では、関連しそうなprocess名を列挙することや、アラートの説明文を言い換えることを行動復元とは呼びません。

例えば、「PowerShellが実行された」という出力があっても、それだけではPowerShellの役割や前後関係は分かりません。本研究で復元したいのは、mshtaがPowerShellを起動し、PowerShellがcmdを起動し、cmdがpayloadを起動し、そのpayloadが外部へ通信した、という一連の行動です。

さらに、もっともらしい文章が生成されただけでは、ログ調査の結果として十分ではありません。各行動について、誰が実行したのかを表す主体、何をしたのかを表す行為、何に対して行ったのかを表す対象、その行動を裏付けるログ証拠、そして複数行動の順序が必要です。

例えば「PowerShellがcmdを起動した」という主張に対して、実際のprocess creationログが存在し、正しいPowerShell instanceとcmd instanceが接続されていなければなりません。同名のPowerShellが同じ時間帯に複数存在する場合、別のPowerShellを選択してしまうと、文章としては自然でも対象chainの復元にはなりません。

したがって、本研究が評価するのは、CLOUSEAUが自然な調査報告を書けるかではありません。少数の調査起点から関連ログを探索し、観測された事実を正しい行動列として構成できるかです。

### 次のスライドへの接続

> 行動復元はさまざまな攻撃段階で必要になります。その中で本研究は、攻撃が端末上へ現れ始める侵入初期の行動列に対象を絞りました。

## スライド4：なぜ侵入初期に着目するのか

### タイトル

> 侵入初期は、対応可能性・観測可能性・判断困難性が重なる

### 画面に載せる文章

```text
侵入前                侵入直後                       侵入後
偵察・準備  →  実行・process展開・初期通信  →  横展開・窃取・被害
                         ↑
                    本研究の対象
```

> 対応に必要な情報がログへ現れ始めるが、正常行動との区別にはchainの復元が必要となる。

### 発表時に話す文章

本研究が対象とするのは、攻撃者が組織やシステムについて情報を集める侵入前の偵察ではありません。また、資格情報窃取、横展開、情報窃取、破壊までを含む攻撃全体でもありません。

対象とするのは、攻撃が端末へ到達し、悪性文書の処理、regsvr32やmshtaの実行、PowerShellやcmdへの展開、payloadの起動、初期の外部通信といった具体的な痕跡が端末ログへ現れる区間です。MITRE ATT&CKの用語では、Initial Accessそのものの成立過程よりも、その直後のExecutionから初期Command and Controlに近い範囲を主に扱います。

この区間へ着目する第一の理由は、対応判断に直結する情報を得られるからです。起点となった文書、後続process、payload、通信先を復元できれば、隔離する端末、停止するprocess、遮断する通信、追加で探索する痕跡を具体化できます。NISTは、封じ込めをインシデントの拡大を防ぎ、追加被害を抑える活動と位置づけています。本研究は防御成功率を測るものではありませんが、封じ込め判断に必要な情報を行動復元によって提示できるかを評価します。

第二の理由は、この区間の行動が端末ログに観測可能な形で現れるからです。processの親子関係、command line、file操作、registry変更、network connectionなどは、主体・行為・対象を持つ具体的な行動証拠になります。侵入前の活動よりも、端末上の因果関係をログから構成しやすい領域です。

第三の理由は、観測できるにもかかわらず、正常行動との区別が難しいからです。PowerShell、cmd、Python、Run key、network connectionなどは正常業務でも使用されます。そのため、単一イベントの検出だけでなく、前後の行動を正しいchainとして復元する必要があります。

このように侵入初期は、対応に利用できる情報があり、ログとして観測できる一方、正常行動との区別には行動列の復元が必要になる領域です。この3つが重なることが、本研究で侵入初期に着目する理由です。

### 次のスライドへの接続

> ただし、侵入初期の攻撃行動だけを評価しても、エージェントが本当にログから行動を復元したのか、疑わしいprocessを攻撃らしく説明しただけなのかは分かりません。そこで正常行動も同じ枠組みで評価します。

## スライド5：なぜ正常行動も評価するのか

### タイトル

> 攻撃と似た正常行動を含めることで、行動復元能力を評価する

### 画面に載せる文章

```text
攻撃：mshta → PowerShell → cmd → payload → 通信
正常：explorer → cmd → batch → Python → 通信

同じ観測要素でも、行動の文脈と対象chainは異なる。
```

### 発表時に話す文章

攻撃データだけを対象にした場合、CLOUSEAUがログから正しい行動を復元したのか、それともPowerShellやcmdなどの疑わしいprocessを攻撃らしく説明したのかを区別しにくくなります。

そこで正常側でも、攻撃と似たログ構造を持つ行動を対象にしました。例えば、Python HTTP serverの起動では、explorerからcmdが起動され、batch fileが実行され、その後にPython processとnetwork動作が発生します。packet captureでは、cmdからbatch fileが実行され、tsharkとdumpcapが起動し、最終的にcapture fileが作成されます。

DiscordによるRun key登録も、観測された操作だけを見ると攻撃のPersistenceで使われるregistry変更と似ています。しかし、このケースでは正規アプリケーションの自動起動登録として発生しています。また、Sublime TextからのPython実行では、plugin processからcmdとPythonが起動されます。これも攻撃のscript executionと似た親子process構造を持っています。

正常側で評価したいのは、正常か攻撃かという最終判定だけではありません。対象となる正常行動の開始点、process、script、file、registry、networkを正しく接続し、時間的に近い別行動を対象chainへ混ぜずに復元できるかです。

したがって、今回の正常ケースは一般的な日常行動を無作為に選んだものではありません。攻撃でも利用される観測要素を含み、SOC調査で正しい説明が必要になるdual-useな正常行動を選んでいます。

### 次のスライドへの接続

> ここまでで、攻撃と正常を同じ観測単位で評価する理由を説明しました。次に、今回の16ケースが具体的にどのような範囲を代表するのかを整理します。

## スライド6：今回のユースケースは何を表すのか

### タイトル

> 攻撃8ケースと正常8ケースは、異なる行動構造を比較するために選定した

### 画面に載せる文章

```text
攻撃側
悪性文書／LOLBin
  → PowerShell・cmd
  → payload
  → 初期外部通信

正常側
開発・検証／network診断／アプリ設定／script実行
  → process・script・file・registry・network
```

> 攻撃種類の網羅ではなく、chainの起点・長さ・構成が異なるケースを評価する。

### 発表時に話す文章

今回の攻撃8ケースは、8種類の独立した攻撃ではありません。ATLASv2のS3・S4に含まれる侵入初期の行動列を、異なるfocus processと異なるchain範囲で切り出したものです。

例えば、Wordによる文書処理だけを対象とする短いケースがあります。別のケースでは、Equation Editorからregsvr32が起動し、remote SCTに関連する通信までを追跡します。さらに長いケースでは、regsvr32からPowerShell、cmd、payload、外部通信まで、processとnetworkが混在する8 stepのchainを対象とします。S4では、mshtaを起点としてPowerShell、cmd、payload、外部通信までを含む9 stepのchainも対象としています。

また、同じ大きなchainでも、regsvr32から開始するケース、PowerShellから開始するケース、mshtaから開始するケースがあります。これにより、chainの先頭に近い起点と中間起点、短いchainと長いchainで、復元性能がどう変化するかを確認できます。

正常8ケースでは、Python HTTP server、packet capture、Discordのshell起動とRun key登録、Sublime TextからのPython実行などを対象としています。こちらも正常業務全般を代表するものではありません。攻撃側と同様に、process creation、commandまたはscript execution、file、registry、networkを含む局所的な行動列を選んでいます。

したがって16ケースの目的は、攻撃と正常を幅広く網羅することではありません。攻撃・正常の双方に現れる観測要素について、chainの長さ、起点位置、edgeの種類、同名processの曖昧性が異なるとき、CLOUSEAUがどこまで復元できるかを調べることです。

### 次のスライドへの接続

> これらのケースを研究者独自の名前だけで説明すると、他の攻撃や正常行動との関係が分かりにくくなります。そこで、行動の目的とログ上の観測内容を、公的な体系を用いて分けて整理します。

## スライド7：公開体系をどのように使うのか

### タイトル

> 行動の目的と、ログ上で観測された操作を分けて整理する

### 画面に載せる文章

| 分類するもの | 使用する体系 | 例 |
|---|---|---|
| 行動の目的・文脈 | MITRE ATT&CK | Execution、Command and Control |
| 観測された操作 | ATT&CK Data Components／Sysmon | Process Creation、Script Execution、Network Connection |

> 同じ観測操作でも、攻撃と正常では目的・文脈が異なる。

### 発表時に話す文章

攻撃行動を整理する際には、MITRE ATT&CKのTacticsとTechniquesを用います。これは、攻撃者が何を目的としてその行動を行ったかを表します。例えば、悪性コードを動かす目的はExecution、侵害した端末と通信する目的はCommand and Controlとして整理できます。

一方、ログに記録された操作は、ATT&CK Data ComponentsやMicrosoft Sysmonのevent categoriesを用いて整理します。今回のケースには、Process Creation、Command Execution、Script Execution、File AccessまたはCreation、Windows Registry Modification、Network Connection Creationが含まれます。

ここで重要なのは、目的と観測操作を分けることです。例えばRegistry Modificationという操作は、攻撃者が永続化のために行う場合もあれば、Discordが正規の自動起動登録として行う場合もあります。Network Connectionも、payloadがC2へ接続する場合と、Pythonが正常なHTTP serverとして通信する場合があります。

攻撃側にはATT&CK上の戦術的目的を付与します。正常側には攻撃戦術を無理に割り当てず、開発・検証、network診断、アプリケーション設定、script実行など、実データから確認できる業務文脈を付与します。その上で、攻撃と正常に共通する観測操作を同じ単位で比較します。

この整理により、本研究は「攻撃ケースと正常ケースを別々に試した研究」ではなく、「同じ種類の観測操作が異なる文脈とchain構造で現れたとき、行動復元性能がどう変化するかを評価した研究」として説明できます。

### 次のスライドへの接続

> 公的体系へ対応させることで、今回直接検証した範囲、構造だけが類似する範囲、現在は検証していない範囲を区別できます。

## スライド8：今回どこまで検証したのか

### タイトル

> 本研究が直接検証した範囲と、まだ検証していない範囲

### 画面に載せる文章

| | 直接検証した範囲 | 一部のみ扱った範囲 | 未検証の範囲 |
|---|---|---|---|
| 攻撃 | 侵入直後のprocess・script実行、payload展開、初期外部通信 | 悪性文書を介したInitial Accessの直後 | Reconnaissance、Credential Access、Lateral Movement、Exfiltration、Impactなど |
| 正常 | 開発・検証、network診断、アプリ設定、script実行に伴う局所行動列 | 同じ観測構造を持つ未実験の正常行動 | 一般業務、認証、OS保守、長時間・複数ホストのworkflowなど |

### 発表時に話す文章

攻撃側で直接検証したのは、侵入直後に端末上へ現れるprocessとscriptの実行、payloadへの展開、初期の外部通信です。悪性文書の処理は含まれますが、メールが配送され、ユーザーが文書を開き、脆弱性悪用が成立するまでのInitial Access全体を検証したわけではありません。

また、侵入前のReconnaissance、資格情報を取得するCredential Access、他端末へ移動するLateral Movement、情報を持ち出すExfiltration、暗号化や破壊を行うImpactは対象としていません。複数ホストをまたぐ攻撃や、数時間から数日にわたる長期の攻撃も未検証です。

正常側で直接検証したのは、開発・検証、network診断、アプリケーション設定、script実行に伴う局所的な行動列です。一般的なOffice作業、ブラウザやメール利用、認証、OS update、software installation、backup、複数ホストを含む業務workflowを代表するものではありません。

ただし、未実験の行動であっても、同名processの複数instance、長いprocess chain、processとnetworkが混在するedgeなど、今回と同じ構造を持つ場合には、同様の復元失敗が発生する可能性を議論できます。一方で、今回得られた精度値を未実験の攻撃や正常業務へそのまま一般化することはできません。

したがって、本研究の範囲は、攻撃の全段階や正常業務全般ではなく、攻撃と正常の双方に現れるprocess、script、file、registry、networkから構成される、単一ホスト・局所時間窓内の行動列です。

### 次のスライドへの接続

> この範囲を明示した上で、CLOUSEAUがどの行動を復元でき、どの行動を復元できなかったか、そして成否を分けた構造は何かを分析します。

## スライド9：ここから研究結果へどうつなぐか

### タイトル

> 研究課題：CLOUSEAUは、どの行動を証拠付きで復元できるか

### 画面に載せる文章

> 攻撃と正常では目的が異なっていても、端末ログ上では同じ種類の操作として観測される。本研究では、CLOUSEAUが関連ログを正しいchainとして復元できるかを評価し、復元の成立条件と失敗条件を分析する。

画面下部には評価単位だけを置く。

```text
主体・行為・対象・証拠・順序
```

### 発表時に話す文章

ここまで説明したように、攻撃と正常では行動の目的が異なります。しかし端末ログ上では、process creation、script execution、file、registry、network connectionという同じ種類の操作として観測されます。

そのため、疑わしいイベントを一件検出できたかだけでは、ログ調査能力を十分に評価できません。対象となるprocess instanceを正しく選択し、親子process、script、file、registry、networkを対象chainとして接続し、各行動を証拠と順序を含めて出力できるかを評価する必要があります。

本研究では、CLOUSEAUへhost、focus process、時間範囲などの調査起点を与え、関連ログを探索させました。出力された行動列を、主体、行為、対象、critical evidence、順序に分解し、正常8ケースと攻撃8ケースで評価しました。

最終的に明らかにしたいことは、CLOUSEAUの平均点だけではありません。どのような行動では復元が成立し、どのような行動では部分的な復元に留まり、どのような条件では対象chainを復元できなかったのかです。

以降では、まず全体の復元結果を示します。その後、復元できたケースと復元できなかったケースを比較し、chain長、focus位置、process instanceの曖昧性、edgeの種類、証拠保持、順序が復元結果へどのように関係したかを分析します。

## 導入部を通して聞き手の頭に作る構造

導入終了時点で、聞き手が次の流れを理解できている状態を目指す。

```text
アラートは調査の開始点である
            ↓
単一ログは攻撃・正常の両方に現れる
            ↓
前後のログを証拠付き行動列として復元する必要がある
            ↓
侵入初期は対応可能性・観測可能性・判断困難性が重なる
            ↓
攻撃とdual-use正常行動を同じ観測単位で評価する
            ↓
今回の直接検証範囲と未検証範囲を区別する
            ↓
CLOUSEAUが復元できる行動とできない行動を分析する
```
