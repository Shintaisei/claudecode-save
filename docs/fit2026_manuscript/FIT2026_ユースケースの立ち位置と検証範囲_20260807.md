# FIT2026：ユースケースの立ち位置と検証範囲

作成日: 2026-08-07  
位置づけ: 「復元できた／できなかった」を分析する前提として、攻撃8ケース・正常8ケースが何を代表し、どこまでを検証したかを固定する。  
状態: 構造化の初版。ATT&CK techniqueの厳密な割当、ケース選定根拠、未検証範囲の優先順位は今後精査する。

## 1. なぜユースケースの立ち位置を先に決めるのか

復元の成否は、対象行動の長さ、ログに現れるedge、起点process、同時刻の類似行動、利用できるログ種別によって変化する。そのため、16ケースを同質な標本として単純集計するだけでは、「CLOUSEAUが何を復元でき、何を復元できなかったか」を適切に説明できない。

先に次の3層を区別する。

1. **直接検証した範囲**: 実際に実験したS3/S4攻撃チェーンと正常行動チェーン。
2. **構造的に類似する範囲**: 親子process、script、registry、networkなど、同じ観測グラフを持つ未実験行動。ここでは失敗機序の類似可能性までを議論する。
3. **未検証範囲**: 戦術段階、時間幅、ホスト数、ログ種別、起点条件が現在の実験と異なる行動。性能を一般化しない。

### 1.1 公開体系を使った抽象化方針

攻撃目的と正常業務を同じ粒度で分類する単一の公的体系は採用しない。代わりに、次の3層を組み合わせる。

| 層 | 使用する体系 | 役割 |
|---|---|---|
| 行動の目的・文脈 | 攻撃側はMITRE ATT&CK Tactics/Techniques、正常側は実データから定義する業務文脈 | なぜその行動が行われたかを表す |
| 観測された行動 | MITRE ATT&CK Data ComponentsおよびMicrosoft Sysmon event categories | 攻撃・正常に共通するprocess、command、script、file、registry、networkの操作を表す |
| 復元難度を生む構造 | 本研究で定義するchain長、focus位置、edge混在、instance曖昧性 | CLOUSEAUがなぜ復元できた／できなかったかを分析する |

MITRE ATT&CK Data Componentsには、現在のケースへ直接対応する次の公開分類がある。

- `DC0032 Process Creation`
- `DC0064 Command Execution`
- `DC0029 Script Execution`
- `DC0055 File Access`
- `DC0039 File Creation`
- `DC0082 Network Connection Creation`
- `DC0050 Windows Registry Key Access`
- `DC0056 Windows Registry Key Creation`
- `DC0063 Windows Registry Key Modification`

また、MicrosoftのSysmon公式資料は、process execution、network communication、file modification、configuration changeを低レベルのsystem behaviorとして整理している。同資料ではSysmon eventを、悪性を直接判定するアラートではなく、相関によってsequenceやtimelineを構成する観測証跡と位置づけている。この考え方は、本研究が攻撃・正常を同じ行動要素で評価する根拠と一致する。

したがって、FITでの抽象表現は次を基本とする。

> 攻撃・正常のラベルに先立ち、各ユースケースをProcess Creation、Command/Script Execution、File Access/Creation、Registry Modification、Network Connection Creationからなる観測行動列として表現する。その上で、攻撃側にはATT&CK上の戦術的文脈を、正常側には開発、診断、アプリケーション設定などの業務文脈を付与する。

OCSFもSystem Activity、Network Activity、Application Activityなどのvendor-neutralな公開分類を提供する。ただし、現在の実験はWindows endpointのprocess/file/registry/network edgeが中心であり、FIT本文ではATT&CK Data ComponentsとSysmon分類を主に用いる。OCSFは将来、別製品・別ログ形式へ一般化する際の補助体系とする。

### 1.2 現在のユースケースの抽象的な行動群

公開分類へ合わせると、16ケースはまず次の行動群へ整理できる。

| 抽象行動群 | 攻撃側の例 | 正常側の例 | 共通する観測要素 |
|---|---|---|---|
| 文書・ファイルを入力とするprocess実行 | Word悪性文書処理 | batch、Python scriptの読込み | File Access＋Process/Script Execution |
| 親子processによる実行連鎖 | Equation Editor→regsvr32、mshta→PowerShell→cmd→payload | explorer→cmd→Python、plugin_host→cmd→Python | Process Creation＋Command Execution |
| script／interpreter実行 | PowerShell、regsvr32 remote SCT | batch、Python、Sublime plugin実行 | Command Execution＋Script Execution |
| processに帰属するnetwork動作 | payloadの外部通信、PowerShellの8080/8443通信 | Python listener/connection、packet capture | Network Connection Creation |
| system設定の変更 | 現攻撃8ケースでは中心対象外 | Discord Run key登録 | Windows Registry Key Modification |
| file生成を伴う処理 | 現攻撃8ケースではsupporting中心 | packet capture file生成 | File Creation |

この整理により、攻撃と正常を別々の事例集として扱うのではなく、**同じ観測行動群が異なる文脈とchain構造で現れたとき、復元性能がどう変化するか**を研究課題にできる。

## 2. 攻撃側の位置づけ

### 2.1 用語上の注意

現在の攻撃ログは、主として悪性文書またはLOLBinを起点とする、端末侵入後の初期実行、後続process展開、payload実行、外部通信までを含む。MITRE ATT&CK上の`Reconnaissance`は一般に侵入前の情報収集を指すため、本研究の対象を「偵察」とだけ表現すると誤解を招く。

FITでは、現時点では次の表現を基本とする。

> 脆弱性悪用を含む侵入シナリオにおいて、端末上に最初の具体的な痕跡が現れてから、後続process・payload・外部通信へ展開する侵入初期の行動列。

必要に応じて、`Initial Accessそのものの成否`ではなく、**侵入直後にエンドポイントログで観測できるExecutionから初期Command and Controlまで**を中心に扱う、と補足する。

### 2.2 この段階へ着目する理由

研究上の動機は次のように整理する。

- 悪性文書、LOLBin、PowerShell、payload、外部通信の接続を早期に復元できれば、侵入後の影響拡大前に調査・隔離・通信遮断の判断材料を提示できる。
- SOCでは単一アラートだけでなく、その前後の親子processと通信を結び、どこまで侵入が進んだかを短時間で把握する必要がある。
- 初期行動を復元できるかは、その後の調査範囲、封じ込め対象、追加確認すべきホストや通信先を決めるうえで重要である。

ただし、「ここさえ分かれば大半の攻撃を防げる」という有効率自体は本実験で測っていない。FITでは、**早期封じ込めの判断に寄与し得る重要な調査区間**と表現し、予防率や被害削減率までは主張しない。

### 2.3 攻撃8ケースの実体

8ケースは8種類の独立攻撃ではない。ATLASv2 S3/S4の攻撃関連clusterを、異なるfocus processとchain範囲で切り出したものである。同じ大きな侵入系列の部分chainが一部重複している。

| 構造群 | ケース | 対象範囲 | 主に検証すること |
|---|---|---|---|
| 悪性文書処理 | `s3_pt_01_word_document_processing` | WordによるRTF open、子Word起動 | 文書入力と短いprocess edgeを復元できるか |
| Equation Editor／regsvr32初期展開 | `s3_pt_02_regsvr32_remote_sct` | `svchost → EQNEDT32 → regsvr32 → :8080` | exploit後の子processとremote SCT通信を結べるか |
| regsvr32起点の長系列 | `s3_pt_03_regsvr32_long_chain` | `EQNEDT32 → regsvr32 → PowerShell → cmd → payload → :9999` | processとnetworkが混在する8-step chainを閉じられるか |
| PowerShell中間起点 | `s3_pt_04_powershell_mid_chain` | regsvr32後のPowerShellからpayload/C2まで | chain中間のprocess-time起点から前後を復元できるか |
| Wordから初期通信 | `s4_pt_01_word_w1` | `explorer → Word → 文書 → 子Word → :8080` | user/process起点、文書、通信を一系列にできるか |
| Word部分chain | `s4_pt_02_word_w3` | `Word → 文書 → 子Word → :8080` | 上流を除いた短い文書・通信chainを復元できるか |
| mshta起点の長系列 | `s4_pt_03_mshta_c1` | `svchost → mshta → PowerShell → cmd → payload → C2` | LOLBinから9-stepの後続展開を追跡できるか |
| PowerShell部分chain | `s4_pt_04_powershell_c1` | mshta後のPowerShellからpayload/C2まで | 長系列の中間起点から後続を閉じられるか |

### 2.4 攻撃側で直接検証した構造

- 悪性文書のopenと子process起動
- Equation Editor、regsvr32、mshta、PowerShellなどを介した後続process展開
- LOLBin／script interpreterを含む多段process chain
- process creationと外部network connectionが混在する行動列
- 同じ大きなchainを異なるfocus processから調査する条件
- 2～9 stepの短系列・長系列
- 単一ホスト、約5分の局所時間窓、process/time起点

### 2.5 類似性から議論できる攻撃パターン

実験していない攻撃であっても、次の観測構造を持つ場合、今回特定した失敗要因が類似する可能性を議論できる。

- 正規ツールやLOLBinからscript interpreterやpayloadへ連鎖する攻撃
- 親子processと外部通信を複数回pivotして追う必要がある攻撃
- 同名processが複数あり、正しいinstance選択が必要な攻撃
- 短い直接edgeでは復元できるが、長系列で前半または後半を落としやすい攻撃
- 近傍の正常行動を誤って対象chainへ接続しやすい攻撃

ここから一般化できるのは、主として`instance選択`、`長系列追跡`、`edgeの独立step化`、`証拠保持`、`順序検証`という失敗機序である。未実験攻撃に対する精度値や復元成功率までは一般化しない。

### 2.6 攻撃側の主な未検証範囲

- 侵入前のReconnaissanceおよびResource Development
- public-facing application、valid account、remote serviceなど、悪性文書以外のInitial Access
- Credential Access、Discovery、Privilege Escalation、Persistence、Defense Evasion
- Lateral Movement、Collection、Exfiltration、Impact
- 複数ホストをまたぐ攻撃chain
- 数時間～数日にわたる低頻度・長期滞在型の攻撃
- process/time起点が与えられない調査
- cloud、identity、email、SaaS、network-onlyの証跡を中心とする攻撃
- 暗号化、injection、memory-onlyなど、現在のcanonical process edgeで表現しにくい行動

## 3. 正常側の位置づけ

### 3.1 正常8ケースを選ぶ意味

正常側は、一般的な日常行動を無作為抽出したものではない。process起動、script実行、listener、registry write、packet captureなど、**攻撃でも利用され得る観測要素を含み、アラート起点の調査で誤って悪性chainとして接続され得る正常行動**を対象としている。

したがって、正常ケースの役割は単に「正常ログでも動くか」を見ることではない。

> 攻撃・正常の双方に現れるprocess、script、registry、networkのedgeから、対象となる正常行動の境界を証拠付きで復元し、近傍行動を過剰接続しないかを評価する。

### 3.2 正常8ケースの構造群

| 正常場面 | ケース | 対象範囲 | 主に検証すること |
|---|---|---|---|
| 開発・検証用HTTPサーバ起動 | `chain_02_e01_python_simplehttpserver_network_chain` | `explorer → cmd → batch → Python` | user起点のscript・process chainを復元できるか |
| ネットワーク診断・packet capture | `chain_04_e03_dns_packet_capture_batch_chain` | `cmd → batch → tshark → dumpcap → pcapng` | 7-stepの正常な管理・診断chainを閉じられるか |
| HTTP listener | `chain_05_e03_python_simplehttpserver_network_chain` | `cmd → Python → 0.0.0.0:8000` | process起動とlistenerを結べるか |
| HTTP接続 | `chain_06_e04_python_simplehttpserver_network_chain` | Python listenerへのnetwork connection | 単一network edgeを正しいinstanceへ帰属できるか |
| アプリからshell起動 | `chain_09_e07_cmdexe_other_chain` | `Discord → cmd` | 短いdual-use process edgeを復元できるか |
| アプリの自動起動登録 | `chain_10_e07_discord_run_key_registry_chain` | `Discord → reg.exe → Run key write` | 攻撃のPersistenceと似た正常registry操作を復元できるか |
| エディタからPython実行 | `chain_11_e07_sublime_python_script_execution_chain` | `plugin_host → cmd → Python → hello.py` | 開発行動のscript executionを復元できるか |
| HTTP batch＋listener | `chain_24_e18_cmdexe_other_chain` | `explorer → cmd → batch → Python → :8000` | script起動とlistenerを含む4-step正常chainを復元できるか |

### 3.3 正常側で直接検証した場面

- 開発・検証目的と考えられるPython script／HTTP server実行
- packet captureを伴うネットワーク診断・ログ取得
- Discordのshell起動とRun key登録
- Sublime TextからのPython script実行
- process、batch/script、registry、listener、network connectionを含むdual-use行動
- 単一ホスト、約5分の局所時間窓、process/time起点

正常側は「すべての日常行動」の代表ではなく、**攻撃行動と観測上似るためSOC調査で説明が必要になる正常行動**の事例集合と位置づける。

### 3.4 類似性から議論できる正常パターン

- 管理者や開発者によるshell・script実行
- ローカルのテストサーバやlistener起動
- 診断ツール、packet capture、ログ収集
- 正規アプリケーションの設定変更・自動起動登録
- IDE、editor、pluginからの子process起動
- 正常だが攻撃でも使われるprocess・registry・network motifを持つ行動

これらについても、今回議論できるのは観測構造と失敗機序の類似性であり、未実験製品・業務に対する精度を保証するものではない。

### 3.5 正常側の主な未検証範囲

- ブラウザ閲覧、Office編集、メール送受信などの一般的ユーザー行動全般
- 認証、ログオン、権限変更、ファイル共有
- OS update、software installation、backup、antivirusなどの長い管理行動
- scheduled task、service、WMIなどのbackground activity
- 数時間～数日にまたがる業務workflow
- 複数ユーザー・複数ホスト・サーバ／クライアント間の正常chain
- cloud、SaaS、identity、network applianceを含む正常業務
- 大量の同名processが並行する高負荷環境
- アラートにならず、process/time起点も与えられない正常行動

## 4. 攻撃・正常を共通軸で比較する

最終的な「復元できた／できなかった」分析では、攻撃／正常というラベルだけでなく、次の共通構造を説明変数として整理する。

| 軸 | 値の例 | 見たい関係 |
|---|---|---|
| chain長 | 1、2～4、5～9 step | 長系列ほど後続edgeやOrderを失うか |
| focus位置 | chain先頭、中間、末尾 | 中間起点から前後へ戻れるか |
| edge種別 | process、script、registry、file、network | どのedgeでatomic step化に失敗するか |
| instance曖昧性 | 同名process少／多、近傍cluster少／多 | 誤instance選択と失敗が対応するか |
| dual-use性 | 攻撃固有に近い／正常でも頻出 | 近傍正常行動の過剰接続が増えるか |
| evidence明示性 | 単一canonical row／複数row統合 | critical evidenceを保持できるか |
| 時間的密度 | 対象周辺のイベント少／多 | 時刻近接だけの誤接続が増えるか |
| 出力完全性 | subject・operation・object・evidence・order | 部分取得と完全復元を分ける |

この表により、例えば「攻撃だから難しい」ではなく、`長いprocess/network混在chainだから難しい`、`正常でも7-step packet-capture chainは難しい`、`攻撃でも2-stepの明示的edgeは比較的復元しやすい`という構造的な分析を目指す。

## 5. 一般化の書き分け

FITでは、一般化の強さを次の3段階で書き分ける。

### 直接言える

> 本実験のS3/S4攻撃8ケースおよび正常8ケースでは、〇〇が観測された。

### 構造的類似性から示唆できる

> 同様に、同名processの複数instanceや多段のprocess/network pivotを含む行動でも、同種の復元失敗が生じる可能性がある。

### 現時点で言えない

> 未実験の攻撃戦術や正常業務全般に対して、同じ復元率が得られるとは限らない。

## 6. FIT向けの暫定的なユースケース説明

> 攻撃側では、悪性文書またはLOLBinを起点として、PowerShell、cmd、payload、外部通信へ展開する侵入初期の行動列を対象とした。これらは、端末上に侵入の具体的な痕跡が現れ、早期封じ込めの判断に必要となる区間である。正常側では、Python HTTP server、packet capture、Discord Run key登録、Sublime Textからのscript実行など、攻撃でも用いられ得るprocess・script・registry・network構造を持つ正常行動を対象とした。これにより、攻撃／正常というラベルだけでなく、chain長、起点位置、edge種別、instance曖昧性が行動復元の成否へ与える影響を分析する。

### 6.1 発表スライド向けの簡略版

#### スライド：「なぜ侵入初期に着目するか」

**中心メッセージ**

> 侵入初期は、封じ込め判断に必要な情報が端末ログへ現れ始める一方、正常行動との区別には複数ログの関連付けが必要となる区間である。

**3つの理由**

1. **対応に直結する**  
   文書、起点process、後続process、payload、通信先を復元できれば、隔離・遮断・追加調査の対象を判断できる。
2. **ログで観測できる**  
   Process Creation、Command/Script Execution、File、Registry、Network Connectionとして端末telemetryに現れる。
3. **正常との区別が難しい**  
   PowerShell、cmd、Python、Run key、network connectionは正常業務にも現れ、単一イベントだけでは悪性を判断できない。

**研究上の位置づけ**

> 本研究は防御成功率を測るのではなく、早期封じ込めの判断材料となる行動列を、ログ調査エージェントがどこまで証拠付きで復元できるかを評価する。

#### スライド：「今回どこまで検証したか」

| | 検証済み | 一部のみ | 未検証 |
|---|---|---|---|
| 攻撃 | 侵入直後のprocess/script実行、payload展開、初期外部通信 | 悪性文書を介したInitial Accessの直後 | Reconnaissance、Credential Access、Lateral Movement、Exfiltration、Impactなど |
| 正常 | 開発・検証、network診断、アプリ設定に伴うprocess/script/registry/network行動 | 攻撃と同じ観測構造を持つdual-use行動 | 一般業務、認証、OS保守、長時間・複数ホストworkflowなど |

**一文での範囲説明**

> 攻撃の全段階や正常業務全般ではなく、攻撃・正常の双方に現れるprocess、script、file、registry、networkからなる端末上の局所行動列を検証した。

#### スライド間の接続文

> 同じ観測行動が攻撃と正常の双方に現れるため、単一ログの検出ではなく、関連する行動を正しいchainとして復元できるかが重要となる。そこで、主体・行為・対象・証拠・順序を用いてCLOUSEAUの復元結果を評価した。

## 7. 次に確定する項目

1. 攻撃8ケースについて、侵入段階とATT&CK techniqueを過不足なく割り当てる。
2. 正常8ケースについて、実データ上の業務場面と正常である根拠を確認する。
3. 16ケースへchain長、focus位置、edge構成、instance曖昧性、時間密度の属性を付与する。
4. 属性表へ3反復のAction、Precision、完全step、Critical、Orderを結合する。
5. 定量値とrun定性分析を用いて、成功・部分成功・失敗分類を確定する。
6. 未実験だが構造的に類似する例と、完全に範囲外の例を攻撃・正常それぞれ図示する。
