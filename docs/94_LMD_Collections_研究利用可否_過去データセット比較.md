# LMD Collections 研究利用可否メモ

作成日: 2026-04-17

## 結論

LMD Collectionsは「使える」。ただし、主役にする研究テーマを間違えると、あとで使えない。

安全な位置づけは次の通り。

| 使い方 | 判定 | 理由 |
|---|---|---|
| Sysmon CSVを使ったラテラルムーブメント分類 | 使える | ラベル付きCSV、Normal/EoRS/EoHT、十分な件数がある |
| ラテラルムーブメント検知モデルの比較実験 | 使える | 2.3M版で3クラス分類ができる |
| 正常/攻撃のEventID・プロセス・通信傾向分析 | 使える | 生CSVに `Image`, `CommandLine`, `DestinationIp`, `QueryName` などがある |
| HayabusaにEVTXを直接かける研究 | そのままでは厳しい | 今回取得できた中身はCSV中心で、EVTX本体は確認できていない |
| 複数ログを横断した行動復元 | 厳しい | Sysmon中心で、Security/System/TaskSchedulerなどとの横断ができない |
| 「人間の正常業務行動」を豊かに扱う研究 | やや弱い | Normalはあるが、NetBIOS/ネットワークイベント偏重、ホスト偏りが強い |
| 実運用に近い誤検知分析 | 補助なら使える | 攻撃期間ラベルであり、現実のSOCアラート起点とは少し違う |

したがって、今の研究全体での扱いは、

> apt-persistenceを主データ、LMDを補助・比較・Sysmon特化検証データにする

のが一番安全。

LMDだけを主役にするなら、研究テーマを「Sysmonログによるラテラルムーブメント分類」へ寄せる必要がある。

## これまで頓挫してきた観点での整理

### 1. ATLAS系で詰まった点

ATLAS系は、攻撃手順や検知知識は豊富でも、研究でそのまま使えるWindows EVTX/Sysmonログとして扱いにくかった。Hayabusaに直接かける、プロセスツリーを復元する、正常行動と比較する、という用途に乗せづらかった。

LMDはこの点ではATLASより良い。

- CSVとして実データがある
- Sysmon由来のイベント項目がある
- `Image`, `CommandLine`, `ParentImage`, `DestinationIp`, `QueryName` などがある
- Normalと攻撃ラベルがある

ただし、LMDもEVTX本体ではない。Hayabusa実験の主データにはしづらい。

### 2. CERT Insider Threatで詰まった点

CERTは正常業務行動の文脈は強いが、Windowsイベントログではない。`logon`, `http`, `device` などの抽象CSVであり、Sysmonのプロセス・コマンドライン・レジストリ・ファイル作成を追えない。

LMDはこの点ではCERTより良い。

- Sysmonイベント単位で分析できる
- プロセス名・コマンドライン・親プロセスがある
- ネットワーク、DNS、レジストリ、ファイル作成が同じCSVにある

ただし、CERTのような「ユーザ業務の生活感」はLMDでは弱い。LMDのNormalは多くがネットワーク接続、Windowsサービス、ドメイン系通信であり、人間の業務行動分類には向きにくい。

### 3. apt-persistenceで見えてきた強みと課題

apt-persistenceはEVTX形式で、Security/Sysmon/TaskScheduler/Application/Systemを持つ。Hayabusaや横断ログ分析には一番合う。

一方で、正常行動がGHOSTS由来で、実運用の自然な正常行動かどうかは慎重に見ないといけない。また、Wazuhアラートの誤検知を起点にする場合、どのアラートを選ぶかで研究が重くなる。

LMDはapt-persistenceと比べると、次のように位置づく。

| 観点 | apt-persistence | LMD |
|---|---|---|
| ファイル形式 | EVTX中心 | CSV中心 |
| Hayabusa適性 | 高い | 低い |
| 複数ログ横断 | できる | ほぼSysmonのみ |
| ラベル | 攻撃マシン/正常マシン、GT.yml | 行単位でNormal/EoRS/EoHT |
| ML実験のしやすさ | 前処理が必要 | すぐできる |
| 正常行動の量 | 多い | 多い |
| 正常行動の自然さ | GHOSTS由来で要注意 | 一部日常アプリあり、ただしNetBIOS偏重 |
| 攻撃対象 | Persistence中心 | Lateral Movement中心 |
| 研究での安全な役割 | 主データ向き | 補助・比較向き |

## LMDの強み

### 1. ラベル付きで大規模

LMD-2023 2.3M版には、ラベル付きCSVで約214万行ある。

| ラベル | 意味 | 行数 |
|---:|---|---:|
| 0 | Normal | 1,632,903 |
| 1 | EoRS | 375,239 |
| 2 | EoHT | 135,866 |
| 合計 |  | 2,144,008 |

これは分類実験にはかなり使いやすい。

### 2. Sysmon由来なので、行動単位で読める

EventID 1, 3, 10, 11, 13, 22などが含まれるため、以下のような行動分析ができる。

- プロセス作成
- ネットワーク接続
- ProcessAccess
- ファイル作成
- レジストリ変更
- DNSクエリ

ATLASやCERTより、Windows上の実体ある挙動に近い。

### 3. ラテラルムーブメントにテーマが合う

EoRSとEoHTがあり、リモートサービス悪用と認証情報悪用を分けられる。

研究テーマを「端末ログからラテラルムーブメントを見つける」に寄せるなら、テーマ適合度は高い。

### 4. Normalが十分ある

Normalが160万行以上あり、正常側の比較対象としては量がある。

含まれる正常行動の例:

- Opera / Edge
- Teams / Slack / Viber
- VS Code / Python
- Windows Defender
- OneDrive
- DNS / LDAP / SMB / Kerberos
- Windows Update
- NetBIOS系通信

## LMDの危ない点

### 1. EVTXではない

今手元にあるLMDはCSV中心。READMEではEVTX/XMLにも触れているが、今回Google Driveから取得したRARの中ではCSVが中心で、EVTXを確認できていない。

これは大きい。

Hayabusaを使う研究、EVTXからアラートを出して起点にする研究、Sigmaルールを直接適用する研究には、そのままでは向かない。

### 2. ホスト名リークが強い

Normalは `LAPTOP-ROPR18AK` にかなり偏り、攻撃は `win-dc-*`, `win-host-*` などAttackRange系ホストに偏っている。

そのため、`Computer` を入れて学習すると、モデルが攻撃挙動ではなく環境差を覚える危険がある。

これは「あとで使えません」になりやすいポイント。

### 3. 時刻リークが強い

攻撃が特定の日付に集中している。

たとえばLMD-2023 2.3M版では、2022-10と2023-11はNormalのみ、2023-12に攻撃が多い。

前処理済みCSVには `SystemTime_year`, `month`, `week`, `day_of_week` が入っている。これをそのまま使うと、時刻で分類できてしまう。

### 4. EventID分布で分類できてしまう

NormalはEventID 3が非常に多い。

| EventID | Normal件数 |
|---:|---:|
| 3 | 1,399,345 |
| 5 | 174,734 |
| 1 | 19,544 |
| 13 | 17,751 |
| 22 | 9,929 |

攻撃側はEoRS/EoHTでEventID 10や7や23が目立つ。分類モデルが「ラテラルムーブメントらしい行動」ではなく、EventIDの偏りだけを見てしまう可能性がある。

### 5. 攻撃ラベルは「攻撃コマンドそのもの」ではなく「攻撃期間ログ」に近い

攻撃ラベルの中にも、Splunk Universal Forwarder、Windowsサービス、DNS、通常プロセスが多く含まれる。

つまり、LMDのラベルは「この1行が攻撃手順そのもの」というより、「攻撃実行期間・攻撃カテゴリに属するログ」と見る方が安全。

## 研究目的との相性

今までの流れを見ると、研究の中心はおそらく次の方向。

> 検知アラートを起点に、周辺ログから正常行動/攻撃行動を復元し、誤検知や判断根拠を説明できるようにする

この目的に対して、LMD単体は少しずれる。

理由:

- Hayabusaの起点アラートを作れない
- Security/TaskScheduler/Systemなどの横断ログがない
- 攻撃ラベルはあるが、SOCアラート起点ではない
- Normalはあるが、ホスト・時刻・EventIDに偏りがある

一方で、次の用途にはかなり合う。

> Sysmonログ上で、Normal / EoRS / EoHT の違いを定量的に見せる

または、

> apt-persistenceで作った分析観点が、LMDのラテラルムーブメント系ログにも通用するかを補助検証する

## 使うならこう使う

### 主研究データにはしない

主データはapt-persistenceの方が安全。

理由:

- EVTXがある
- Hayabusaに直接かけられる
- 複数ログを横断できる
- 起点アラートから周辺ログを復元する研究に合う

### LMDは補助実験にする

LMDの役割は次がよい。

1. Sysmon単体での比較実験
2. ラテラルムーブメント分類のベースライン
3. EventID/プロセス/通信の攻撃カテゴリ差の分析
4. apt-persistenceで作った説明軸の外部データ検証

### LMDでやるなら安全な実験設計

最低限、以下を比較する。

| 実験 | 目的 |
|---|---|
| 全特徴量あり | 素の性能を見る |
| `Computer` 除外 | ホスト名リークを潰す |
| 時刻特徴除外 | 時刻リークを潰す |
| `Computer` + 時刻特徴除外 | より現実的な性能を見る |
| EventID分布をそろえる | EventIDだけで分類していないか確認 |
| 日付holdout | 未来日・別期間に通用するか確認 |
| ホストholdout | 未知ホストに通用するか確認 |

この比較をしないと、あとで「高精度だけどリークでした」となる危険がある。

## Go / No-Go 判定

### Go

以下の研究テーマなら使ってよい。

- Sysmonログによるラテラルムーブメント検知
- Normal / EoRS / EoHT の3クラス分類
- EventID・プロセス・通信先の違いによる攻撃カテゴリ分析
- 不均衡データでの分類評価
- apt-persistenceの補助比較データ

### Conditional Go

以下は条件付きで使える。

- 正常行動分析
  - ただし、Normalの大半がEventID 3とNetBIOS系通信であることを明記する
- 行動復元
  - ただし、Sysmon CSV内での簡易復元に限る
- 誤検知分析
  - ただし、Hayabusa/SOCアラート起点ではなく、ラベル付きログ比較として扱う

### No-Go

以下には主データとして使わない方がよい。

- HayabusaにEVTXをかける研究
- 複数Windowsログを横断して判断する研究
- SOCアラート起点の誤検知復元
- 人間の通常業務行動を細かく分類する研究
- 実運用に近いエンドポイント監視データとしての評価

## 「あとで使えません」を避けるための確認リスト

LMDを研究に入れる前に、以下を先に確認する。

- [ ] 研究内でLMDを「主データ」にするのか「補助データ」にするのか決める
- [ ] LMDではHayabusa/EVTX実験をしないと明記する
- [ ] `Computer` を抜いた分類性能を出す
- [ ] 時刻特徴を抜いた分類性能を出す
- [ ] EventID分布だけで分類できていないか確認する
- [ ] ランダム分割以外に、日付分割かホスト分割を試す
- [ ] Normalの偏り、攻撃期間ラベル、ライセンス未明記を限界として書く
- [ ] LMD-2022は主実験に使わず、LMD-2023 2.3Mを使う

## 最終判断

LMDは捨てなくてよい。むしろ、Sysmon CSVの大規模ラベル付きデータとしてはかなり有用。

ただし、今の研究の中心が「Hayabusaの起点アラートから正常行動を復元する」なら、LMDは主役ではない。主役にすると、EVTXがない・横断ログがない・アラート起点ではない、という理由で後から苦しくなる。

一番安全な使い方はこれ。

> apt-persistenceを主データにして、LMDは「Sysmon単体・ラテラルムーブメント分類の補助検証」として使う。

この位置づけなら、LMDは十分使える。あとで「使えません」になる可能性もかなり下げられる。
