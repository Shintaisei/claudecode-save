# ATLAS v2 S3 スライド作成用統合整理

更新日: 2026-05-04

## 1. この研究でやりたいこと

今回の主目的は、ATLAS v2 の attack day ログ全体から、

1. まず investigation の起点になる異常シーケンスを少数まで絞る
2. その異常近傍に含まれる正常行動ログをできるだけ残す
3. 偽陽性も含めて、なぜ怪しく見えたかを説明できる形にする
4. 最終的に、false positive 研究や normal behavior extraction に使える seed を得る

ことである。

重要なのは、今回の目的が単なる「異常検知精度の最大化」ではない点である。  
本当に欲しいのは、attack day 全体をそのまま読む代わりに、

- 少数の異常起点
- その周辺の正常文脈
- 偽陽性との比較対象

を、研究に使える粒度で残すことである。

したがって評価軸は次の 2 本立てで考える。

- detector として、どこまで attack を含む範囲を落とさずに絞れるか
- その結果として、研究に使える正常文脈がどれだけ残るか

## 2. 対象データと前提

今回の主対象は `ATLAS v2 S3` である。  
ログ源としては主に `Security` を使い、後半で `Sysmon` を補助的に加えた。

前提は次の通りである。

- 学習は `benign-only`
- attack を学習には入れない
- 評価ラベルは `Security` 側の ground truth を使う
- Sysmon には直接ラベルがないため、Sysmon 単独評価でも最終評価は Security ラベル基準で見る

## 3. どういう粒度でシーケンス化したか

試した session 粒度は大きく 3 種類である。

### 3.1 `computer_process + 10分`

1 本の session がかなり長く、候補発見用としては使えるが、そのまま読むには大きすぎる。

### 3.2 `computer_process + 1分`

10 分よりは小さくなるが、まだ巨大 session が残る。

### 3.3 `computer_process + 1分 + 100 event chunk`

読解単位としてはかなり扱いやすいが、初段 detector としては細かすぎて偽陽性が膨らみやすかった。

### 3.4 最終的に本線にした粒度

最終的に一番良かった coarse detector 側の粒度は

- `computer_user + 10分`

である。

これは「どの user 文脈で異常近傍を拾うか」を見るにはかなり相性が良かった。

## 4. まず試したモデル群

最初は、できるだけ有名どころの sequence model で benign-only anomaly detection を行う方針で進めた。

### 4.1 Forecasting 系

- `LSTM`
- `Transformer`
- `next_log prediction`

### 4.2 Reconstruction 系

- `LSTM AutoEncoder`

### 4.3 One-class 系

- `IsolationForest`

### 4.4 後から足した補助系

- `Security second pass hybrid reranking`
- `Sysmon minute-level IsolationForest`

## 5. Forecasting 系が厳しかった理由

`next_log` 系は、最終的には今回の目的にあまり合わなかった。

代表的な結果は次である。

- `LSTM + computer_process + 1分 + 100 event chunk`
  - `F1=0.0258`
  - `Recall=1.0`
  - `Precision=0.0130`
- `LSTM + computer_process + 10分`
  - `F1=0.1404`
  - `Recall=1.0`
  - `Precision=0.0755`
- `LSTM + computer_user + 10分`
  - `F1=0.2857`
  - `Recall=1.0`
  - `Precision=0.1667`

この結果は、単に閾値設計の問題だけではなかった。  
実際には、

- benign-only forecasting が今回の sequence に十分 generalize していない
- `1回でも外したら session 陽性` 的な集約が細粒度 session と相性が悪い
- 読みたい「正常近傍文脈」よりも、全体を過敏に陽性化してしまう

という問題があった。

したがって、forecasting 系を本線に置くのはやめた。

## 6. AutoEncoder 系の位置づけ

LSTM AutoEncoder は oracle で見ると一定の情報を持っていたが、benign percentile 由来の threshold で切ると実運用寄り評価で崩れた。

つまり、

- score 自体は悪くない
- ただし threshold 校正が弱い
- 今すぐ主軸にするには不安定

という判断になった。

## 7. なぜ IsolationForest が本線になったか

最終的に一番安定した coarse detector は、

- `IsolationForest`
- `Security`
- `computer_user + 10分`
- `1-2 gram TF-IDF`
- benign-only 学習

の構成だった。

この方式が良かった理由は次である。

- benign-only で自然に one-class anomaly detection を組める
- template 列を session 文書として扱える
- coarse sequence を「まず数本に絞る」目的に合っていた
- forecasting 系より過敏に壊れにくかった

## 8. First Pass の最終結果

最終的な coarse detector のベストは次である。

- `IsolationForest + Security(computer_user + 10分) + 1-2 gram TF-IDF`
- `F1=0.667`
- `Precision=0.667`
- `Recall=0.667`

参照:
- [iforest_s3_cu10_g1_2_c010_stable/results.json](/c:/Users/komat/OneDrive/Desktop/ATLAS以外のデータセット/analysis_data/model_runs/iforest_s3_cu10_g1_2_c010_stable/results.json:1)

S3 の test では、

- test sequence 総数: `18`
- 予測陽性 sequence: `3`
- 真陽性 sequence: `2`
- 偽陽性 sequence: `1`

となった。

ここで重要なのは、coarse detector が「完璧な分類器」ではなくても、

- 読むべき sequence を 18 本から 3 本へ落とせた
- その 3 本の中に本命 attack を 2 本残せた

という点である。

## 9. First Pass 陽性 sequence の中身

First pass で陽性になった 3 sequence の合計は次である。

- total events: `118,495`
- attack events: `286`
- normal events: `118,209`

真陽性 2 本だけを見ると、

- total events: `94,815`
- attack events: `286`
- normal events: `94,529`

である。

これは、「怪しい sequence を起点に見ても、中身の大半は正常ログである」ことを意味する。  
今回の研究目的からすると、これはむしろ好ましい。

## 10. 偽陽性 sequence の意味

偽陽性 sequence は 1 本で、

- `win-32-h1|win-32-h1$|20220719T1420Z`
- total events: `23,680`
- attack events: `0`
- normal events: `23,680`

であった。

この sequence は現時点では誤検知だが、

- 偽陽性がどういう正常行動から生じるか
- 真陽性の近傍正常文脈と何が違うか

を見る比較対象として重要である。

## 11. なぜ second pass が必要だったか

First pass の時点で `3 sequence` までは落ちたが、それでも

- `118,495 event`

あるため、人がそのまま読むにはまだ重い。

したがって次に必要だったのは、

- first pass の中をさらに細かく切る
- 本当に読むべき帯だけを上位へ出す

second pass であった。

## 12. Second Pass の設計

Second pass は `100 event chunk` を基本単位にした。

スコアは単一モデルではなく、hybrid にした。

使った要素は次である。

- `KNN benign distance`
- `rare process onset`
- `delta onset`
- 補助的な base fallback

考え方としては、

- benign では見慣れない chunk
- 特定 process が急に立ち上がる帯
- 急激に異常度が増す帯

をまとめて「読む価値が高い chunk」とみなす。

## 13. Second Pass の結果

Second pass の `review_windows top10` は次である。

- `10 window`
- `5,400 event`
- attack events: `195`
- normal events: `5,205`

参照:
- [second_pass_s3_cu10_hybrid/results.json](/c:/Users/komat/OneDrive/Desktop/ATLAS以外のデータセット/analysis_data/model_runs/second_pass_s3_cu10_hybrid/results.json:1)

これは first pass の `118,495 event` に対して、

- `118,495 -> 5,400`
- 約 `95.4%` 削減

である。

つまり、attack day の巨大ログから

- まず 3 sequence
- さらに 10 window

まで縮めることができた。

## 14. Second Pass で見えた主要帯

Second pass で特に強かった帯は次である。

- `payload.exe`, `chunk 331-340`, `1000 event`, `attack 34`, `normal 966`
- `payload.exe`, `chunk 323-329`, `700 event`, `attack 155`, `normal 545`

一方で、`werfault.exe` や `wmiapsrv.exe` のような帯も上がっており、ここは偽陽性帯として読む必要がある。

## 15. なぜ Sysmon を足したか

Security だけでも coarse detector と second pass は作れたが、

- minute 単位の補助起点
- 小さい局所帯の裏取り
- process image ベースの説明力

を増やすために Sysmon を足した。

ここで重要だったのは、最初に使っていた `sysmon.exe` を含む Security session は「本物の Sysmon ログではない」と確認した点である。  
その後、実 Sysmon XML を別経路から読み込んで実験した。

## 16. Sysmon minute detector の結果

実 Sysmon XML による benign-only minute detector では、

- `F1=0.5217`
- `Precision=0.375`
- `Recall=0.857`

が出た。

さらに minute seed として特に重要だったのは、

- `20220719T1433Z`
- `20220719T1436Z`
- `20220719T1437Z`

である。

特に `1437Z` では top image に `payload.exe` が見えており、Security 側の `payload.exe` 帯ときれいに整合した。

参照:
- [sysmon_s3_minute_iforest/results.json](/c:/Users/komat/OneDrive/Desktop/ATLAS以外のデータセット/analysis_data/model_runs/sysmon_s3_minute_iforest/results.json:1)

## 17. Security と Sysmon の関係

ここで分かったのは、

- `Security` は coarse detector と chunk reranking に強い
- `Sysmon` は minute-level の補助起点に強い
- しかし両者を単純に 1 本の fused score にすると改善しない

ということである。

実際に単純融合は `F1=0.25` 程度で、Security-only より良くならなかった。

したがって最終方針は、

- `Security first pass`
- `Security second pass`
- `Sysmon は補助的 rerank / 裏取り`

とした。

## 18. Review Queue の作成

モデルを増やすより、実務的に使える出力にするため、

- first pass で陽性になった sequence

- Sysmon minute seed

を 1 つの review queue に束ねた。

参照:

1. `win-32-h1|aalsahee|20220719T1430Z`
2. `win-32-h1|win-32-h1$|20220719T1430Z`

## 20. 実務的にどこまで絞れたか

この結果を seed 数で見直すと、

- coarse 異常 sequence: `3本`
- second pass review windows: `10個`
- high-confidence 異常 seed: `6個`

である。

したがって、実務的な初動 triage としては、

- 最初に見る異常起点を 5-10 個前後まで減らす

という感覚にかなり近い。

dominant process ごとに集計すると次である。

- `powershell.exe`

- `powershell.exe` と `regsvr32.exe` は attack-near normal context としてかなり強い帯

## 24. 正常イベントの内容

残っている正常イベントで多い EventID は主に次である。

- `4656`
- `4658`
- `4663`

つまり、今回残っている正常文脈は、

- 通常の file access
- その前後の process activity
- 複数 process が混じる周辺文脈

を含んでいる。

例えば、

- `payload.exe` 帯では `csrss.exe`
- `powershell.exe` 帯では `csrss.exe`, `vmtoolsd.exe`
- `regsvr32.exe` 帯では `repmgr.exe`, `eqnedt32.exe`, `taskhost.exe`

のような周辺 process も観測されている。

## 25. ここまでで言える主張

少なくとも S3 に関しては、次まではかなり強く言える。

1. benign-only anomaly detection でも、attack day 全体から suspicious sequence を数本まで絞れる
2. coarse detector だけでは大きすぎるが、second pass により数千 event 規模まで落とせる
3. Security だけでなく Sysmon minute seed を補助的に使うことで、攻撃帯の説明力が増す
4. high-confidence seed の中には、大量の正常イベントが残っている
5. 特に `powershell.exe` と `regsvr32.exe` 帯は、研究用 normal behavior seed としてかなり使いやすい

## 26. 今回の成果を一言でいうと

今回の成果は、

「ATLAS v2 S3 の attack day を、18 sequence から 3 sequence、さらに 10 window、最終的には 6 本の高信頼 seed まで絞り込み、その中に attack-near normal context を 2,000 event 以上残せた」

ことである。

## 27. 限界と注意点

一方で、次ははっきり限界として書くべきである。

### 27.1 シナリオ限定

現時点の詳しい分析は S3 に集中している。  
S4/M4/M5/M6 への横展開は次段階である。

### 27.2 小さい真陽性 sequence の局所化が弱い

`win-32-h1|win-32-h1$|20220719T1430Z` のような小さい真陽性側では、second pass の局所化がまだ弱い。

### 27.3 pure benign ではない

ここで残した正常行動は `pure benign` ではなく、

- attack-near normal context

である。  
ただし今回の研究目的には、むしろこちらの方が重要である。

### 27.4 Security と Sysmon の単純融合は未完成

融合 scoring 一本化はまだうまくいっていない。  
現時点では、Security 主軸 + Sysmon 補助の方が妥当である。

### 28.1 coarse detector

- model: `IsolationForest`
- unit: `Security / computer_user + 10分`
- score: `F1=0.667, P=0.667, R=0.667`
- `18 sequence -> 3 sequence`

### 28.2 second pass

- `118,495 event -> 5,400 event`
- 約 `95.4%` 削減
- attack events retained: `195`

### 28.3 high-confidence seed

- `5,400 event -> 3,000 event`

### 28.4 normal behavior retention

- high-confidence 全体: `normal 2,805 / 3,000`

- normal-dominant subset: `2,260 / 2,300`
- normal ratio: `98.3%`

## 29. スライドでの見せ方候補

### 29.1 ストーリー型

1. 課題: attack day が巨大すぎて読めない
2. 方針: benign-only detector でまず絞る
3. coarse detector: 18 -> 3 sequence
4. second pass: 118,495 -> 5,400 events
5. high-confidence seed: 6 windows / 3,000 events
6. 正常行動が 2,805 events 残る
7. 研究に使える attack-near normal context を確保できた

### 29.2 比較型

- LSTM/Transformer は精度は低め
- AE は threshold 校正が難しい
- IsolationForest が coarse detector として最も安定
- Security + Sysmon は役割分担で使うのが最も良い

### 29.3 研究価値強調型

- 異常そのものを見つけるだけでなく
- 異常近傍の正常文脈を大量に残している
- そのため false positive 研究や normal behavior extraction に向く

## 30. 最終的な現在方針

現時点での本線は次である。

1. `Security first pass`
   `IsolationForest + computer_user + 10分`
2. `Security second pass`
   `100 event chunk` の hybrid reranking
3. `Sysmon補助`
   minute-level seed の裏取り
4. `high-confidence seed`
   `payload / powershell / regsvr32` を核に読む
5. `normal behavior analysis`
   normal-dominant seed から研究対象を掘る

この方針により、

- 実務寄りの初動 triage
- 研究向けの正常文脈抽出

の両方をある程度両立できている。
