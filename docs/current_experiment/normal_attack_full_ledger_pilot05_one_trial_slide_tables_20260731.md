# pilot05 研究発表用集計 — すべて1試行平均

## 集計単位

- **1試行 = 1モデル × 1ユースケース × 1 Stage**
- 全12試行：4ユースケース × Stage 1–3
- `gpt-4.1-mini` 6試行、`gpt-5.4-mini` 6試行
- InputにはCached inputを含む。Total tokensはInput + Outputであり、Cachedを二重加算しない。
- 精度は各集合のmicro-average。`平均hits / 平均denominator`は、合計値を試行数で割った表示であり、割合そのものはmicro-averageと同じ。
- モデルごとに担当ユースケースが異なるため、モデル間の数値はケース難易度を統制した直接比較ではない。

## Slide 9 — 取れていない主因

| 原因 | 観測結果 | 解釈 |
|---|---:|---|
| Causal edge欠落 | **11/12試行** | ログ行は取得しても、親子・後続・networkなどを因果edgeとして接続できていない |
| 近傍行動の過剰接続 | **8/12試行** | 時間的に近い別process/file/moduleを主要chainへ混入 |
| 未裏付け・幻覚タグ | **8/12試行** | 原証拠でatomic actionを裏付けられない候補を出力 |
| 明確な早期停止 | **1/12試行** | 全体低精度を単純な論点数・回数制限だけでは説明できない |
| Critical evidence未取得 | **48/48 step** | action候補とcanonical evidence rowの結合ができていない |

### 具体例

- `mshta C1 / gpt-4.1-mini / Stage 3`は**450 API calls、2,189,034 tokens、$0.701798、22.69分**を使ったが、Action recallは**3/27 = 11.11%**だった。
- したがって、主問題は「調査回数が少ない」ことではない。未解決edgeに沿ったpivot、正しいprocess instanceの維持、atomic action化、Gold外candidateの抑制に問題がある。
- `Python HTTP / Stage 2–3`では、対象時刻より38秒前の別DNS chainを選択し、その誤ったinstanceを追加探索で精緻化した。
- `Word document`ではcore 2-stepは比較的安定したが、文書openの誤型付けとGold外file/module追加によりPrecisionが40%に留まった。

## Slide 10 — 結論

1. 1試行平均は**117.67 calls、572,128 tokens、$0.240974、6.65分**。
2. Chiefは平均**5.00論点**を生成しており、「論点が1件に固定される」問題はこのpilotでは解消している。
3. ただし、探索量を増やしても因果edge取得は改善せず、Stage 3ではコスト増とcandidate過剰生成が生じた。
4. 次の改善軸は、`process-instance選択`、`unresolved edgeに基づくpivot`、`atomic action正規化`、`candidate admission`、`critical evidence binding`の5点。
5. 公平なモデル比較には、同一4ユースケースを両モデルで実行するpaired実験が必要。
