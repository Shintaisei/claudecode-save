# ATLASv2 S3/S4におけるCBCアラート起点の攻撃行動列復元実験

作成日: 2026-07-23  
状態: **実験準備完了。モデル実行・結果集計は未実施。**  
対象ホスト: `WIN-32-H1`  
対象シナリオ: ATLASv2 S3, S4

## 1. この追加実験の位置付け

本研究の目的は、アラートを単に「真陽性／偽陽性」と分類することではない。調査者が判断を下す前提となる、ログ証拠の収集、関連ログの対応付け、時系列での整理を自動的に構成することである。既存の正常行動23ユースケースでは、host・process・時間窓を与え、アラート要約なしでも証跡付き行動列を復元できる場合があることを確認した。

一方、その実験だけでは、実際に検知製品が発したアラートを起点として、攻撃に関係する行動列をどこまで復元できるかは検証していない。そこで本追加実験では、ATLASv2に記録された実在のCBCアラートを調査開始点とし、観測ログだけから攻撃行動列を復元できるかを評価する。

この実験で検証する主張は、次のように限定する。

> CBCアラートを受けた調査において、エージェントがアラート文面の再述にとどまらず、一次ログに基づく証跡付き攻撃行動列を構成できる条件と範囲を明らかにする。

したがって、評価対象は「攻撃を必ず完全復元できるか」や「アラートの真偽を自動決定できるか」ではない。観測された証拠で裏付けられる範囲を過剰に因果接続せずに復元できるかを評価する。

## 2. 研究課題と評価対象

本実験は、以下の三つの研究課題を扱う。

| 研究課題 | 問い | 観測する出力 |
| --- | --- | --- |
| RQ1: アラート起点復元 | CBCアラートを与えたとき、対応する攻撃行動列を証跡付きで復元できるか | 行動ステップ、親子関係、コマンド、通信、順序 |
| RQ2: 起点の具体性 | 同じ攻撃クラスタに対する異なるアラート種別で、復元の質は変わるか | アラート種別ごとの復元スコア |
| RQ3: アラート要約への依存 | アラート要約を入力から除き、さらにDB上でも隠したとき、どこまで復元能力が残るか | Stage 1–3の別集計結果 |

主要評価対象は、Goldで定義した行動ステップ、必要な証拠要素、行動順序である。`triage_decision`はエージェント出力として保存するが、本スイートでは採点しない。すなわち、本実験の主張は判断の自動化ではなく、判断の土台となる行動列復元の自動化にある。

## 3. データセットと攻撃シナリオ

対象は、同一Windowsホスト `WIN-32-H1` のATLASv2 S3およびS4である。両シナリオには、悪性文書を入口とし、正規Windowsプログラムを利用してコード実行・payload実行・外部通信へ進む記録が含まれる。

### 3.1 S3

S3では、悪性RTFをWordで開いた後、Equation Editor、`regsvr32`、PowerShell、`cmd`、payloadへ至る系列が観測される。

```text
Wordが悪性RTFを開く
  ├─ 境界ケース: Word PID5592（後続への直接エッジは未確定）
  ├─ Equation Editor PID6032 → regsvr32 PID6124 → 10.193.66.115:8080
  └─ Equation Editor PID2244 → regsvr32 PID3992 → PowerShell PID2340
                                  → cmd PID1880 → payload.exe → ortrta.net:9999
```

ここで、Word PID5592から後続のEquation Editorへ直接つながるログ証跡は確認できない。そのため、Word起点ケースのGoldは「Wordが文書を開いた」という観測済み範囲に限り、後続のローダやpayloadを必須ステップに含めない。

### 3.2 S4

S4では、複数のWordエピソードと、`svchost`から`mshta`、PowerShell、payloadへ至る長い系列が記録される。

```text
Wordエピソード
  W1: Word PID3236 → 子Word PID4572、外部:8080
  W2: Word PID5980 → 子Word PID3784、外部:8080
  W3: Word PID2608 → 子Word PID3060、外部:8080

長い実行系列
  svchost PID644 → mshta PID4724 → PowerShell PID2976 → PowerShell PID3820
                   → cmd PID2168 → payload.exe → ortrta.net:9999
```

Wordエピソードと`mshta`系列は時刻が近いが、両者を直接つなぐ親子関係などの観測エッジはない。よって、同じホスト上の攻撃文脈としては扱うが、一つの因果系列としてGoldには接続しない。

## 4. ユースケースの設計

### 4.1 選定原則

CBCアラートを次の条件で選定した。

1. `cbc_alerts`に実在するアラート行である。
2. host、対象プロセス、PID、アラート作成時刻から調査入力を構成できる。
3. 一次ログにより、親子関係、コマンドライン、通信、ファイル操作の少なくとも一つが確認できる。
4. 同一攻撃クラスタでも、検知対象や`report_name`が異なるアラートは別の調査起点として残す。
5. 同じPID、親PID、`alert_id`、`report_name`の単なる重複行だけを統合する。
6. 明確な連結系列だけでなく、未観測の因果を補わずに止まれるかを確認する文書起点の境界ケースも含める。

ATLASv2のプロセスGround Truthは候補選定の補助に用いるが、PID再利用があるため、PIDラベルだけを正解根拠には用いない。Goldは実データベースのログ証跡に基づいて定義する。

### 4.2 入力数と評価単位

Stage 1では、選定したCBCアラートごとに入力を作る。S3は11件、S4は13件、合計24件である。同じ攻撃クラスタに複数アラートがあっても、現場では異なるアラートが別の調査開始点になり得るため、Stage 1では保持する。

一方、Stage 2/3はアラート要約を入力から除く。同じhost・process・時間窓という可視入力を、異なるGoldに対して重複採点することを避けるため、一意なprocess-time文脈に統合する。S3は4文脈、S4は4文脈であり、各Stageは8入力となる。

| シナリオ | Stage 1: CBCアラート起点 | Stage 2: process-time | Stage 3: process-time + 要約非表示 |
| --- | ---: | ---: | ---: |
| S3 | 11 | 4 | 4 |
| S4 | 13 | 4 | 4 |
| 合計 | **24** | **8** | **8** |

したがって、総モデル入力数は40である。ただし、Stage 1の24件とStage 2/3の8件は一対一に対応しない。このため、Stage 1は「アラート種別を含む調査開始点の評価」、Stage 2/3は「一意なprocess-time文脈における要約依存性の評価」として別集計する。24件対8件を、そのまま対応ありの性能差として解釈してはならない。

### 4.3 カバレッジ

ユースケースは、攻撃の開始位置と行動列の長さが偏らないように構成した。

| 種類 | S3 | S4 | 実験上の役割 |
| --- | --- | --- | --- |
| 文書／Office起点 | Word `normal.dotm` | Word `normal.dotm`、Office VBL | 未観測の因果を補わない境界評価 |
| ローダ起点 | `regsvr32`、`scrobj.dll`、外部通信 | `svchost`→`mshta`、HTA | 親子・通信を用いる前方復元 |
| スクリプト起点 | PowerShell `IEX`、URL download | hidden/encoded PowerShell | 中間地点からの前後復元 |
| 後段起点 | PowerShell interpreter | child PowerShell encoded | payload/C2までの後段復元 |

## 5. 実験条件

### 5.1 共通入力

全ケースについて、対象ホスト、対象プロセス、時間窓を入力として与える。時間窓はCBCアラートの`create_time`を中心とする前後15分、合計30分で固定する。CBCアラートは実行ログより遅れて作成される場合があるため、アラートより前に生じた入口・親プロセスも観測できるようにした。

時間窓はプロンプト上の指示ではなく、各caseの`enforce_time_scope: true`によりadapter DBへ物理的に適用する。対象テーブルから窓外行を除外するため、エージェントが時間範囲外のログを検索して結論に使うことはできない。

### 5.2 三つの情報条件

| 条件 | モデルに与える開始情報 | CBCアラート要約のDB上の扱い | 目的 |
| --- | --- | --- | --- |
| Stage 1 | host、process、30分窓、選定CBCアラート要約 | 利用可能 | 現場のアラート起点調査として復元できるか |
| Stage 2 | host、process、30分窓 | 利用可能。ただし開始入力には含めない | 開始時の要約なしで調査できるか |
| Stage 3 | host、process、30分窓 | SQL探索対象から除外 | 下位テレメトリのみで復元できるか |

Stage 3は`--exclude-cbc-alert-summary`が必須である。フラグなしでStage 3を実行しようとすると、実行器はfail-closedで停止する。これにより、アラート要約が見えているStage 2相当の条件で誤ってStage 3を実行することを防ぐ。なお、CBCの下位イベントテレメトリは残す。Stage 3が除外するのはアラートのタイトル・理由等の要約行であり、攻撃の一次証拠そのものではない。

### 5.3 入力・Goldの漏えい防止

Stage 1の入力に含めるCBC要約は、各ケースで選定した1件のアラート行だけである。Goldの先頭ステップや後続行動列を入力から生成していない。

Stage 2/3の入力には、`alert_id`、`alert_name`、`alert_reason`、`cbc_alert`、`ground_truth`、`source_alert_row`を含めない。dry-runの実際のChief入力を全ケースについて確認し、Stage 2/3にGold、期待行動、アラート要約が混入していないことを検査した。

## 6. 正解データ（Gold）の定義

### 6.1 Goldが表すもの

Goldは、攻撃シナリオの説明文を要約したものではない。各調査入力に対して、観測ログから復元すべき最小限の行動列と、その根拠を定義したものである。各Goldステップには、以下のいずれかの具体的な証跡を対応付ける。

- プロセスの親子関係
- 実行ファイル・コマンドライン
- スクリプト実行内容
- ネットワーク接続先、ポート、DNS名
- ファイル作成・起動等のイベント

Goldの順序評価には、明示的な順序ペアを用いる。従来Goldの`[before_step_id, after_step_id]`形式と、新しいmapping形式のどちらも採点器が正規化して扱う。

### 6.2 過剰主張を防ぐ規則

Gold作成では、次を禁止する。

- 同一ホスト・近接時刻であることだけを理由に、別系列を因果接続すること。
- CBCアラートのタイトルや検知理由を、一次ログの代わりの証拠として使うこと。
- ATLASv2のシナリオ記述を、そのまま観測済みの行動ステップとして採点すること。
- 文書起点から後続ローダへの直接エッジがないにもかかわらず、攻撃全体をGold必須ステップにすること。

この規則により、S3のWord境界ケース、S4のWord W1–W3は、長いpayload系列とは分離して採点する。これらは失敗しやすいノイズではなく、「証拠のない接続をもっともらしく補完しない」という能力を確認するための限界ケースである。主たる攻撃行動列の成功率と混ぜず、別途報告する。

### 6.3 Stage 3で採点可能なGold

Stage 3ではCBCアラート要約を閲覧できないため、要約にしか根拠を持たないステップを採点してはならない。Stage 3の8ケースについて、各Goldステップがcanonicalな`cbc_events`証跡だけで裏付けられることを検査し、45ステップを`stage3_status=pass`として採点対象に登録した。`cbc_alerts`要約に依存するステップは0件である。

## 7. 実装と実行パイプライン

専用の実行・採点ドライバを用意した。

```text
case JSONL
  → caseごとのGold path解決
  → Stage 3の採点可能ステップCSV生成・検査
  → CLOUSEAU runnerでモデル実行
  → caseごとのGoldを指定して採点
```

旧実験用のドライバはGoldのルートを固定していたため、本スイートには使用しない。新しいドライバは各caseの`formal_gold_root`と`gold_chain_file`からGoldを解決し、40入力それぞれを正しいGoldで採点する。

実行前には次をfail-fastで確認する。

1. Stage 1=24、Stage 2=8、Stage 3=8、合計40という構成であること。
2. `instance_id`が重複していないこと。
3. 全40ケースのGold pathが解決できること。
4. 各Goldに採点可能なステップと必要な行動要素があること。
5. Stage 3のGoldがCBCアラート要約に依存しないこと。
6. Stage 3 validation CSVで8ケースすべてを採点可能に絞り込めること。
7. Stage 3の実行コマンドに必ず`--exclude-cbc-alert-summary`が付くこと。

## 8. 準備段階での検証結果

ここで報告するのは**実験準備の検証結果**であり、モデルの復元性能ではない。

| 検証項目 | 結果 | 意味 |
| --- | ---: | --- |
| S3 Gold・入力検証 | 157/157 pass | S3のGold証跡、時刻窓、入力条件を確認 |
| S4 Gold・入力検証 | 284/284 pass | S4のGold証跡、時刻窓、入力条件を確認 |
| 統合case再生成preflight | 85/85 pass | 40入力の構成・一意性・Stage条件を確認 |
| Gold path解決 | 40/40 | 各入力が対応するGoldを参照可能 |
| Stage 3採点対象 | 8ケース・45ステップ | 要約非表示でも採点可能な一次証拠のみ |
| Stage 3 Goldの要約依存 | 0ステップ | `cbc_alerts`要約への依存なし |
| 専用ドライバdry-run | 40/40完走 | 実行・保存・Gold接続の配線を確認 |

dry-runは`gpt-5.4-mini`を指定して実施したが、モデルAPIを呼び出していない。したがって、この時点でモデルの成功率、時間、費用はまだ報告できない。

独立レビューでは、次の条件が再確認された。

- 全40入力で`hard_time_scope_enforced=true`
- Stage 3の8入力で`post_filter_cbc_alert_summary_rows=0`
- Stage 2/3のclueにGold、期待行動、アラートID・名称・理由の漏えいなし
- Stage 3の8ケースすべてで、validation CSVによる採点フィルタ後にも分母が残る
- 実行器が各caseのGoldを参照し、旧スイート固定のGoldを誤用しない

以上から、モデル実行から個別Goldによる採点までを一貫して開始できる状態にあると判定した。

## 9. 研究報告での結果提示方針

モデル実行後は、少なくとも以下を分けて示す。

1. **Stage 1: アラート起点復元**  
   24 alert-target入力における復元性能を、S3/S4、攻撃段階、アラート種別ごとに示す。

2. **Stage 2/3: 要約依存性**  
   8 unique process-time入力に対して、開始入力からアラート要約を除いた影響（Stage 2）と、DB検索からも要約を除いた影響（Stage 3）を示す。

3. **境界ケース**  
   Word文書起点を主攻撃行動列の成功率とは分離し、未観測の因果関係を不当に補完しなかったかを定性的・定量的に示す。

4. **復元範囲**  
   入口、ローダ、PowerShell、payload、外部通信のどこまで到達できたかを、Goldステップ・証拠要素・順序の各指標で示す。

5. **実用性**  
   モデル別に、実行時間、入力時間窓（30分）に対する完了可否、API費用、失敗・中断率を併記する。

この構成により、「アラート要約がある24件」と「要約を除いた8件」を不適切に一対一比較することを避けつつ、アラート起点の実務的評価と要約非依存の能力評価を両方報告できる。

## 11. 結論

ATLASv2 S3/S4に対するCBCアラート起点の攻撃復元実験は、24件のアラート起点入力と、情報を段階的に削減した8件ずつのprocess-time入力からなる40入力スイートとして準備した。各入力のGold、時間窓、入力隔離、Stage 3のアラート要約除外、採点接続を検証済みである。

現時点で確定しているのは、**意図した条件で実験を開始し、ケースごとに正しいGoldで採点できる**ことである。まだ確定していないのは、各モデルが実際にどこまで攻撃行動列を復元できるか、30分以内に完了するか、どの程度の費用がかかるかである。これらはモデル実行後の結果として報告する。
