発表用 2枚構成スライド方針
更新日: 2026-05-12

1. まず結論
- 明日の発表で 2 枚にまとめるなら、
  - 1枚目で「ユースケース候補をどう作ったか」
  - 2枚目で「その中で何が使えて、何が難しいか」
  の構成が最も分かりやすい
- 今回の論点は、
  - 異常検知から正常候補をどう抽出したか
  - その候補が Security 生ログ上で本当に追跡可能か
  の 2 段階である
- したがって、2枚とも候補一覧を並べるのではなく、
  - 1枚目は「作り方の正当性」
  - 2枚目は「研究上の知見」
  を担わせる


2. なぜこの2枚構成がよいか
- 今の内容は
  - 異常検知の方法
  - 偽陽性候補の抽出
  - ユースケース化
  - 起点の評価
  が混ざって見えやすい
- そのまま 1 枚に詰めると、
  - 何をしたのか
  - 何が分かったのか
  が分離しない
- なので、
  - 1枚目 = 何をしたか
  - 2枚目 = 何が分かったか
  と分けると、聞き手が追いやすい


3. 1枚目の役割
- タイトル案
  - 「偽陽性候補からユースケース候補を作る流れ」
  - 「異常検知結果から正常ユースケース候補を抽出」
- このスライドの目的
  - ユースケース候補が恣意的に選ばれたものではなく、
    異常検知結果から機械的に得られたことを示す
- 聞き手に持って帰ってほしいこと
  - 「候補は最初から決め打ちしていない」
  - 「normal-only の異常窓から選んでいる」


4. 1枚目に載せるべき内容
- 目的
  - 偽陽性として上位化した正常行動から、追跡実験用ユースケース候補を作る
- 抽出フロー
  - 5日目ログにシーケンス異常検知
  - 上位シーケンスをそのまま観察対象にする
  - シーケンス内部を再分割して局所 LOF をかける
  - 高スコアシーケンスの内部から説明可能な process を抽出
- 結果として出てきた候補
  - explorer.exe
  - winword.exe
  - firefox.exe
  - repmgr.exe
  - repwmiutils.exe
  - spoolsv.exe
  - tpautoconnsvc.exe
- 1文の結論
  - ユースケース候補は、異常検知で上位化した正常窓から抽出した


5. 1枚目のおすすめレイアウト
- 上段
  - 目的を 1 文で書く
- 中段
  - 4 ステップ程度のフロー図
    - シーケンス検知
    - シーケンス保持
    - 局所 LOF
    - 候補抽出
- 下段
  - 候補 process を横並びか小表で置く
- 小表にするなら列は 3 つ程度で十分
  - candidate process
  - normal-only
  - ざっくり行動型


6. 1枚目で話す内容の例
- 第二段階の LOF により、5日目ログから優先的に見るべき高スコアシーケンスを絞り込んだ
- このシーケンスをそのまま実務上の観察入力とみなし、内部だけを 10 event 単位で局所読解した
- その結果、explorer.exe や winword.exe などが局所的に現れる窓を、シーケンス内部の正常候補として確認できた
- ここで重要なのは、ユースケースを先に決めたのではなく、異常検知で上位化したシーケンスの内部から候補を作った点である


7. 1枚目で削ってよいもの
- LOF score の細かい数値一覧
- sequence rank / micro rank の全列挙
- raw log の長いパス
- 各候補の詳しい説明
- 7候補すべての詳細比較


8. 2枚目の役割
- タイトル案
  - 「Security 生ログから見た再構成可能性」
  - 「どの正常候補が起点から追跡可能か」
- このスライドの目的
  - 候補の中でも、実際に起点から追えるものと追いにくいものを分ける
- 聞き手に持って帰ってほしいこと
  - 「異常検知で上位だからといって、必ずしも良いユースケースではない」
  - 「対象オブジェクトが具体的に見えるかが重要」


9. 2枚目に載せるべき内容
- 評価軸
  - Security 生ログで具体的な対象が見えるか
  - 起点から関連ログ調達が回せそうか
  - 行動として意味づけできるか
- 3分類
  - 再構成しやすい
    - explorer.exe
    - winword.exe
    - firefox.exe
  - 条件付きで再構成可能
    - repmgr.exe
  - 起点はあるがユースケース化が難しい
    - repwmiutils.exe
    - spoolsv.exe
    - tpautoconnsvc.exe
- 具体的な根拠を短く添える
  - explorer.exe: Recent / AutomaticDestinations
  - winword.exe: Content.Word / temp file
  - firefox.exe: profile / telemetry file
  - repmgr.exe: Carbon Black events
  - spoolsv.exe: spool driver files
  - tpautoconnsvc.exe: spool DLL / HLP
- 1文の結論
  - 正常行動の再構成可能性は、異常度だけでなく対象オブジェクトの具体性に依存する


10. 2枚目のおすすめレイアウト
- 左側
  - 3分類の箱
    - 再構成しやすい
    - 条件付き
    - 難しい
- 右側
  - 各箱に process 名を配置
- 下段
  - 結論を 1 文で置く
- あるいは小表でもよい
  - process
  - raw で見えた対象
  - 再構成可否


11. 2枚目で話す内容の例
- 抽出した候補を Security 生ログに戻して確認すると、ProcessName だけでなく ObjectName や TargetFilename がかなり有効な起点になることが分かった
- explorer.exe では Recent や Jump List 系、winword.exe では Content.Word や一時ファイル、firefox.exe では Firefox profile 配下のファイルが確認できた
- これらは process 名より特異性が高く、正常行動の再構成に使いやすい
- 一方で spoolsv.exe や tpautoconnsvc.exe は具体パスは見えるが背景反復が強く、業務行動としての意味づけが難しかった
- したがって、再構成可能性は異常度だけではなく、対象オブジェクトの具体性に大きく依存すると言える


12. 2枚目で削ってよいもの
- 7候補すべての raw path を長文で並べること
- 全件数の細かい数値
- AccessMask の詳細一覧
- EventID の網羅列挙


13. 発表で一番伝えるべき芯
- 1. 異常検知結果から正常候補を機械的に作った
- 2. その中でも Security 生ログで対象オブジェクトが見えるものは再構成しやすい
- 3. 背景サービス系は高順位でもユースケース化しにくい


14. かなり短く言うなら
- 1枚目は「選び方」
- 2枚目は「使えるもの / 使えないもの」


15. 2枚をそのまま箇条書きにした完成版

[1枚目]
- 偽陽性として上位化した高スコアシーケンスから、追跡実験用ユースケース候補を作成
- 5日目ログにシーケンス異常検知を適用
- 上位シーケンスをそのまま観察対象とし、内部に局所 LOF を適用
- 高スコアシーケンスの内部から説明可能な process を抽出
- 候補として
  - explorer.exe
  - winword.exe
  - firefox.exe
  - repmgr.exe
  - repwmiutils.exe
  - spoolsv.exe
  - tpautoconnsvc.exe
  を得た
- ユースケース候補は、異常検知で上位化したシーケンスの内部から抽出した

[2枚目]
- 抽出候補を Security 生ログに戻して、起点として使える情報を確認
- 有効だったのは
  - ObjectName
  - TargetFilename
  - TargetObject
- 再構成しやすい
  - explorer.exe
  - winword.exe
  - firefox.exe
- 条件付きで再構成可能
  - repmgr.exe
- 起点はあるがユースケース化が難しい
  - repwmiutils.exe
  - spoolsv.exe
  - tpautoconnsvc.exe
- 正常行動の再構成可能性は、異常度だけでなく対象オブジェクトの具体性に依存する
