# ATLAS v2 複数シナリオ 正常ユースケース候補整理

作成日: 2026-05-04

## 1. この追加実験の目的

今回の目的は、`S3` だけでなく `S4 / M4 / M5 / M6` にも同じ抽出フローを適用し、

- どの scenario で
- どの種類の正常行動を
- どれくらいの粒度まで絞って
- 研究用の「正常ユースケース候補」として残せるか

を確認することである。

ここでの主眼は、`最高F1の異常検知器` を競うことではない。  
目的はあくまで、`attack を含むか attack 近傍にある広い文脈の中から、研究で使えそうな正常行動を復元すること` である。

そのため、評価は次の2軸で見る。

1. `coarse detector` が attack を含む session を少数まで絞れているか
2. その後に残した `review windows` や `high-confidence/usecase seeds` の中に、研究で使える正常行動が十分残っているか

## 2. 今回ほかの scenario に適用したフロー

S3 で最も安定していた `Security + computer_user + 10分` の coarse detector を、そのまま `S4 / M4 / M5 / M6` に横展開した。

流れは全 scenario で共通である。

1. `benign1_cu10_200k` を benign-only 学習データとして固定
2. 各 scenario の `attack_*_cu10` を test 側へ差し替え
3. `IsolationForest + 1-2gram TF-IDF` で coarse sequence を検知
4. coarse 陽性 sequence の中を second pass で `100 event chunk` 単位へ落とす
5. その中から、研究上読みたい正常行動の型に合わせて seed を選ぶ

重要なのは、最後の `seed 選定` を S3 と同じ process allowlist で固定しないことだった。  
S3 では `payload.exe / powershell.exe / regsvr32.exe` が強かったが、これは `S3特有の境界ケース` にかなり依存していた。  
正常ユースケースを作ることが目的なら、scenario ごとに残りやすい正常行動の型を見て seed を選び直す方が自然である。

### 3.2 coarse detector の読み方

この表だけを見ると `M4` が最も安定して見える。  
ただし今回の目的は `sequence-level F1` の最大化ではない。

実際には、

- `S4` は coarse detector の F1 自体は中程度だが、残った review windows がすべて正常だった

という違いがあり、`どの正常行動を研究材料にしたいか` によって value が変わる。

### 4.1 ここで見えたこと

`S4 / M4 / M6` は、review windows 段階で `attack event が 0` になっている。  
つまり `attack を含む coarse sequence` を起点にしても、second pass で見えているのは実質 `正常行動の島` である。

これは、正常ユースケース作成という目的にはかなり都合がよい。  
研究で欲しいのは「攻撃を見つけること」そのものより、「攻撃を含む長い文脈のどこに正常行動が密に残っているか」なので、`review windows が pure normal` であることはむしろ強みになる。

一方 `M5` だけは、review windows の中にも少量の attack が残った。  
これは欠点でもあるが、`PowerShell 主体の procedural chain が attack 近傍でどう見えるか` を見る境界ケースとしてはむしろ有用である。

## 5. S3 の高信頼 seed をそのまま使うとどうなるか

S3 では `payload.exe / powershell.exe / regsvr32.exe` を high-confidence seed として使った。  
これをそのまま他 scenario に流すと次のようになった。

| Scenario | selected windows | total events | attack | normal | コメント |
| --- | ---: | ---: | ---: | ---: | --- |
| S4 | 0 | 0 | 0 | 0 | S3 用 allowlist は空振り |
| M4 | 0 | 0 | 0 | 0 | S3 用 allowlist は空振り |
| M5 | 2 | 1,700 | 8 | 1,692 | PowerShell 帯だけ残る |
| M6 | 0 | 0 | 0 | 0 | S3 用 allowlist は空振り |

これは自然な結果で、`S3 の高信頼異常 seed` は `S3特有の境界ケース` に強かっただけで、`複数シナリオ共通の正常ユースケース抽出器` ではなかった。

したがって、正常ユースケースを主目的にするなら、`高信頼異常 seed` を共通化するのではなく、`scenario ごとの normal-dominant process` を使って seed を作る方がよい。

## 7. 複数シナリオを並べたときの役割分担

今回の結果を研究用途で見ると、各 scenario は次のように役割分担できる。

| Scenario | 向いている正常ユースケース | 行動型 | 判定 | コメント |
| --- | --- | --- | --- | --- |
| S4 | 更新・スキャン・管理系 | 背景動作型 | 正常 | pure normal が厚い |
| M4 | Office / 管理ツール操作 | 単発操作型〜手続型 | 正常 | 説明しやすい |
| M5 | PowerShell 近傍の normal context | 手続型 | 正常寄り | 境界ケースとして有用 |
| M6 | Office + WMI 背景処理 | 手続型 + 背景動作型 | 正常 | 混成型の文脈 |
| S3 | LOLBin / PowerShell / payload 近傍 | 手続型 | 正常寄り〜判断保留 | 攻撃近傍境界の代表例 |

ここで大事なのは、`一番良い scenario を1つ決める` 必要はないことだと思う。  
正常ユースケースを作る目的なら、むしろ

- `pure normal` を集める scenario
- `attack-near normal` を集める scenario

を分けて持つ方が強い。

## 8. 今回の目的に照らした結論

### 8.1 何が確認できたか

確認できたことはかなり明確である。

1. `S3` の高信頼 seed は、複数シナリオ共通の抽出器ではなかった
2. しかし `Security(cu10) -> second pass` の粗い流れ自体は他 scenario にも横展開できた
3. その後の seed を scenario ごとに切り替えることで、`pure normal` も `attack-near normal` も両方作れた
4. 特に `S4 / M4 / M6` は、最終 seed が `100% normal` になりやすく、正常ユースケース作成の母集団としてかなり扱いやすい
5. `M5` は pure normal ではないが、PowerShell 主体の境界ケースとして研究上の価値が高い

### 8.2 今回の目的に一番合う scenario

今回の目的が `正常のユースケースを作ること` なら、優先順位は次のように置くのがよい。

1. `M4`
   Office 操作と管理ツールが混ざるので、最も説明しやすい normal context
2. `M6`
   Office + WMI の混成で、M4 より少しシステム寄りの正常行動が取れる
3. `S4`
   背景動作型の normal context を大量に取れる
4. `M5`
   attack-near procedural case として補助的に使う

### 8.3 研究資料としての使い分け

資料化するときは、次の3層で整理すると分かりやすい。

1. `pure normal`
   S4 / M4 / M6
2. `attack-near normal`
   S3 / M5
3. `cross-scenario taxonomy`
   背景動作型 / 単発操作型 / 手続型 の軸で並べる

この整理にすると、単に「異常検知の精度がどうだったか」ではなく、`どの normal behavior がどの scenario で回収できたか` を主役にできる。

## 9. 実務・研究上の含意

今回の結果は、正常ユースケース作成に関して次の示唆を与える。

- 正常行動の抽出では、`最強の異常 detector` より `正常をどの型で残したいか` の方が重要
- 同じ detector を使っても、seed の選び方で残る normal context は大きく変わる
- Office 系、背景更新系、PowerShell 系のように、`行動型ごとのユースケース母集団` を scenario ごとに分けて作る方が再利用しやすい
- 特に `S4 / M4 / M6` のように final seed が pure normal になる scenario は、正常行動研究のベースラインとして扱いやすい

## 10. 現時点の推奨

次の分析フェーズでは、次の方針がよい。

1. `M4` を主ケースとして、Office / 管理ツールの正常行動を詳細復元する
2. `M6` を副ケースとして、Office + 背景管理の混成行動を復元する
3. `S4` を背景動作型の対照ケースとして使う
4. `M5` は境界ケースとして別枠で整理する

この構成にすると、

- pure normal
- mixed normal
- attack-near normal

の3種類が揃い、研究の正常ユースケース群としてかなりバランスがよい。
