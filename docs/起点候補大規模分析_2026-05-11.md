# 起点候補大規模分析

更新日: 2026-05-11

## 1. 目的

この文書は、`0417_網屋資料確認_小松崎.pdf` の定義に沿って、現在のデータ群から
**起点アラートとして実際に使えそうなもの** を横断的に洗い出し、次を明確にするためのもの。

1. どのデータ源に、どの粒度の起点候補があるか
2. それを `高特異性 / 中特異性 / 低特異性` のどこに置くべきか
3. 見かけ上は強そうでも、研究上は採用しない候補は何か
4. 明日の発表と今後の実験で、どの候補を優先して使うべきか

## 2. 先に結論

結論として、**ATLAS の `session_test.pkl` だけでは高特異性起点はほぼ作れない**。
一方で、`C_Data97` を中心とする Wazuh / Sysmon / Registry / FileCreate の詳細側には、
高特異性で扱える起点候補が複数ある。

特に強いのは次。

- `DropboxUpdate.exe -> C:\Windows\Temp\GUR*.exe`
- `install_choco_software.ps1` / `logs.zip` のような特定ファイル
- `Discord` や `Dropbox` の `Run` / protocol 関連レジストリキー
- `wazuh-agent.exe -> net.exe -> net1.exe` と `SecEdit.exe /export`

ただし最後の `net.exe` / `SecEdit.exe` 系は、**具体コマンドまで見ればかなり追えるが、PDF の厳密な高特異性条件では「中特異性」寄り** と置く方が安全。

## 3. 今回の分類ルール

`0417_網屋資料確認_小松崎.pdf` に合わせ、今回は次のルールで置く。

### 3.1 高特異性起点

次のどれかを直接示せるもの。

- 特定ファイルパス
- 特定 URL / ドメイン
- 特定レジストリキー
- 特定タスク名
- 特定サービス名

今回の横断分析では、**Wazuh alert 単体でも一部ある**。さらに Sysmon / Registry を足すと増える。

### 3.2 中特異性起点

次のように条件を足せば追えるもの。

- `host + user + process + local time window`
- 親子 process 連鎖
- 具体 command line
- 1-2分程度の周辺イベント

例:

- `wazuh-agent.exe -> net.exe accounts`
- `net.exe -> net1.exe user guest`
- `OneDrive.exe /background`
- `taskschd.dll` を読む `MicrosoftEdgeUpdate.exe`

### 3.3 低特異性起点

候補空間が広すぎて、そのままでは使いにくいもの。

- `Windows logon success`
- `svchost.exe` 単独
- SCA / CIS ベンチマーク通知
- `Executable dropped` でも背景生成が大量に混ざるもの

## 5. まず ATLAS 側の限界

`session_test.pkl` 側は、セッションごとに

- `templates`
- `label`

しか持たず、テンプレートも

`Provider=... | Channel=Security | EventID=4656 | ProcessName=firefox.exe | ObjectType=file`

のような要約済み文字列だった。

したがって、少なくともこのモデル入力だけでは次が落ちている。

- `ObjectName`
- ファイルパス
- `TargetFilename`
- `TargetObject`
- `CommandLine`
- `ParentImage`
- `TaskName`
- `ServiceName`
- URL / ドメイン

つまり、**ATLAS モデル入力だけで高特異性起点を作れないのは、後処理不足ではなく入力表現の限界** である。

## 6. 横断集計の結果

### 6.1 Wazuh alert の粗い特異性帯

Wazuh のフラット CSV を、次の簡易ルールで数えた。

- `targetFilename` あり: 高特異性候補
- 親子 process / command line / 強い rule description あり: 中特異性候補
- それ以外: 低特異性候補

結果は次。

| dataset | 高 | 中 | 低 | 読み方 |
| --- | ---: | ---: | ---: | --- |
| `C_Data42` | `164` | `312` | `1034` | 候補数は多いが背景ノイズも多い |
| `C_Data45` | `99` | `103` | `599` | Discord 系が目立つ |
| `C_Data96` | `0` | `0` | `1458` | Wazuh 側だけでは薄い |
| `C_Data97` | `14` | `87` | `510` | 数は少ないが質が良い |

重要なのは、**高候補の件数が多いこと自体は価値ではない** こと。
`C_Data42` と `C_Data45` には `Executable dropped` が多いが、その中には `.NET NativeImages` のような背景生成が大量に混ざる。

## 8. ケース別の直接根拠

### 8.1 Dropbox Update の Temp EXE 生成

`C_Data97` では、次の直接根拠が取れる。

- FileCreate で `DropboxUpdate.exe` が
  - `C:\Windows\Temp\GURC786.exe`
  - `C:\Windows\Temp\GUR9FB1.exe`
  - `C:\Windows\Temp\GUR8495.exe`
  - `C:\Windows\Temp\GUR5AA9.exe`
  を作成
- Wazuh で `Executable dropped in Windows root folder`
- ProcessCreate で
  - 親: `Dropbox 207.4.5821 Offline Installer.x64.exe`
  - 子: `DropboxUpdate.exe`

したがってこれは、
**「具体パス」「生成元 process」「前段の installer」まで追える高特異性起点」**
として採用できる。

### 8.2 Wazuh agent による discovery

`C_Data97` の ProcessCreate では、次が直接見える。

- `C:\Program Files (x86)\ossec-agent\wazuh-agent.exe`
- `net.exe accounts`
- `net user administrator`
- `net1 user guest`
- `SecEdit.exe /export /cfg C:\Windows\Temp\secexport.cfg`

Wazuh alert 側では

- `Discovery activity executed`
- `A net.exe account discovery command was initiated`
- `SecEdit.exe binary in a suspicious location launched by powershell`

が対応する。

これは **rule description だけではなく、具体コマンド列として追える** ため、
研究上かなり使いやすい。ただし PDF の厳密基準では「特定ファイル/URL」ではないため、
主分類は `中特異性起点` に置く。

### 8.3 OneDrive の Explorer access

`C_Data97` の ProcessCreate では

- `OneDrive.exe /background`
- 親: `C:\Windows\explorer.exe`

が見え、Wazuh 側では

- `Explorer process was accessed by ... OneDrive.exe, possible process injection`

が対応する。

これは **ユーザ文脈の process chain と alert が結び付く** ので、`中特異性起点` として扱える。

### 8.4 Discord の Run key 書き込み

`C_Data97` の Registry detail では、次が直接見える。

- `HKU\...\Software\Microsoft\Windows\CurrentVersion\Run\Discord`
- 値: `"C:\Users\win11\AppData\Local\Discord\Update.exe" --processStart Discord.exe`

さらに ProcessCreate では

- `Update.exe --processStart Discord.exe`
- `Discord.exe --squirrel-install 1.0.9163`

が見える。

これは Wazuh 単独では弱いが、**raw Sysmon / Registry を足すと高特異性起点に上がる**。

## 9. 再現性の観点

候補ファミリの横断出現をみると、再現性が高いのは次。

- `wazuh-agent.exe -> net.exe accounts`

  - 合計 `100`
- `net user administrator / guest`
  - `C_Data42`, `45`, `97`
  - 合計 `60`
- `taskschd.dll` by `svchost.exe`
  - `C_Data42`, `45`, `97`
  - 合計 `62`
- `taskschd.dll` by `MicrosoftEdgeUpdate.exe`

  - 合計 `17`

**再現性は低いが、1ケースとしての説明力は非常に高い**。

- `MsMpEng.exe -> LSASS`

## 11. 研究としての意味

今回の分析で重要なのは次の 2 点。

1. **ATLAS モデル入力だけでは高特異性起点は復元できない**
2. **ただし同じホストの richer な Wazuh / Sysmon / Registry を足すと、高特異性起点はかなりの精度で再構成できる**

つまり、モデルで扱う表現の限界と、後段の起点復元で補える部分が切り分けられた。
これはそのまま、実験系の限界と今後の拡張方針になる。

## 12. 次にやるべきこと

優先度順では次。

1. `DropboxUpdate.exe` ケースをケーススタディとして固定する
2. `wazuh-agent.exe -> net.exe -> net1.exe -> SecEdit.exe` を 1 本の手続型ケースとして整理する
3. `OneDrive` / `Discord` の raw registry と process chain を alert と対応付ける
4. `taskschd.dll` は `svchost.exe` ではなく `EdgeUpdate` など意味のある process 側だけ残す
5. `.NET NativeImages` 系の `Executable dropped` は除外ルールに入れる
