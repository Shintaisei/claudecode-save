# 手法節用メモ 2026-06-15

このメモはFIT2026原稿の「手法」「実験設定」「評価方法」に書くための日本語材料である。特に、単にCLOUSEAUのアーキテクチャを使っただけではなく、評価設計・正解データ・採点・レビュー手順をかなり作り直したことを明示する。

## まず伝えるべきこと

本研究で固定したアーキテクチャは、計画エージェント、調査エージェント、QA/SQL、最終統合からなるCLOUSEAU型のログ調査パイプラインである。一方、本実験の主な工夫はアーキテクチャ自体の新規性だけではない。むしろ、SOC調査起点からログ上の行動列をどれだけ証跡付きで復元できるかを測るために、入力条件、正解データ、採点単位、レビュー手順を再設計した点が重要である。

## アーキテクチャ以外に変更した点

| 観点 | 変更内容 | 論文での意味 |
| --- | --- | --- |
| 評価対象 | 単一ケースではなく23個の行動チェーンを対象化 | 個別事例ではなく、複数の振る舞い型に対する評価になる |
| 入力条件 | stage1/stage2/stage3の3段階に分けた | 初期手掛かりが弱くなると復元精度がどう変わるかを測れる |
| Stage3 | CBC alert summaryをSQL検索対象から隠した | アラート要約を言い換えるだけでなく、telemetryから復元できるかを測る |
| 正解データ | alert summaryを根拠として数えないnon-alert goldへ寄せた | アラート文ではなくログ証跡に基づく行動復元を評価できる |
| 採点単位 | 行動全体の一括一致ではなく、主語・行動・対象・証跡・順序へ分解 | どの能力が弱いかを部品別に分析できる |
| 採点方針 | 表現一致ではなく内容包含で採点 | 出力形式や言い回しの違いではなく、実質的に正解内容を含むかを評価できる |
| レビュー | 2回レビュー、割れた場合の追加採択を導入 | 単一judgeのぶれを抑え、採点の根拠を残せる |
| GPT-5.5 | 構造化出力に失敗したためraw出力salvageとして別扱い | 能力の参考値として見るが、正式な構造化runとは区別する |
| 分析軸 | stage別、場面別、usecase別、モデル主張別、Investigator/SQL proxy別に整理 | 平均点だけでなく、どの場面で何が起きたかを説明できる |

## Stage設計

本実験では、同一の行動チェーンを3つの入力条件で評価する。

| stage | 入力 | DBで見える情報 | 目的 |
| --- | --- | --- | --- |
| stage1 | process-time情報に加えてCBC alert summaryも入力に含める | CBC alert summary、CBC EDR/NGAV、OS/browser logs | アラート補助ありでの復元能力を見る |
| stage2 | host、process、timestampなどのprocess-time情報のみを入力にする | CBC alert summaryはDB内では検索可能 | アラート文を手渡ししない場合に、モデルが調査で関連情報へ到達できるかを見る |
| stage3 | process-time情報のみを入力にする | CBC alert summaryはSQL検索対象から隠し、CBC EDR/NGAV telemetryは残す | アラート要約に頼らず、telemetry証跡から行動を復元できるかを見る |

Stage3は「CBCを全部消す」条件ではない。消しているのはalert summaryであり、EDR/NGAV telemetryは残している。このため、Stage3はアラート要約ショートカットを外した条件として説明するのが正確である。

## 正解データの扱い

正解データは、アラート名やアラート説明の再記述ではなく、ログ上で確認できる行動ステップとして整理する。各ステップは、主語、行動、対象、重要証跡、順序関係に分けて扱う。

重要な方針は次の通りである。

- CBC alert summaryは調査の入口としては使ってよい。
- しかし、CBC alert summaryだけを根拠にした内容はnon-alert evidenceとして数えない。
- Stage3に合わせて、alert summaryを根拠にしないgoldへ寄せた。
- これにより、「アラートを説明できたか」ではなく、「ログ証跡から行動を復元できたか」を評価できる。

## 採点rubric

最終採点では、行動ステップを細かい部品に分けて評価する。

| 指標 | 分母 | 意味 |
| --- | --- | --- |
| `action_step_recall` | gold step数 x 3 | 主語、行動、対象をどれだけ復元できたか |
| `critical_evidence_recall` | gold step数 | 各行動を支える重要なnon-alert evidenceを復元できたか |
| `behavior_sequence_order` | gold step数 - 1 | 隣接する行動順序をどれだけ保てたか |
| `candidate_claim_precision` | 候補出力のclaim slot数 | 出力した主張のうち、どれだけ正しい/支持可能か |
| `overclaim_slot_count` | 件数 | gold外、誤り、根拠不足の主張がどれだけあるか |

採点は厳密な文字列一致ではなく、内容包含で行う。つまり、フィールド名や表現が違っても、正解データの実質的な内容が出力内に入っていればhitとする。ただし、alert summaryだけを根拠にした内容はcritical non-alert evidenceのhitにしない。

## レビュー手順

採点は単一の自動judgeだけに依存しない。各runについて候補出力とgoldを並べたレビュー行を作成し、2回の独立レビューを行う。2つのレビューで一致したものを採用し、割れたものはconflict queueに入れて、追加レビューまたは保守的な採択ルールで確定する。

この手順により、モデル出力の形式差、GPT-5.5のraw出力、証跡の言い換えなどに対して、単純な自動一致よりも妥当な採点を行う。

## GPT-5.5の扱い

GPT-5.5は1周分、23チェーン x 3ステージ = 69 runを実施した。ただし、構造化JSON/code_steps契約に従わない出力が多かったため、4.1-miniや5.4-miniの正式な構造化runと同列には扱わない。

その代わり、raw出力に含まれる行動説明、証跡、仮説、QA風の質問を正規化し、同じcomponent rubricでsalvage採点した。したがって、GPT-5.5の結果は「潜在的な内容復元能力の参考値」としては有用だが、「構造化出力に成功した正式run」としては報告しない。

## 論文で使いやすい説明文

本研究では、CLOUSEAU型のエージェントアーキテクチャを前提としつつ、評価プロトコルを再設計した。具体的には、同一の行動チェーンに対して、アラート補助あり、process-time起点、alert summaryを検索対象から除外したtelemetry中心条件の3段階を設定した。また、正解データをalert summaryの再記述ではなく、ログ上で確認可能なnon-alert evidence付き行動ステップとして整理し、主語・行動・対象・証跡・順序の部品単位で採点した。さらに、採点結果は2回の独立レビューとconflict解消を通じて確定した。これにより、本実験は単なるアラート説明生成ではなく、SOC調査起点から証跡付き行動列を復元する能力を評価する設計になっている。

## 書かない方がよい表現

- 「新しいアーキテクチャを提案した」とだけ書く。
- 「Stage3ではCBC情報をすべて除去した」と書く。
- 「GPT-5.5は正式な構造化出力で最高精度だった」と書く。
- 「SQL精度を直接測定した」と書く。
- 「アラート情報を使わずに完全復元した」と書く。

より正確には、アーキテクチャは大きく変えず、評価設計、入力制御、gold、採点、レビュー、分析軸を作り込んだ、と説明する。
