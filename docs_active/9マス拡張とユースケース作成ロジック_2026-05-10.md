# 9マス拡張とユースケース作成ロジック

更新日: 2026-05-10

## 1. この文書の目的

- 先生に対して、異常検知による絞り込みの先で、どうユースケースを作るかを論理的に説明できる形にする
- 9マスを埋める作業が、恣意的な後付けではなく、異常検知結果から自然に導かれたことを示す
- `process` だけでなく、`file` や `domain` を起点にした拡張方針も明示する

## 2. 全体の論理

今回の研究の流れは、次の 4 段階で説明するのが自然。

1. 大量ログから異常検知で観察対象を絞る
2. 上位の局所ログに再ランキングをかける
3. その中から「正常だが偽陽性になりやすい」候補を抽出する
4. 抽出した候補をユースケースに変換し、9マスに配置する

重要なのは、ユースケースが最初から決まっていたのではなく、
**異常検知で上に来たものを観察した結果、偽陽性ユースケースとして意味があるものを残した**
という順序になっていること。

## 3. 絞り込みからユースケース作成まで

### 3.1 第1段階: first pass

- 元の大量ログから、異常らしい sequence を粗く絞る
- ここでは「どの時間帯・どの系列を見るべきか」を決める

### 3.2 第2段階: second pass

- `100 event chunk` 単位で再ランキングする
- ここでは「どの塊から読むべきか」を決める

### 3.3 第3段階: third pass

- 上位 chunk を `10 event micro-chunk` に切って再ランキングする
- ここでは「どの局所ログが、さらに異常検知に引っかかりやすいか」を決める

### 3.4 第4段階: ユースケース化

- `payload.exe` のような明確な攻撃主体は除く
- `tpautoconnect.exe` のような背景ノイズは切り分ける
- 残った非coreプロセスや関連対象を、偽陽性ユースケース候補とみなす

この第4段階が、先生に説明すべき「ユースケース作成」の核になる。

## 4. なぜこれでユースケースと言えるか

ユースケースとみなす条件は、次の 3 つで十分説明できる。

1. 異常検知で上位に来ている  
2. 正常行動として意味づけできる  
3. 偽陽性になりやすい理由を説明できる  

この条件を満たすものだけを残しているため、
「正常ログを後から広く拾ってきた」のではなく、
「異常検知で実際に見に行くことになる正常寄り候補」をユースケース化している、
と説明できる。

## 5. いまの中核ユースケース

現時点での中核候補は次の 3 つ。

- `explorer.exe`
  - 単発のファイル操作
  - 偽陽性になりやすい理由:
    背景ノイズ中に局所的に現れ、異常スコアが上がる

- `winword.exe`
  - 単発の文書閲覧
  - 偽陽性になりやすい理由:
    周辺アクセスと組み合わさると不審に見えやすい

- `repmgr.exe`
  - 文書関連アクセス連鎖
  - 偽陽性になりやすい理由:
    単独では意味が弱く、文脈なしだと異常に見えやすい

この 3 つは、絞り込み後の `top10 sequence` から直接得られており、もっとも論理的に強い。

## 6. 9マスをどう拡張するか

9マスを広げるときも、原則は変えない。

- 母集団は異常検知上位の sequence / chunk / micro-chunk
- そこから非core対象を抽出
- 偽陽性としての意味があるものだけ採用

この方針で、次のように拡張する。

### 6.1 process 起点

- `explorer.exe`
- `winword.exe`
- `repmgr.exe`
- `firefox.exe`
- `repwmiutils.exe`
- `spoolsv.exe`
- `tpautoconnsvc.exe`

### 6.2 file 起点

process をそのまま使うだけでなく、関連する file を起点に変換できる。

- `explorer.exe` が開いたファイル
- `winword.exe` が参照した文書
- `repmgr.exe` が触った文書関連オブジェクト
- `firefox.exe` 周辺のダウンロードファイル

これはかなり重要で、
**同じ候補から process ユースケースと file ユースケースの両方を作れる**
ため、9マスの拡張に使いやすい。

### 6.3 domain / browser artifact 起点

- `firefox.exe` 周辺の訪問ドメイン
- browser cache
- 一時ファイル

これは browser 系偽陽性ユースケースとして自然。

## 7. 9マスの読み方

今回の 9マスは、「正常行動の種類」と「起点特異性」の掛け合わせとして使う。

| 起点特異性 \ 正常行動 | 単発操作型 | 手続型 | 背景動作型 |
| --- | --- | --- | --- |
| `高` | `explorer.exe`, `winword.exe` | `repmgr.exe` | `空欄でもよい` |
| `中` | `firefox.exe` | `repwmiutils.exe` | `spoolsv.exe`, `tpautoconnsvc.exe` |
| `低` | 将来の対照群 | 将来の対照群 | 将来の対照群 |

ここで大事なのは、
9マスを無理に全部埋めることではなく、
**偽陽性として価値のある候補から順に埋める**
こと。

## 8. 先生向けに強調するとよい点

### 8.1 恣意的でないこと

- 先に異常検知で対象を絞っている
- その上位からさらに順位を付けている
- その順位の高い正常寄り候補だけをユースケース化している

### 8.2 偽陽性研究として自然なこと

- 攻撃そのものではなく、攻撃に見えやすい正常行動を対象にしている
- つまり SOC や実務者が実際に困る対象に近い

### 8.3 追跡実験につながること

- このユースケースは `CLOUSEAU` に渡す POI になる
- そこから追跡可能性や `正常 / 攻撃 / 判定不能` を評価できる

## 9. 研究の主張として言いやすい形

この部分は、次のように言うと通しやすい。

「本研究では、まず異常検知により観察対象を大幅に圧縮し、その上位結果に対して局所再ランキングを実施した。そこから、攻撃主体や背景ノイズを除いた正常寄り候補を抽出し、偽陽性になりやすい正常行動ユースケースとして整理した。したがって、後段で構成されるユースケースは後付けではなく、異常検知結果に基づいて自然に得られたものである。」

## 10. ユースケースの位置づけ

今回のユースケース群は、一般的な正常操作を網羅的に列挙したものではない。位置づけとしては、**一般操作の中でも、異常検知で偽陽性として上位化されやすく、かつ追跡可能性の差を比較しやすい正常行動候補群**である。

この定義にしておく理由は 3 つある。
1. 研究対象を「日常操作一般」ではなく「実務で実際に調査対象になりやすい正常操作」に限定できる。
2. ユースケース選定が後付けではなく、異常検知結果に基づく自然な抽出であると説明できる。
3. `CLOUSEAU` による追跡実験で、起点ごとの `追跡可能 / 半追跡可能 / 追跡困難` の差を比較しやすい。

したがって本研究では、一般操作の中から無作為にケースを取るのではなく、次の条件を満たすものをユースケース候補として採用する。
1. 一般操作として現実にあり得ること
2. 異常検知の `sequence rank` と `micro rank` で実際に上位化されていること
3. `payload.exe` のような攻撃そのものではなく、正常側の意味づけが可能であること
4. 起点から前後の関連ログを辿れるかどうかを比較できること

この条件で整理すると、9マスは「一般操作の分類表」ではなく、**偽陽性として現れた一般操作を、操作タイプと追跡可能性で比較するための整理表**になる。

具体的には、今回の候補は次のように位置づけられる。
- `explorer.exe`
  - 一般的なファイル参照・ファイル操作
  - 偽陽性として上がりやすく、追跡しやすい
  - `高 x 単発操作型`
- `winword.exe`
  - 一般的な文書閲覧・文書オープン
  - 偽陽性として上がりやすく、追跡しやすい
  - `高 x 単発操作型`
- `repmgr.exe`
  - 文書関連の手続的なアクセス連鎖
  - 正常操作だが単独では意味が弱く、文脈依存
  - `高〜中 x 手続型`
- `firefox.exe`
  - 一般的なブラウザ操作
  - 正常だが background noise に埋もれやすい
  - `中 x 単発操作型`
- `spoolsv.exe`, `tpautoconnsvc.exe`
  - 一般的なサービス・背景動作
  - 偽陽性としては上がりやすいが、追跡は難しい
  - `中 x 背景動作型`

このため先生向けには、「本研究のユースケースは、一般的な正常操作の網羅ではなく、異常検知結果から自然に抽出された偽陽性候補の正常操作を、操作タイプと追跡可能性の観点から整理した比較実験用ケース群である」と説明するのが最も論理的である。
