## 1. 残った attack 2 件 — 復元は可能か

### 1.1 事実関係

`100 event` 圧縮後に **attack ラベル付きで残ったのは 2 件のみ**（M4・S4 各 1 件）。

| 項目 | M4 | S4 |
| --- | --- | --- |
| micro rank | 3 | 9 |
| session | `win-32-h1\|...\|20220719T2250Z` | `win-32-h1\|...\|20220720T0050Z` |
| chunk / micro | `chunk068` / `micro05` | `chunk010` / `micro09` |
| テンプレート | `4663 \| searchprotocolhost.exe \| file` | 同左 |
| 同 micro 内 | normal 9 件（searchfilterhost, repmgr 等） | normal 9 件（sysmon, wmiprvse 等） |

いずれも **malware 実行ログではなく、file access 監査列に埋まった attack-labeled event** である。

参照 CSV:

- `analysis_data/model_runs/thirdpass_model_benchmark_benign1to4/m4_knn_review100/top_micro_flat_events.csv`（`label=1` の行）
- `analysis_data/model_runs/thirdpass_model_benchmark_benign1to4/s4_knn_review100/top_micro_flat_events.csv`（同上）

### 1.2 「復元」の種類を分ける

ここで言う復元は **1 種類ではない**。次の 3 層に分けて考える。

| 層 | 対象 | 可能か | 内容 |
| --- | --- | --- | --- |
| **A. 監査列の説明復元** | 残った 1 ログ + 同 micro 10 件 | **可能** | `4656→4663→4658` の並び、前後プロセス、同一 session 内の反復パターンを説明する |
| **B. 具体パス復元** | 上記 + `ObjectName` 等 | **条件付きで可能** | Security 生ログ（JSONL/XML）から `ObjectName`, `SubjectUserName`, `AccessMask` 等を引く。テンプレート CSV だけでは不足 |
| **C. 攻撃シナリオ全体復元** | payload 実行〜目的達成 | **Security 単体では不十分** | ATLASv2 groundtruth + Sysmon（ProcessCreate 等）+ 必要なら DNS/CBC が要る |

### 1.3 結論（attack 2 件）

- **「なぜ third pass 後も残ったか」の説明復元（A）** → 可能。研究上も価値がある（benign 監査列に attack が埋まる例）。
- **「どのファイルに触ったか」まで（B）** → 攻撃シナリオ用 Security JSONL が手元にあれば可能。**現ワークスペースには攻撃側 JSONL が無い**（後述 §6）。持ってくるか、`external/box/atlasv2.tar.gz` から展開する必要がある。
- **「M4/S4 攻撃手順全体」（C）** → 今回の主題（正常 FP 復元）とは別軸。第二段階の「攻撃 / 正常 / 保留」判断用に **参照ケース** として扱うのが自然。

**正常ユースケース（U1–U4）の復元とは目的が違う。**  
attack 2 件は「攻撃手順の完全復元」より **「モデルが落とせなかった attack-labeled 監査 event の説明」** を主眼に置く。

## 2. Excel での視覚化 — 何を作るか

### 2.1 目的

- 母集団 **400 event** のうち、どれが **採用 / 補助 / 除外 / attack** かを一目で分かるようにする
- 各ログが **どの pass で残り、どの micro-chunk に属するか** を追えるようにする
- 復元作業の進捗（定義済み / ObjectName 取得済み / ストーリー成立）を管理する

### 2.2 推奨ブック構成（シート 5 枚）

| シート名 | 行数 | 主な列 |
| --- | ---: | --- |
| **01_400マスター** | 400 | `scenario`, `micro_rank`, `offset_in_micro`, `label`, `template`, `ProcessName`, `EventID`, `ObjectType`, `parent_session_id`, `chunk_index`, `micro_index`, `pass_stage`(src/3k/100), `adoption`(U1–U4/補助/除外/attack/未分類), `restore_status`, `notes` |
| **02_採用サマリ** | 集計 | シナリオ×採用区分の件数、プロセス別件数（抽出まとめ §5 の表を再掲） |
| **03_U1-U4台帳** | 4（+補助1） | ユースケース ID、代表 1 ログのキー、代表 micro-chunk、優先シナリオ、復元ステータス、代表 ObjectName（後から埋める） |
| **04_残attack2** | 2 | §1.1 の表 + groundtruth 照合欄 + Sysmon 補足欄 |
| **05_復元チェックリスト** | 手順 | 下記 §4.3 の調査項目を行単位でチェック可能に |

### 2.3 入力データ（結合元）

| ソース | パス |
| --- | --- |
| 400 event フラット | `analysis_data/model_runs/thirdpass_model_benchmark_benign1to4/{s3,m4,m6,s4}_knn_review100/top_micro_flat_events.csv` |

### 2.4 視覚化のルール（色分け案）

- **緑:** U1–U4 主採用に紐づく行
- **黄:** 補助（`spoolsv.exe`）・境界（U4 caution）
- **灰:** 背景除外（sysmon, csrss, svchost, process なし 4688/4690 等）
- **赤:** `label=1`（残 attack 2 件）
- **白:** 400 内だが未分類（後で除外 or 文脈のみ）

### 3.2 生ログ（JSONL/XML）を見ないと分からないこと

| フィールド | 復元での役割 |
| --- | --- |

| **AccessMask** / **AccessList** | 読み/書き/削除の別 |
| **HandleId** | 4656–4663–4658 の同一操作チェーン紐づけ |
| **@timestamp** | 前後 10 分・同一 minute への展開 |
| **EventRecordID** | 生ログへの一意リンク |

`@timestamp`, `Channel`, `EventID`, `ProcessName`, `ObjectName`, `SubjectUserName`, …

| 調査 | 目的 |
| --- | --- |
| 代表 1 ログの **ObjectName** | UC 名を具体化（例: 特定 DLL, ユーザプロファイル, Office 文書パス） |

## 4. 「行動復元」の定義（この研究での意味）

### 4.1 最終ゴールとの関係

研究の最終ゴールは「攻撃 / 正常 / 決めきれない」の整理。  
**今フェーズ（第一段階）** で検証することは次の 1 文に集約する。

> **異常候補として浮いたログを起点に、関連ログを手がかりに狭め、analyst が納得できる“行動の説明”に到達できるか。**

（出典: `docs/ATLASv2_正常行動復元_統合ドキュメント.md` §2）

### 4.2 本フェーズで採用する定義（案）

**行動復元が「成立」したとき**、次の 4 条件をすべて満たす。

1. **起点:** third pass 後の 1 ログ（または残 attack 1 件）を明示できる  
2. **スコープ:** そのログを含む micro-chunk（10 event）を示せる  
3. **具体化:** 少なくとも 1 つは生ログフィールド（主に `ObjectName` または同等）で、抽象テンプレートを人間が読める行動に変換できる  
4. **判断:** その説明が「正常手続」「背景」「攻撃」「境界（attack-near だが benign 説明可）」のいずれかに分類でき、根拠を 1 段落で書ける  

**「成立しない」例**

- `4656/4663/4658` の並びだけ述べて終わり（ObjectName も前後プロセスも無い）  
- 10 件がすべて sysmon/csrss 背景で、ユーザ手続に結びつかない  
- 件数が少なく単独では story が立たない（searchfilterhost 等 — 抽出まとめ §7）

### 4.3 正常と attack で復元の意味を分ける

| 種別 | 復元の問い | 成功例 |
| --- | --- | --- |
| **正常（U1–U3）** | なぜ anomaly なのに benign か | 「管理エージェントが設定/収集用パスへ定期アクセス」 |
| **境界（U4）** | なぜ attack-near でも normal 側に残るか | 「索引更新の file access が attack ラベル付きイベントと同型」 |
| **残 attack** | なぜモデルが落とせなかったか | 「benign 型監査列への埋め込み。実行本体は別チャネル」 |

### 4.4 あえてやらないこと（スコープ外）

- 全 400 件の個別ユースケース化  
- 機械的な自動要約のみで「成立」判定  
- 第二段階の最終判定（攻撃/正常/保留）の確定 — 復元後に行う

## 6. 分析に使えるログ種別（ATLASv2）

### 6.1 データセットが持つストリーム（公式）

ATLASv2（`external/atlasv2/README.md`）には次がある。

| ストリーム | 形式の例 | 研究での位置づけ |
| --- | --- | --- |
| **Microsoft Windows Security Audit** | `msft-security` XML → JSONL | **現フェーズの主分析対象**（抽出・third pass 完了） |
| **Sysmon** | `sysmon-h1-*.xml` | 補助（ProcessCreate 中心の 100 件選定実験あり）。実行・コマンドラインの補強 |
| **DNS**（Wireshark） | txt | 通信の補助（今回未使用） |
| **Firefox** | ログ | アプリ操作の補助（今回未使用） |
| **Carbon Black Cloud**（cbc-edr, ngav, alerts） | jsonl | EDR 視点（今回未使用） |

シナリオ: benign 4 日 + attack 日の **S3, M4, M6, S4**（h1）を主に使用。

### 6.2 ワークスペース内の所在（2026-05-20 時点）

| データ | 場所 | 備考 |
| --- | --- | --- |
| Security benign JSONL | `analysis_data/atlasv2_benign_runs/jsonl/msft-security-h1-benign-*.jsonl` | 約 23 GB。**あり** |
| Security attack JSONL | `data_desc.json` 上は `...\ATLAS系データセット取得\hayabusa\atlasv2_runs\jsonl\msft-security-h1-{s3,m4,m6,s4}.jsonl` | **この PC ではパス不在** |
| deep-loglizer 前処理 | `analysis_data/atlasv2_for_deep-loglizer/exp_benign1to4_vs_*_cu10/` | session pkl 等。**あり** |
| モデル結果 | `analysis_data/model_runs/secondpass_*`, `thirdpass_*` | **あり** |
| Sysmon XML（一部） | `external/atlasv2_data/atlasv2/data/{benign,attack}/h1/sysmon/` | M4/M6/S3/S4 + benign1–4。**部分のみ** |
| フル ATLASv2 圧縮 | `external/box/atlasv2.tar.gz` | 約 12 GB。**未展開** |
| groundtruth | `data_desc` 上は `...\atlasv2\data\attack\h1\msft-security\groundtruth\` | **ワークスペース内未確認** |

### 6.3 持ってくる／展開すべきもの（優先順）

1. **必須:** `msft-security-h1-m4.jsonl`, `msft-security-h1-s4.jsonl`（残 attack・U4・ObjectName 用）  
2. **推奨:** 同様に `s3`, `m6`（比較・難易度ケース）  
3. **推奨:** 対応 **groundtruth** ディレクトリ（攻撃ラベル照合）  
4. **任意:** Sysmon XML 全シナリオ（`external/box/atlasv2.tar.gz` 展開、または Hayabusa 済み JSONL）  

配置案:

```text
analysis_data/atlasv2_attack_runs/jsonl/   ← 攻撃シナリオ Security JSONL
analysis_data/atlasv2_groundtruth/         ← groundtruth（公式構造を維持）
```

`data_desc.json` の絶対パスは、コピー後に一括置換するか、環境変数 `ATLASV2_ROOT` で参照するよう scripts を直す。
