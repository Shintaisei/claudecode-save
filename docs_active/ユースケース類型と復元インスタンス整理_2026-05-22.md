# ユースケース類型と復元インスタンス整理（2026-05-22）

## 目的

現在の議論では、次の 2 つが混ざりやすい。

1. 研究として何個のユースケースを立てているのか
2. 実際に `CLOUSEAU` に何件入力して試せるのか

さらに、`行動復元` の定義もまだ広く、何をもって「1件復元できた」と言うかが少し曖昧である。  
本メモではこの 3 点を分離して整理する。

## 1. まず区別するもの

本研究では、少なくとも次の 3 層を分けて扱う。

### 1.1 ユースケース類型

研究の本文や中間報告で使う、代表的な行動カテゴリ。  
例:

- `U1`: `repmgr.exe`
- `U2`: `repwmiutils.exe`
- `U3`: `tpautoconnsvc.exe`
- `U4`: `searchprotocolhost.exe`

これは「何系の行動を対象にするか」を表す分類であり、件数の単位ではない。

### 1.2 復元インスタンス

実際に `CLOUSEAU` に入力する 1 件 1 件の対象。  
これはシナリオ・時間帯・`micro-chunk`・`ObjectName`・文脈ごとに分かれる。

たとえば `repmgr.exe` でも、

- `M6` の安定した正常文脈
- `M4` のやや混ざった文脈
- `S4` の別時間帯

は別インスタンスである。

### 1.3 復元結果

各インスタンスに対して `CLOUSEAU` を実行し、

- どの主体が
- どの文脈で
- どのファイルアクセス行動をしたか

を説明した出力。

---

## 2. 「4つのユースケース」とは何か

今言っている `4つ` は、「研究上の代表類型が 4 つ」という意味で理解するのが自然である。  
つまりこれは

- 代表ラベル
- 代表カテゴリ
- 論文・報告用の整理軸

であって、「実験入力が 4 件しかない」という意味ではない。

現在の代表類型は次のように見ればよい。

| 類型ID | 主体 | 位置づけ |
| --- | --- | --- |
| `U1` | `repmgr.exe` | 管理エージェント系の正常ファイルアクセス |
| `U2` | `repwmiutils.exe` | 管理・収集補助系の正常ファイルアクセス |
| `U3` | `tpautoconnsvc.exe` | 接続補助サービス系の正常ファイルアクセス |
| `U4` | `searchprotocolhost.exe` | 境界的な検索・索引系ファイルアクセス |

この 4 つは「代表的に何を語るか」の整理であって、下に複数の実例を持ちうる。

---

## 3. 実際に `CLOUSEAU` に入れられる件数

実際に入力できる対象は、類型より多い。  
なぜなら 1 類型の中に、複数の復元インスタンスがあるからである。

復元インスタンスは、少なくとも次で分かれる。

1. シナリオごと
2. 時間帯ごと
3. `100 event chunk` ごと
4. `10 event micro-chunk` ごと
5. `ObjectName` ごと
6. 正常文脈 / 攻撃近傍文脈ごと

したがって、

- `4つの類型`
- `もっと多い入力件数`

は矛盾しない。  
むしろ、

- 類型は少数に絞る
- 実験インスタンスはその下で複数回す

という構造の方が自然である。

---

## 4. 具体的な理解のしかた

一番分かりやすい見方は次である。

### 4.1 上位: 類型

例:

- `management_agent_file_access`
- `management_agent_collection_file_access`
- `auto_connection_service_file_access`
- `search_indexer_file_access`

### 4.2 下位: インスタンス

例:

- `U1 / M6 / repmgr.exe / CryptnetUrlCache / normal`
- `U1 / M4 / repmgr.exe / 別 ObjectName / normal`
- `U3 / S4 / tpautoconnsvc.exe / file access / normal`
- `U4 / S3 / searchprotocolhost.exe / normal`
- `U4 / M4 / searchprotocolhost.exe / attack_context`
- `U4 / S4 / searchprotocolhost.exe / attack_context`

この整理にすると、

- 研究で語る代表ユースケースは少数
- 実際に回す `CLOUSEAU` 入力は複数

が同時に成立する。

---

## 5. 今の `行動復元` 定義がまだ甘い理由

現状では `行動復元` という言葉の中に、少し異なるレベルの作業が入っている。

### 5.1 混ざっているもの

1. `1ログ` を説明する
2. `1 micro-chunk` を説明する
3. `1 類型` の代表行動を説明する
4. `正常 / 攻撃近傍 / 攻撃` を判断する
5. `access_behavior` のような行動ラベルを付ける

これらは関連しているが、同じではない。

### 5.2 そのため起きていること

今は、

- 「復元した」と言ったときに何を指すか
- 1件の成功単位が何か
- 評価対象がインスタンスなのか類型なのか

がまだ少し揺れている。

したがって、「定義がまだ甘い」という感覚は正しい。

---

## 6. 今後はどう定義すべきか

実務的には、`復元成功` をインスタンス単位で定義し、類型はその上に載せるのがよい。

### 6.1 推奨する単位

**復元の最小単位 = 1 復元インスタンス**

つまり、

- 特定のシナリオ
- 特定の時間帯
- 特定の POI

に対して `CLOUSEAU` を 1 回走らせ、その結果を 1 件の復元結果とみなす。

### 6.2 類型の扱い

複数インスタンスを見たあとで、

- これは `U1` 型
- これは `U3` 型

のように上位類型へまとめる。

---

## 7. 現時点での定義案

現段階では、次のように置くのが一番扱いやすい。

### 7.1 ユースケース類型

複数の復元インスタンスをまとめるための代表カテゴリ。  
研究で「何系の正常 / 境界行動を対象にしたか」を述べるために使う。

### 7.2 復元インスタンス

`CLOUSEAU` に実際に入力する 1 件の調査対象。  
`scenario + time window + POI` で識別する。

### 7.3 行動復元

1 つの復元インスタンスについて、

- 主体
- 対象
- 操作
- 文脈
- 周辺根拠

を用いて、人間が読める形で「どんな行動だったか」を説明すること。

### 7.4 復元成功

少なくとも次を満たしたとき、そのインスタンスは復元成功とみなす。

1. `POI` が明示されている
2. 主体プロセスが言える
3. `read / write / delete / enumerate` などのアクセスの意味が言える
4. `normal / attack_context / attack` のどれ寄りか説明できる
5. その判断の根拠を周辺ログで支えられる

---

## 8. この整理で言えること

この整理を採ると、今の状態は次のように言える。

1. 研究上の代表ユースケース類型は現在 4 つである
2. ただし実際に `CLOUSEAU` に入力できる復元インスタンスはそれより多い
3. 今後の実験は「類型」ではなく「インスタンス」単位で回すべきである
4. `行動復元` の定義はまだ調整中だが、成功単位はインスタンスに置くと整理しやすい

---

## 9. 現時点の結論

現状の `4つ` は、入力件数ではなく **代表類型の数** と理解するのが正しい。  
一方で、実際に `CLOUSEAU` に流して試せる対象は、シナリオ別・時間帯別・POI別に見ればもっと多い。

また、`行動復元` の定義はまだ完全には締まり切っていない。  
したがって次段階では、

- 類型
- 復元インスタンス
- 復元成功条件

の 3 つを分けて書くことが重要である。
