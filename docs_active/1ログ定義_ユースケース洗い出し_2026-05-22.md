# `1ログを説明する` 定義でのユースケース洗い出し（2026-05-22）

## 目的

本メモでは、`行動復元` を次のように定義する。

> **行動復元 = 異常候補として残った対象 1 ログについて、その 1 ログが何の行動として読めるかを説明すること**

この定義に固定したうえで、現在の `ATLASv2 thirdpass review100` から、ユースケースとして扱える対象 1 ログを洗い出す。

---

## 1. 今回の定義

### 1.1 復元対象

復元対象は **1ログ** である。  
ここでいう 1ログとは、少なくとも次で識別できる 1 行の Security event を指す。

- `scenario`
- `session / time window`
- `EventID`
- `ProcessName`
- `ObjectType`
- 必要なら `offset_in_micro` や `event_record_id`

### 1.2 復元で言うこと

その 1ログについて、次を言えればよい。

1. **主体**  
   どのプロセスのログか
2. **行動**  
   何のファイルアクセス行動として読めるか
3. **文脈**  
   `normal` / `attack_context` / `attack` のどれ寄りか
4. **根拠**  
   その周辺ログを見て、なぜそう読めるか

### 1.3 重要な点

この定義では、復元の成功単位は

- `10ログまとまり`
- `プロセス群`
- `シナリオ全体`

ではなく、**対象 1 ログ** である。  
周辺 `micro-chunk` や `100 event chunk` は、1ログを説明するための補助証拠として使う。

---

## 2. この定義でユースケースとは何か

この定義を採ると、ユースケースとは

> **「どういう種類の 1ログを、どういう行動として説明するか」**

という単位になる。

したがって、ユースケース名は

- `repmgr.exe の 4663/file`
- `tpautoconnsvc.exe の 4663/file`
- `searchprotocolhost.exe の 4663/file`

のように、**対象 1 ログの型** を表すのが自然である。

---

## 3. 洗い出しの基準

今回、ユースケース候補に採る 1ログは次を満たすものとする。

1. `thirdpass review100` に実際に残っている
2. `EventID=4663` または、その解釈に直結する `4660` を含む
3. analyst が単体で見たときに一度は気になる
4. 周辺 `micro-chunk` を使えば説明が補強できる
5. 背景ノイズ単体ではない

逆に、次は主ユースケースには採らない。

- `sysmon.exe`
- `csrss.exe`
- `svchost.exe`
- `services.exe`
- process 名なし `4688 / 4690`

理由は、1ログで見ても「説明したい行動」より「背景監査」に寄りすぎるためである。

---

## 4. 洗い出した対象 1ログユースケース

以下では、対象 1ログの型としてユースケース候補を整理する。

### 4.1 主採用

#### U1. `repmgr.exe / EventID=4663 / ObjectType=file`

- 想定する行動:
  `management_agent_file_access`
- 主なシナリオ:
  `M6` 主軸、`M4` と `S4` は補助
- 理由:
  件数が最も多く、`all normal` で、1ログ単位でも「管理エージェントの file access」と説明しやすい
- 1ログ復元の問い:
  この `repmgr.exe 4663/file` は、何を読んだ / 列挙した正常アクセスなのか

#### U2. `repwmiutils.exe / EventID=4663 / ObjectType=file`

- 想定する行動:
  `management_agent_collection_file_access`
- 主なシナリオ:
  `M6` 主軸、`M4` は補助、`S4` は弱い
- 理由:
  `repmgr.exe` と並ぶ管理・収集補助系の 1ログとして意味づけしやすい
- 1ログ復元の問い:
  この `repwmiutils.exe 4663/file` は、収集補助のどの種類のアクセスとして説明できるか

#### U3. `tpautoconnsvc.exe / EventID=4663 / ObjectType=file`

- 想定する行動:
  `auto_connection_service_file_access`
- 主なシナリオ:
  `S4` 主軸、`S3` は別インスタンスとして比較
- 理由:
  件数が十分あり、名前だけでは役割が分かりづらく、1ログでも analyst が確認したくなる
- 1ログ復元の問い:
  この `tpautoconnsvc.exe 4663/file` は、一時ファイル処理 / 接続補助のどちら寄りか

#### U4. `searchprotocolhost.exe / EventID=4663 / ObjectType=file`

- 想定する行動:
  `search_indexer_file_access`
- 主なシナリオ:
  `S3 normal`, `S4 normal`, `M4 attack_context`, `S4 attack_context`
- 理由:
  件数は多くないが、1ログで見たとき最も境界的で、偽陽性説明の価値が高い
- 1ログ復元の問い:
  この `searchprotocolhost.exe 4663/file` は検索・索引更新の正常アクセスか、攻撃近傍の境界ログか

### 4.2 補助採用

#### U5. `spoolsv.exe / EventID=4660 or 4663 / ObjectType=file`

- 想定する行動:
  `print_spooler_file_access`
- 主なシナリオ:
  `M4` 主軸、`S3` は比較、`S4` は件数少
- 理由:
  1ログで見ると削除・後処理に見えやすく、補助比較として有用
- 1ログ復元の問い:
  この `spoolsv.exe` の file access / delete 系ログは、印刷後処理として説明できるか

### 4.3 保留

#### H1. `searchfilterhost.exe / EventID=4663 / ObjectType=file`

- 理由:
  件数が少なく、単独 1ログとしては説明材料が足りない
- 現時点の扱い:
  `searchprotocolhost.exe` の周辺補助ログ

#### H2. `wmiprvse.exe / EventID=4663 / ObjectType=file`

- 理由:
  件数が少なく、attack-near 文脈が強い
- 現時点の扱い:
  独立ユースケースより境界補助

## 5. `1ログ定義` にすると U4 はどう割れるか

特に `searchprotocolhost.exe / 4663 / file` は、1ログ主体にすると 1 件ではなく複数に割るのが自然である。

### 5.1 正常インスタンス

- `S3 / searchprotocolhost.exe / 4663 / file / normal`
- `S4 / searchprotocolhost.exe / 4663 / file / normal`

### 5.2 攻撃近傍インスタンス

- `M4 / searchprotocolhost.exe / 4663 / file / attack_context`
- `S4 / searchprotocolhost.exe / 4663 / file / attack_context`

したがって、**類型としては 1 つでも、1ログユースケースの実験対象としては複数に分かれる**。

---

## 6. 実際に回す単位

この定義にした場合、`CLOUSEAU` へ入力する単位は次になる。

> **対象 1ログ + その周辺文脈**

つまり、

- 主役は 1ログ
- `micro-chunk` は説明補助
- `100 event chunk` は背景補助

である。

このとき、入力候補の単位は

- `U1` という類型

ではなく、

- `M6 のこの repmgr.exe 4663/file 1行`
- `S4 のこの tpautoconnsvc.exe 4663/file 1行`

のような **個別ログインスタンス** になる。

## 8. この定義での利点

この定義にすると、次が明確になる。

1. 復元成功の単位が 1ログになる
2. 周辺 `micro-chunk` は「証拠」であって「主役」ではない
3. `4つしかないのか` と `もっと入力できるのでは` が両立する
4. `CLOUSEAU` に渡す POI をログ単位で固定しやすい

---

## 9. 結論

今後は、`行動復元 = 1ログを説明すること` と定義して進める。  
この定義に基づく現時点の主ユースケースは次の 4 つである。

1. `repmgr.exe / 4663 / file`
2. `repwmiutils.exe / 4663 / file`
3. `tpautoconnsvc.exe / 4663 / file`
4. `searchprotocolhost.exe / 4663 / file`

補助として

5. `spoolsv.exe / 4660 or 4663 / file`

を残し、`searchfilterhost.exe` と `wmiprvse.exe` は保留とする。  
以後の `CLOUSEAU` 実験は、これらの **対象 1ログインスタンス** を起点に回すのが自然である。
