# 抽出フェーズ完了まとめ

## 1. このフェーズで確定したこと

今回の抽出フェーズで確定した結論は次の 4 点である。

1. `数万 event -> 3000 event` までは pure model だけで圧縮できた
2. その標準フローとしては
   - `first pass: 10分 sequence-level IsolationForest`
   - `second pass: 100 event chunk-level IsolationForest`
   が最も妥当だった
3. `3000 event -> 100 event` も pure model で試した結果、
   - `M4 / S4` は `attack を少量含んだ normal 主体の 100event` を作れた
   - `S3` は 3000event までは強いが 100event では attack が落ちる
   - `M6` は upstream から難しく、difficulty case として扱うのが自然
4. したがって、抽出についてはここで一度完了とし、次フェーズでは `interpret and write usecases` に移る

## 2. 研究上の主張

このフェーズで言いたいことは、

`異常検知の候補集合から、attack を完全に消さずに false positive 側の正常文脈も残す review set を、段階的な pure model 圧縮で作れた`

という点である。

特に、

- `3000event` まではかなり安定して model-only で作れた
- `100event` も `M4 / S4` では model-only で mixed candidate set を作れた

ため、少なくとも

- `M4 / S4 = 補助ケース`
- `S3 = attack-near 比較ケース`
- `M6 = difficulty case`

という立て付けは十分に説明可能である。

## 3. 学習データと評価対象

### 3.1 学習側

- 正常学習データ: `Security benign-1to4`
- 使った粒度
  - first pass: `computer_user / 10分 sequence`
  - second pass: `100 event chunk`
  - third pass: `10 event micro-chunk`

### 3.1.1 各段階で何を学習したか

今回の抽出で使ったモデルは、すべて `Security benign-1to4` の正常データだけで学習した one-class / novelty detection である。

#### first pass の学習

- 学習対象:
  - `10分 sequence` に集約した正常データ
- 1 サンプルの意味:
  - ある `computer_user` の 10分ぶんの Security event 列
- 特徴化:
  - event template 列を `1-2gram TF-IDF` に変換
- 学習したもの:
  - `IsolationForest`
- スコアの意味:
  - 正常 4日間の sequence 分布からどれだけ外れているか
- 使い方:
  - scenario 側の全 sequence にスコアを付け、上位 anomalous sequence を残す

#### second pass の学習

- 学習対象:
  - 正常データを `100 event chunk` に切った集合
- 1 サンプルの意味:
  - Security event 100件の連続塊
- 特徴化:
  - chunk 内の event template 列を `1-2gram TF-IDF` に変換
- 比較したモデル:
  - `IsolationForest`
  - `LOF`
  - `One-Class SVM`
  - `SGD One-Class SVM`
  - `kNN`
- 最終採用:
  - `IsolationForest`
- スコアの意味:
  - 正常 chunk 分布からどれだけ外れているか
- 使い方:
  - first pass で残った sequence の内部 chunk にスコアを付け、`top30 chunk = 3000 event` を作る

#### third pass の学習

- 学習対象:
  - 正常データを `10 event micro-chunk` に切った集合
- 1 サンプルの意味:
  - Security event 10件の連続塊
- 特徴化:
  - micro-chunk 内の event template 列を `1-2gram TF-IDF` に変換
- 比較したモデル:
  - `IsolationForest`
  - `kNN`
- 最終採用候補:
  - `M4 / S4` については `kNN`
- スコアの意味:
  - 正常 micro-chunk 分布からどれだけ外れているか
- 使い方:
  - second pass の `3000 event` を micro-chunk 化し、`top10 micro-chunk = 100 event` を作る

### 3.1.2 学習と評価の分離

重要なのは、各段階で

- 学習:
  - `benign-1to4` の正常分布を覚える
- 評価:
  - `S3 / M4 / M6 / S4` 側のサンプルに異常スコアを付ける

という分離をしている点である。

つまり、attack ラベルを使ってモデルを教師あり学習したわけではない。  
ラベルはあくまで **抽出後の評価** にだけ使っている。

### 3.1.3 train / validation の扱い

`benign-1to4` 側も内部では train / validation に分かれており、

- train:
  - モデル fitting 用
- benign validation:
  - 正常スコア分布の確認用

として使っている。

second pass では、この benign validation 側の score 分布からしきい値を取り、chunk-level の `predicted_positive` 数などを評価した。  
ただし本研究で最終的に重視したのは threshold で切った二値判定そのものより、**score ranking の上位に attack と false positive がどう残るか** である。

- `M6`
- `S4`

## 4. 採用した圧縮フロー

### 4.1 first pass

- 単位: `10分 sequence`
- モデル: `IsolationForest`
- 役割: scenario 全体から anomalous sequence を数本に絞る

### 4.2 second pass

- 単位: `100 event chunk`
- 対象: first pass で predicted positive になった sequence の内部のみ
- モデル比較:
  - `IsolationForest`
  - `LOF`
  - `One-Class SVM`
  - `SGD One-Class SVM`
  - `kNN`
- 採用: `IsolationForest`
- 出力: `top30 chunk = 3000 event`

### 4.3 third pass

- 単位: `10 event micro-chunk`
- 対象: second pass の `3000 event`
- 比較したモデル:
  - `IsolationForest`
  - `kNN`
- 採用候補:
  - `M4 / S4` については `kNN`

ここで重要なのは、

- `3000event` まではかなり安定して pure model で作れた
- `100event` まで行くと scenario 差が大きくなる

という点である。

## 5. 圧縮の変遷

### 5.1 first pass 後

| scenario | predicted sequences | predicted events | predicted attack events | predicted normal events |
| --- | ---: | ---: | ---: | ---: |
| `S3` | `2` | `42,301` | `5` | `42,296` |
| `M4` | `4` | `75,223` | `20` | `75,203` |
| `M6` | `3` | `69,811` | `0` | `69,811` |
| `S4` | `3` | `67,992` | `13` | `67,979` |

読み:

- `S3 / M4 / S4` は first pass の時点で attack を含む sequence が残っている
- `M6` は first pass から attack が残っておらず、この時点で downstream の上限が決まりやすい

### 5.2 second pass 後

採用モデルは `100 event chunk-level IF`。

| scenario | review set | attack events | normal events | 補足 |
| --- | ---: | ---: | ---: | --- |
| `S3` | `3000` | `4` | `2996` | top30 なら attack を残せた |
| `M4` | `3000` | `1` | `2999` | top10 の時点でも attack が残る |
| `M6` | `3000` | `0` | `3000` | attack 不在 |
| `S4` | `3000` | `3` | `2997` | top10 の時点でも attack が残る |

ここで言えるのは、

- `3000event` までは `S3 / M4 / S4` で `attack + false positive` の混在集合を維持できた
- `M6` は second pass の問題ではなく、first pass から攻撃側が薄い

ということである。

### 5.3 third pass 後

`top10 micro-chunk = 100event`

採用候補として見た `kNN third pass` の結果は次。

| scenario | attack events | normal events | first attack rank | 読み |
| --- | ---: | ---: | ---: | --- |
| `S3` | `0` | `100` | `56` | 100event まで詰めると attack が落ちる |
| `M4` | `1` | `99` | `3` | attack と FP を両方残せる |
| `M6` | `0` | `100` | `null` | attack 不在 |
| `S4` | `1` | `99` | `9` | attack と FP を両方残せる |

一方、`IF third pass` は `M4 / S4` でも 100event では attack を残せなかった。  
そのため、`100event` の最終抽出では `IF` より `kNN` の方が良かった。

## 6. 各 scenario の位置づけ

### S3

- first pass / second pass までは attack-near 文脈を十分残せる
- ただし `100event` まで圧縮すると attack が落ちやすい
- したがって
  - `3000event` までは主張しやすい
  - `100event usecase` の主ケースにはしにくい
- 位置づけ: `attack-near 比較ケース`

### M4

- `100event = attack 1 / normal 99`
- pure model のまま mixed candidate set を作れている
- second pass でも third pass でも attack が完全には消えていない
- 位置づけ: `補助ケースとして最も使いやすい`

### M6

- first pass から attack が残っていない
- second pass / third pass でも回収できない
- これは third pass の失敗ではなく、upstream 側の difficulty を表している
- 位置づけ: `difficulty case`

### S4

- `100event = attack 1 / normal 99`
- M4 と同様に pure model で mixed candidate set を作れている
- ただし内容は M4 より background 寄り
- 位置づけ: `補助ケースとして十分成立`

## 7. M4 / S4 は補助ケースとして妥当か

結論として、`M4 / S4` は補助ケースとして採用してよい。

理由は 4 つある。

1. pure model で `100event` まで到達している
2. `attack` を完全には消していない
3. `normal 99` を残している
4. そのため、「異常候補集合の中から false positive 側を読む」という論理に沿っている

ここが重要で、`99 normal` のすべてがそのまま「説明しやすい業務ログ」ではない。

- `repwmiutils.exe 18`
- `sysmon.exe 17`
- `- 14`
- `spoolsv.exe 12`

#### M4 の event id 分布

- `4663 31`

- `4688 7`
- `4690 7`

#### S4 のプロセス分布

- `repmgr.exe 24`
- `vmtoolsd.exe 14`

- `- 13`

### 8.3 ユースケース化しやすさに対する意見

現時点の率直な見立てとしては次の通り。

#### M4

- `100event` 全体の normal 比率: `99%`
- そのうち「そのままユースケース本文の核にしやすい」割合: **`20%〜35%` 程度**
- そのうち「周辺文脈・補足として使いやすい」割合: **`40%〜60%` 程度**

読み:

- attack 汚染は薄い
- ただし normal の中心は `repmgr / repwmiutils / sysmon / spoolsv` なので、業務シナリオそのものより周辺運用文脈に寄る
- それでも、補助ケースとしては十分強い

#### S4

- `100event` 全体の normal 比率: `99%`
- そのうち「そのままユースケース本文の核にしやすい」割合: **`15%〜25%` 程度**
- そのうち「周辺文脈・補足として使いやすい」割合: **`45%〜60%` 程度**

読み:

- attack 汚染は同様に薄い
- ただし `vmtoolsd / tpautoconnsvc / searchprotocolhost` が目立つぶん、M4 より background 寄り
- そのため、補助ケースとしては使えるが、核の密度は M4 よりやや弱い

### 8.4 まとめ

- `M4`: 補助ケースとしてかなり良い
- `S4`: 補助ケースとして十分良いが、M4 より background 寄り

優先度としては

1. `M4`
2. `S4`
3. `S3`
4. `M6`

が自然。

## 9. 偽陽性ログを「あるある正常」と「ちょっと怪しい正常」に分けるとどう見えるか

ここでは `M4 / S4` の最終 `100event` のうち、attack 1件を除いた `99 normal` を次の 2 群に分けて読む。

- `あるある正常`
  - Windows / service / indexer / monitoring / VM 背景動作として説明しやすいもの
- `ちょっと怪しい正常`
  - normal ラベルではあるが、検索系・業務補助系・独自ユーティリティ系が混ざり、attack-near に見えやすいもの

この分類は、event 単体よりも意味のまとまりが出る `10 event micro-chunk` 単位で行った。

### 9.1 M4 の内訳

`100event = attack 1 / normal 99`

micro-chunk ごとの読み:

- `あるある正常`
  - rank 1: `sysmon.exe + csrss.exe`
  - rank 2: `vmtoolsd.exe + searchindexer.exe`
  - rank 5: `spoolsv.exe`
- `ちょっと怪しい正常`
  - rank 3: `searchprotocolhost.exe + searchfilterhost.exe + repmgr.exe`
  - rank 4: `repmgr.exe + repwmiutils.exe + sysmon.exe`
  - rank 6: `repmgr.exe + sysmon.exe + vmtoolsd.exe`
  - rank 7: `repmgr.exe + sysmon.exe`
  - rank 8: `repwmiutils.exe + searchfilterhost.exe`
  - rank 9: `repwmiutils.exe + spoolsv.exe`
  - rank 10: `repmgr.exe + sysmon.exe`

内訳:

- `あるある正常`: `3 micro-chunks = 30 event`
- `ちょっと怪しい正常`: `6 micro-chunks = 69 event`
- `attack`: `1 micro-chunk 内に 1 event`

割合イメージ:

- `あるある正常`: 約 `30%`
- `ちょっと怪しい正常`: 約 `69%`
- `attack`: 約 `1%`

読み:

- M4 は normal が多いが、その中でも **「完全に背景だけ」より「少し癖のある正常」が多数派**
- そのため、偽陽性ユースケースとしては「system background」より「一見怪しいが正常だった監査列」の代表例として使いやすい

### 9.2 S4 の内訳

`100event = attack 1 / normal 99`

micro-chunk ごとの読み:

- `あるある正常`
  - rank 1: `vmtoolsd.exe + searchindexer.exe + sysmon.exe`
  - rank 5: `sysmon.exe + vmtoolsd.exe + csrss.exe`
- `ちょっと怪しい正常`
  - rank 2: `tpautoconnsvc.exe + searchprotocolhost.exe`
  - rank 3: `repmgr.exe + searchprotocolhost.exe`
  - rank 4: `repmgr.exe + vmtoolsd.exe + searchprotocolhost.exe`
  - rank 6: `tpautoconnsvc.exe + searchprotocolhost.exe`
  - rank 7: `spoolsv.exe + repwmiutils.exe + repmgr.exe`
  - rank 8: `vmtoolsd.exe + repmgr.exe`
  - rank 9: `sysmon.exe + wmiprvse.exe`
  - rank 10: `repwmiutils.exe + repmgr.exe + sysmon.exe`

内訳:

- `あるある正常`: `2 micro-chunks = 20 event`
- `ちょっと怪しい正常`: `7 micro-chunks = 79 event`
- `attack`: `1 micro-chunk 内に 1 event`

割合イメージ:

- `あるある正常`: 約 `20%`
- `ちょっと怪しい正常`: 約 `79%`
- `attack`: 約 `1%`

読み:

- S4 は M4 よりさらに **「ちょっと怪しい正常」寄り**
- `tpautoconnsvc.exe` や `searchprotocolhost.exe` を含む列が多いため、背景動作でも analyst 目線では気になりやすい
- そのぶん、「偽陽性として実際に人が悩みそうなケース」の補助例としてはむしろ良い

### 9.3 全体の解釈

`M4 / S4` をまとめて言うと、

- 完全な `あるある正常` だけを抽出したわけではない
- むしろ **normal ラベルだが、監査列としては少し気になるもの** が多く残っている

これは今回の目的にかなり合っている。

なぜなら、取りたいのは

- ただの benign background 全部

ではなく、

- **anomaly ranking 上位に来た中で、それでも false positive 側として読める正常文脈**

だからである。

したがって、

- `M4 / S4` は「偽陽性ログの中でも、あるある正常と少し怪しい正常の両方を含む補助ケース」

と整理するのが最も自然である。

## 10. 正常復元のために、どの正常をユースケース化すべきか

ここで大事なのは、`normal 99` をそのまま全部ユースケース候補にすることではない。  
実務で欲しいのは、

- 監視上かなり普通すぎて誰も見ない正常

ではなく、

- **anomaly ranking 上位に来て実際に analyst が確認しそうだが、調べると正常だったもの**

である。

そのため、ユースケース候補の選定基準を次のように置く。

### 10.1 選定基準

#### 採用する正常

次を満たすものを採用候補とする。

1. `third pass top10 micro-chunk` に入っている
2. `attack_events = 0` または `1/9` 程度の軽い混在で、normal 主体である
3. analyst が見たときに
   - file access の連打
   - delete / close / process creation の混在
   - search / indexing / management / service 系プロセスの組み合わせ
   のため一度は気になる
4. 単なる単一プロセスの無意味な背景ノイズではなく、少なくとも
   - 2 つ以上のプロセス
   - または `4656 / 4663 / 4658 / 4660 / 4688 / 4690`
   のような監査列のまとまり
   が見える
5. 親 `100 event chunk` 側でも比較的上位にあり、局所ノイズでなく周辺文脈の支えがある

#### 採用しない正常

次のようなものは、normal でもユースケース核には採らない。

1. `sysmon.exe / csrss.exe` だけの短い断片
2. 背景プロセス 1 本だけで完結し、業務的な意味づけが弱いもの
3. analyst 目線で「確認する価値がある正常」ではなく、ただの ubiquitous background に近いもの

### 10.2 選定方針

この基準に従うと、ユースケース化に向くのは

- `あるある正常`

よりも、

- **ちょっと怪しい正常**

の方である。

理由は、今回の研究目的が

- 正常をそのまま一般論として列挙すること

ではなく、

- **異常候補上位に来たのに false positive だった正常文脈を復元すること**

だからである。

## 11. 最終 400ログ全体から見た選定手順

ここからは、`M4 / S4` の個別観察だけでなく、**最終 400ログ全体を母集団として、どの正常ログを実務上の解析対象として残すか** を順に決める。

ここでの `400ログ` は

- `S3 100`
- `M4 100`
- `M6 100`
- `S4 100`

を合算したものである。

### 11.1 最終 400ログの主要プロセス

上位プロセス分布は次の通り。

| process | count | attack label |
| --- | ---: | --- |
| `repmgr.exe` | `86` | all normal |
| `sysmon.exe` | `68` | all normal |
| `-` (`4688/4690` など process なし) | `57` | all normal |
| `repwmiutils.exe` | `41` | all normal |
| `vmtoolsd.exe` | `27` | all normal |
| `spoolsv.exe` | `26` | all normal |
| `tpautoconnsvc.exe` | `25` | all normal |
| `searchprotocolhost.exe` | `20` | `18 normal / 2 attack` |
| `csrss.exe` | `19` | all normal |
| `svchost.exe` | `10` | all normal |
| `searchindexer.exe` | `9` | all normal |
| `services.exe` | `5` | all normal |
| `wmiprvse.exe` | `4` | all normal |
| `searchfilterhost.exe` | `3` | all normal |

この表から分かるのは、

1. 最終 400 のかなりの割合は background / OS 基盤プロセスで占められている
2. それを外したあとに、`repmgr / repwmiutils / tpautoconnsvc / spoolsv / searchprotocolhost / searchfilterhost / wmiprvse` が「確認価値のある正常」候補として残る
3. `searchprotocolhost.exe` だけは `normal 18 / attack 2` の混在で、明確な境界候補になっている

### 11.2 まず外す「ほぼ確定背景」

最終 400 の中には、実務上「ユースケース核にしない」方がよいログがかなりある。

#### A. 背景・監視・OS 基盤

- `sysmon.exe`
- `csrss.exe`
- `svchost.exe`
- `services.exe`
- process 名が空の `4688 / 4690`

理由:

1. 件数は多いが、ほぼ background / OS 基盤の補助監査である
2. analyst が単体でこれだけを見て「復元したい正常ユースケース」とは置きにくい
3. 今回の目的は ubiquitous background の列挙ではなく、**異常候補上位に来て確認を要する正常** の復元である

- `searchindexer.exe`

理由:

2. ただし単独では `VM 補助` や `検索索引更新` の背景動作に寄りやすい
3. 主役ログとして採るより、他の気になる 1ログの周辺文脈として使う方が自然

### 11.3 残す「怪しい正常候補」

上を引いたうえで、最終 400 から残すべき候補は次である。

#### 主たる正常候補

### 11.4 1ログ主体での候補化ルール

ここから先は、`A + B + C` のような複数ログの束をそのままユースケース名にしない。  
代わりに、

1. **対象 1ログ** を先に決める
2. その前後 `10 event micro-chunk` を周辺文脈として使う
3. 親 `100 event chunk` の順位を、その 1ログの「周辺支持」として使う

という形にする。

つまり、今回ユースケース化したいのは

- `searchprotocolhost.exe + searchfilterhost.exe`

の束そのものではなく、

- `searchprotocolhost.exe の EventID=4663 file access`
- `searchfilterhost.exe の EventID=4663 file access`

のような **対象 1ログ** である。  
周辺のログ列は、その 1ログがなぜ正常に読めるかを説明するための材料に回す。

## 18. なぜその attack だけが残って、他は落ちたのか

ここは大きく 3 つに分けて説明できる。

### 18.1 attack label 自体が非常に疎だから

`M4 / S4` の second pass review set はそれぞれ

- `M4`: `3000 event` 中 `attack 1`
- `S4`: `3000 event` 中 `attack 3`

だった。

つまり third pass に入る時点で、attack はすでにごく少数しか残っていない。  
そのため、`100event` までさらに詰めると、attack が消える圧力が非常に強い。

### 18.2 残った attack が「normal に埋め込まれた audit triplet」だったから

残った 2 件はどちらも、単独で強烈に異質な event というより

- `4656`
- `4663`
- `4658`

の file access 監査列の中に埋まっていた。

つまり、

- 周囲が完全に別種の異常ログだったから残った

のではなく、

- **normal に近い塊の中に attack-labeled event が 1 件だけ混ざっていたため、その micro-chunk 全体が完全な benign でも完全な attack でもない「境界的な塊」になった**

と考えるのが自然である。

### 18.3 third pass は event 単体ではなく micro-chunk 全体を見ているから

third pass の `kNN` は、1件1件の event ではなく `10 event micro-chunk` 全体を正常 micro-chunk 分布と比較している。

そのため残った理由は、

- その 1 件の attack event 単体が強かった

というより、

- その 10event の並び全体が benign 側から少し浮いた
- しかも attack event を 1 件だけ含んでいた

ということになる。

特に `M4 chunk068` と `S4 chunk010` は、second pass の時点でも attack を含む `100 event chunk` として上位に残っていた。  
そこからさらに micro-chunk 化したときに、その parent chunk の中で比較的スコアが高い 10event が最終 `top10` に入った、という流れである。

## 19. 逆に、他の attack が落ちた理由

他の attack が落ちた理由は、単に「attack だから残る」ような検知ではなかったからである。

今回のモデルは教師ありで attack を直接覚えたわけではなく、

- 正常分布から外れているか
- その並びが benign に対してどれくらい珍しいか

で順位付けしている。

そのため、

- attack でも benign にかなり近い並びなら落ちる
- normal でも benign から外れた rare pattern なら上に来る

ということが起きる。

今回の `S3` で `100event` に attack が残らなかったのも、`M4 / S4` で attack が 1 件しか残らなかったのも、この ranking の性質から自然に説明できる。

## 20. このフェーズを完了とする理由

このフェーズで本来確認したかったのは、

1. model-only でどこまで圧縮できるか
2. attack を残しつつ false positive も残せるか
3. usecase 候補へ接続できるか

の 3 点だった。

今回の結果で、

- `3000event` までは model-only で十分成立
- `100event` も `M4 / S4` では成立
- `M6` は限界例としてきれいに残る

ところまで確認できたので、抽出フェーズとしては十分に区切りがよい。
