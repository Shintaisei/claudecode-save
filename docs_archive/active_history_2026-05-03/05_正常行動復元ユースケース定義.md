# 正常行動復元ユースケース定義
更新日: 2026-05-03

## 1. この文書の目的

本研究の最終ゴールは、異常検知で浮いた対象に対して `攻撃 / 正常 / 決めきれない` を判断できるようにすることである。
ただし現在の主対象はその前段であり、まずは **正常事象でも、起点アラートを手がかりに関連ログ探索が成立し、行動復元まで到達できるか** を検証する。

この整理は、`0417_網屋資料確認_小松崎.pdf` の問題設定を ATLAS v2 実験に接続するためのものである。特に以下を明確化する。

1. 実務では最初に何を入力とみなすか
2. 現在の ATLAS v2 実験では何シーケンスあり、そのうちどれが攻撃を含むか
3. 今回の研究で扱うユースケースは何か
4. 正常行動復元では、どこまで関連ログとして洗い出すのが妥当か
5. 最初の行動復元実験をどう定義するか

## 2. 実務での入力と今回の位置づけ

### 2.1 実務で最初に見るもの

実務の SOC / DFIR では、分析者は生ログ全体から始めるのではなく、まず **異常と判断されたアラートや異常候補** を受け取る。
その後に、

1. 仮説の策定 / 更新
2. スコープ決定
3. 検索・収集
4. 絞り込み
5. 行動復元
6. 攻撃 / 正常の判断

を繰り返す。

したがって、本研究の第一段階も「正常ログ全体のモデリング」ではなく、**異常として上がってきた候補から正常行動復元が成立するか** を問う形に揃える。

### 2.2 今回の研究で扱うユースケース

今回のユースケースは次のように定義する。

- 入力:
  異常検知で浮いたアラート、またはその周辺シーケンス
- 目的:
  その候補が攻撃か正常かをすぐに断定することではなく、まず関連ログ探索が成立して正常行動を再構成できるかを確かめる
- 出力:
  `復元成立 / 復元不成立 / 保留`
  と、成立時には主体・行為・対象・連鎖の要約

つまり現在の主課題は **判定器の完成** ではなく、**正常事象に対しても探索と行動復元が成立する条件の特定** である。

## 3. ATLAS v2 で今見ているシーケンス

### 3.1 実務寄りに使う 2 段構え

現在の ATLAS v2 実験では、実務寄りの first pass / second pass として次の 2 種類のシーケンスを使っている。

1. `computer_user + 10分`
   同一ホスト・同一ユーザーの 10 分単位でまとめる broad sweep。
   まず「どの時間帯 / ユーザー帯を見るべきか」を荒く出す。

2. `computer_process + 10分`
   同一ホスト・同一プロセスの 10 分単位でまとめる triage sweep。
   次に「どのプロセス主体を見るべきか」を絞る。

この 2 段構えは、実務でいきなりプロセス一点に閉じず、まず利用者・時間帯で範囲を見てから主体を絞る流れに近い。

### 3.2 シナリオごとのシーケンス数と攻撃包含数

ATLAS v2 の各 attack day を `10分` で切ったときのシーケンス数は以下の通り。

| Scenario | `computer_user + 10分` 総数 | 攻撃を含む | 攻撃を含まない | `computer_process + 10分` 総数 | 攻撃を含む | 攻撃を含まない |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| S3 | 23 | 3 | 20 | 137 | 8 | 129 |
| S4 | 19 | 6 | 13 | 128 | 14 | 114 |
| M4 | 18 | 6 | 12 | 124 | 13 | 111 |
| M5 | 19 | 5 | 14 | 155 | 11 | 144 |
| M6 | 18 | 6 | 12 | 129 | 14 | 115 |

読み方は次の通り。

- `computer_user + 10分` は 1 日を 18 から 23 個程度の大きめな利用者単位シーケンスとして扱う
- `computer_process + 10分` は 1 日を 124 から 155 個程度の細かい主体単位シーケンスとして扱う
- 攻撃を含むシーケンスは少数であり、多くは攻撃を含まない

このため、実務で最初に broad sweep をかけると「数十ではなく十数個から二十数個の利用者・時間帯候補」を見る構図になり、その後 triage に進むと「百数十個の process session から攻撃を含みうる少数候補を絞る」構図になる。

### 3.3 1シーケンスあたりのデータ量

各 attack day 全体を単純平均したときの 1 シーケンスあたりイベント数は以下の通り。

| Scenario | `computer_user + 10分` 平均 event 数 | `computer_process + 10分` 平均 event 数 |
| --- | ---: | ---: |
| S3 | 11,212 | 1,882 |
| S4 | 12,176 | 1,807 |
| M4 | 11,112 | 1,613 |
| M5 | 16,606 | 2,036 |
| M6 | 12,270 | 1,712 |

大づかみに言うと、

- `computer_user + 10分` は 1 シーケンスあたり約 `1.1万` から `1.7万 event`
- `computer_process + 10分` は 1 シーケンスあたり約 `1,600` から `2,000 event`

である。

さらに、実務で実際に first pass / second pass として見る上位候補では次の程度になる。

| Scenario | broad top10 の平均 event / session | triage top10 の平均 event / session |
| --- | ---: | ---: |
| S3 | 20,979 | 1,704 |
| S4 | 22,413 | 3,375 |
| M4 | 16,272 | 1,352 |
| M5 | 30,621 | 3,204 |
| M6 | 19,808 | 1,984 |

つまり broad は「かなり太い利用者・時間帯単位の塊」を見ており、triage に落とすことで「数千 event 規模の主体単位」まで絞れている。

## 4. 実務で実際に見る候補数の解釈

### 4.1 broad sweep の役割

`computer_user + 10分` の局所逸脱スコアでは、上位 `top10` session で攻撃を含む anomalous window の多くを回収できた。

| Scenario | broad `top10` の TP-window coverage |
| --- | ---: |
| S3 | 100.0% |
| S4 | 98.1% |
| M4 | 100.0% |
| M5 | 96.1% |
| M6 | 91.1% |

したがって broad sweep は、

- 最初に見る候補数を `10` から `20` session 程度に抑える
- その中で怪しい時間帯とユーザー帯を取りこぼしにくく把握する

用途に向いている。

### 4.2 triage sweep の役割

`computer_process + 10分` は、`repmgr.exe`、`svchost.exe`、`firefox.exe`、`-` を慢性的ノイズとして除外した後でも、`top10` 固定では取りこぼしが残る。

| Scenario | triage `top10` | triage `top20` | triage `top50` |
| --- | ---: | ---: | ---: |
| S3 | 73.0% | 95.2% | 100.0% |
| S4 | 57.1% | 93.5% | 100.0% |
| M4 | 54.2% | 93.8% | 100.0% |
| M5 | 66.1% | 66.1% | 96.8% |
| M6 | 54.5% | 89.1% | 100.0% |

そのため triage は、

- `top10` を固定ルールにしない
- `top20` を標準、見落とし重視なら `top50` まで伸ばす

運用が自然である。

ただし `M5` では `top10` から `top20` に広げても coverage が改善しなかった。
このことから、`top20` は万能なしきい値ではなく、シナリオによっては `top50` まで見て初めて十分な回収率になる点も押さえておく必要がある。

### 4.3 実務での見え方

要するに、今回の方式で分析者が最初に見るのは次の二段構えになる。

1. broad sweep:
   1 日の中から `10` から `20` 個程度の user-time session を first pass として確認する
2. triage sweep:
   その後、`20` から `50` 個程度の process session を確認し、主体を絞り込む

ここで重要なのは、**最初から攻撃を含むシーケンスだけが渡るわけではない** ことだが、これは実務にも近い。
実務でも最初に渡るのは「異常として浮いた候補」であり、攻撃を含むものと含まないものが混在する。

## 5. 今回の正常データは何由来か

候補 session の正常部分を集計すると、ほぼすべてが `Security` チャネルの `microsoft-windows-security-auditing` 由来だった。
主要 Event ID は以下が中心である。

- `4656`
- `4658`
- `4663`
- `5156`
- `5158`
- `4660`
- 一部 `4688`, `4689`

つまり本研究で今扱っている「正常」は、業務全体を完全再現した正常ではなく、**Windows Security ログ上に現れる正常文脈** である。
さらに候補 session に現れた主体を見ると、`firefox.exe`、`winword.exe`、`explorer.exe`、`wmiprvse.exe`、`powershell.exe`、`mmc.exe`、`services.exe` などが混ざる。

このため今回の実験は、次のように位置づけるのが正確である。

- 扱う対象:
  Windows Security ログ上の正常文脈
- まだ扱えていないもの:
  業務アプリ全体の意味理解や、端末外部まで含めた完全な業務行動復元

研究目的としては十分妥当だが、論文や発表では「正常業務全体」ではなく **Security 監査上の正常行動復元** と明記したほうがよい。

## 6. 正常行動復元でどこまで関連ログを洗うか

### 6.1 基本方針

正常行動復元では、関連ログの収集範囲を広げすぎると背景動作が大量に混ざり、逆に狭すぎると連鎖が切れる。
そのため、最初から全ログを取りにいくのではなく、次の 3 層で段階的に広げるのがよい。

### 6.2 収集範囲の 3 層

#### レベル 1: 最小復元範囲

起点アラートと同じ

- ホスト
- 主要主体
  `user` または `process`
- 同一 10 分バケット

を対象にする。

ここでは **起点アラートを中心に主体・対象・主要動作が見えるか** を確認する。
単発操作型の正常行動は、この範囲で復元成立するのが望ましい。

#### レベル 2: 連鎖確認範囲

レベル 1 で足りない場合に、次を追加する。

- 直前 10 分
- 直後 10 分
- 同一プロセス名、同一ユーザー、同一端末で連続する session
- `4688/4689` などのプロセス生成・終了
- 同一ファイル、同一オブジェクト、同一接続先に結びつく監査イベント

ここでは **操作の前後関係や手続のまとまりが追えるか** を確認する。
手続型の正常行動は、この範囲まで広げて初めてまとまりが見えることが多い。

#### レベル 3: 背景分離範囲

それでも境界が不明瞭な場合に限って、次を追加する。

- 同一ホスト上の近接時間帯で反復する system / service 系イベント
- ベースライン上で慢性的に多い process
- 常駐・周期ジョブの周辺ログ

ここでは「拾う」のではなく **背景動作として分離する** ことが目的になる。
背景動作型は、広げるほど復元しやすくなるのではなく、背景と本体の分離が必要になる。

### 6.3 どこで止めるか

関連ログの探索は、以下のいずれかを満たしたら打ち切るのが妥当である。

1. 主体・行為・対象・前後関係が説明できる
2. 新しく追加したログが行動の意味を増やさず、背景ノイズだけ増やす
3. 起点アラートから離れすぎて、同一行動と見なす根拠が弱くなる

この打ち切り条件を入れないと、正常行動復元は背景動作の回収実験に崩れやすい。

## 7. 正常行動の複雑さと復元方針

PDF の整理に合わせ、正常行動は次の 3 類型で扱うのがよい。

### 7.1 単発操作型

例:
`Web閲覧`、`添付取得`

特徴:

- 境界が比較的明瞭
- 主体と対象を切り出しやすい
- レベル 1 からレベル 2 で復元成立しやすい

評価観点:

- 起点アラートだけでどこまで狭まるか
- 同一 10 分バケット内で主要主体が追えるか

### 7.2 手続型

例:
`メール受信 → 添付取得 → 文書閲覧`
`Webアクセス → ファイル取得 → 参照`

特徴:

- 複数操作が連なっている
- 境界はやや曖昧だが、まとまりとしては追いやすい
- レベル 2 まで広げて前後関係を見る必要がある

評価観点:

- 起点から前後の関連操作へ枝を伸ばせるか
- 主体・対象・手順の連鎖として要約できるか

### 7.3 背景動作型

例:
`SearchIndexer`、`OSメンテナンス`

特徴:

- 常駐・周期・副作用が混ざる
- 境界も主体も切りにくい
- レベル 3 で背景分離が必要

評価観点:

- 追えたかどうかより、背景から切り分けられるか
- どこで探索を止めるべきかを説明できるか

## 8. 最初の行動復元実験の定義

### 8.1 実験の主題

最初の行動復元実験は、**正常行動の複雑さと起点アラートの特異性に応じて、探索が成立するか / 不成立かを判定する実験** とする。

軸は 2 つ。

1. 起点アラートの特異性
   `高特異性 / 中特異性 / 低特異性`
2. 正常行動の複雑さ
   `単発操作型 / 手続型 / 背景動作型`

これにより、`3 x 3` の実験表を作る。

### 8.2 成立 / 不成立の判定基準

#### 成立

以下を満たすとき、復元成立とする。

1. 起点アラートから探索対象を現実的な範囲に絞れる
2. 関連ログを追加しても、主体・行為・対象・連鎖の説明が改善する
3. 最終的に正常行動のまとまりとして説明できる

#### 不成立

以下のいずれかを満たすとき、不成立とする。

1. 起点が低特異すぎて候補が拡散する
2. 関連ログを増やしても背景ノイズしか増えない
3. 連鎖の途中で主体・対象・境界が失われ、行動としてまとまらない

#### 保留

復元は部分的にできるが、正常と断言するには情報が足りない場合は保留とする。

### 8.3 実験の入口として使う候補

ATLAS v2 上では、起点候補の抽出に次を使うのが自然である。

1. broad sweep:
   `computer_user + 10分` の上位 candidate session
2. triage sweep:
   `computer_process + 10分` の上位 candidate session

このとき broad は「どの時間帯・利用者帯を見るか」、triage は「どの主体を起点に復元を始めるか」の入口として使う。

## 9. 現時点の推奨ユースケース

現時点で最も筋が良いユースケースは次の形である。

1. ATLAS v2 の attack day に対して異常候補を出す
2. `computer_user + 10分` で broad sweep し、`top10` から `top20` の user-time session を first pass にする
3. `computer_process + 10分` で triage し、`top20` を基本、必要なら `top50` まで見る
4. その中から正常寄り候補を選び、起点アラートの特異性と正常行動の複雑さで分類する
5. レベル 1 からレベル 3 の探索範囲を順に広げ、復元成立 / 不成立 / 保留を判定する

この流れなら、最終ゴールである攻撃 / 正常判定に直結する前段として、**正常行動復元がどこで成立し、どこで崩れるか** をかなり実務に近い形で測れる。

## 10. `太めに検知して、100 event 前後で復元する` 方式は有効か

### 10.1 結論

結論として、この二段構えは **正常行動を抽出するための方式として有効** である。
ただし、有効なのは「最初から 100 event 単位で検知する」ことではなく、

1. まず太めの process session で候補を取りこぼしにくく拾う
2. その上位候補だけを 100 event 前後へ再分割して読む

という役割分担をした場合である。

### 10.2 なぜ最初から 100 event 単位ではだめか

`computer_process + 1分 + 100 event chunk` まで薄くすると、候補 1 本あたりのサイズはほぼ狙い通りになった。
top10 candidate の平均サイズは `80` から `97 event` 程度で、分析者が読みやすい。

しかしその代わり、attack 文脈まで細切れになり、top10 coverage は大きく落ちた。

- `S3`: `31.3%`
- `S4`: `18.5%`
- `M4`: `0.0%`
- `M5`: `18.5%`
- `M6`: `37.3%`

つまり、**100 event 前後の粒度は「読む単位」としては良いが、「最初に異常候補を拾う単位」としては細すぎる**。

### 10.3 なぜ二段構えなら有効か

一方で、`computer_process + 10分` や `computer_process + 1分` のような太めの session で first pass を行うと、
見落としを抑えながら候補を出せる。

その後に上位候補だけを `100 event` 前後へ chunk すると、

- 候補抽出段階では attack 文脈を保てる
- 行動復元段階では人が読める大きさまで落とせる
- chunk 内の正常イベント比率も依然として高く、正常文脈を多く含んだまま読める

という両立ができる。

したがって、この方式で期待しているのは

- `正常そのものを最初から直接検知する` ことではなく
- `異常候補として上がった太めの session の中から、正常文脈を保ったまま読める復元単位を切り出す` こと

である。

### 10.4 何をもって「正常行動を抽出できた」とみなすか

この方式では、正常行動の抽出成功を次のように定義するのが妥当である。

1. first pass の太め session が、起点アラート周辺の行動全体を取りこぼさずに含む
2. second pass の `100 event` 前後 chunk に分けることで、主体・行為・対象・前後関係を人が追える
3. その chunk 群をたどることで、正常行動を `単発操作型 / 手続型 / 背景動作型` のどれかとして説明できる

この意味での「抽出」は、単一 chunk だけで正常を断言することではなく、
**太め候補から復元に必要な正常文脈を持つ塊を切り出せること** を指す。

### 10.5 今回の研究における位置づけ

この二段構えは、最終ゴールの `攻撃 / 正常 / 決めきれない` 判定の前段として自然である。

- 第一段階:
  太め session から正常行動復元が成立するかを検証する
- 第二段階:
  復元した結果を基に、攻撃 / 正常 / 保留を判断する

つまり今の研究では、

- 検知器そのものを 100 event 最適化する
のではなく、
- **検知で上がった候補を、復元可能な正常文脈へどう切り直すか**

が主題になる。

## 11. 二段構えで取れた正常行動は研究に使えるか

### 11.1 結論

結論として、**実務寄りの二段構えで取れた正常行動は、今回の研究の第一段階に十分使える**。

ここでいう「使える」とは、

- 起点アラートから探索を始める
- 関連ログを集める
- 正常行動として復元できるかを評価する

という目的に対して、材料として妥当であることを指す。

### 11.2 使える理由

今回の候補は、太めの session でまず文脈を保ち、その後 `100 event` 前後に切り直して読む構造になっている。
このため、次の 3 点が成立している。

1. **起点アラート起点の探索に近い**
   実務と同じく、最初に見るのは生ログ全体ではなく異常候補である。
   そのため、研究の入口が実務フローに沿っている。

2. **正常文脈を大量に含んだ候補になっている**
   これまでの上位候補 session は大半が正常イベントで構成されており、
   「異常だけの塊」ではなく「正常の中に少量の異常や違和感が混ざる候補」になっている。

3. **人が読める大きさまで落とせる**
   first pass のままだと太いが、second pass で `100 event` 前後に区切ることで、
   主体・行為・対象・前後関係を読める単位へ落とせる。

つまり、今回の候補は

- 実務入力に近い
- 正常文脈を含む
- 復元可能なサイズに落とせる

という意味で、研究の第一段階にかなり合っている。

### 11.3 何の研究材料として使えるか

今回の正常行動候補は、特に次の研究材料として使いやすい。

1. **正常行動復元の成立性評価**
   起点アラートから出発して、どこまで関連ログをたどれば正常行動として説明できるかを測る。

2. **正常行動の類型化**
   `単発操作型 / 手続型 / 背景動作型` のどれに当たるかを整理する。

3. **起点アラートの特異性評価**
   `高 / 中 / 低` 特異性のどこから始めると復元が成立しやすいかを比較する。

4. **攻撃 / 正常判定の前段データ**
   後段で `攻撃 / 正常 / 保留` を考えるときの、正常側の復元事例として使う。

### 11.4 逆に、そのままでは使いにくい点

一方で、次の点は明確に限界として残る。

1. **Windows Security ログ由来に偏っている**
   主体は `firefox.exe`、`winword.exe`、`powershell.exe` など多様だが、
   ログ基盤は主に `4656/4658/4663` を中心とした Security 監査である。

2. **正常業務全体の再現ではない**
   今回使えるのは「業務全体の意味理解」より、
   「Security 監査上に現れた正常文脈」の復元である。

3. **候補抽出と最終判定はまだ別問題**
   今回の方式は正常行動復元には向くが、
   そのまま最終判定器になっているわけではない。

したがって、研究では

- 「正常業務全体の代表サンプル」と主張するのではなく
- **異常候補から復元される Security 監査上の正常行動サンプル**

として使うのが適切である。

### 11.5 実務と研究の接続としての意味

実務でも、

1. まず広めに異常候補を取る
2. 次にその中を詳細確認する

という二段構えは自然である。

今回の方式はちょうどそれに対応していて、

- first pass:
  見落としを抑えて候補を取る
- second pass:
  読めるサイズにして正常行動復元を行う

という分担になっている。

このため、研究としても

- データの切り方が実務から乖離していない
- 復元対象が実務の false positive 解析に近い
- 後段の attack / normal 判断へつながる

という意味で、かなり素直な設計になっている。

### 11.6 現時点の判断

現時点では、次のように判断するのが妥当である。

- **採用してよい**
  今回の二段構えで取れた正常行動候補は、正常行動復元の研究材料として十分使える
- **ただし表現は正確にする**
  「正常行動一般」ではなく「異常候補から切り出された Security 監査上の正常文脈」として扱う
- **次に必要なのは事例化**
  実際に候補を `単発操作型 / 手続型 / 背景動作型` へ落として、復元成立例を積む

## 12. この文書から次にやること

1. broad / triage の上位候補から、正常行動候補を `単発操作型 / 手続型 / 背景動作型` に仕分ける
2. それぞれに対して `高 / 中 / 低` 特異性の起点アラート候補を選ぶ
3. `3 x 3` 実験表を作る
4. 各マスで、レベル 1 からレベル 3 の探索で復元成立するかを評価する

これが、現在地点から最終ゴールへ向かう最も自然な第一段階である。
