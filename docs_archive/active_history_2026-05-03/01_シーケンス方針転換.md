# シーケンス方針転換

作成日: 2026-05-03

## 1. この文書の目的

これまでの研究メモが `docs/` に多く蓄積され、今どの方針で進めるかが見えにくくなってきた。
そのため、この文書では「今ここから何をするか」を一枚で整理する。

## 2. 現状認識

これまでの検討では、主に以下の流れで進めていた。

1. 単一のログや単一のアラートを起点として見る
2. そこから関連ログをたどる
3. 偽陽性候補の正常ログや正常行動の説明可能性を調べる

この方針で得られた重要な知見は次の通り。

- 単一ログだけでは、偽陽性として使いやすい正常 seed が十分に取れない
- non-info の FP は、環境由来や攻撃隣接のものが多い
- 実際には、単発イベントよりも前後関係、連鎖、時系列を見た方が意味がある
- すでに研究メモの中でも、`ProcessGuid` や前後イベントを使った連鎖復元が中心になっている

つまり、研究の実態はすでに「イベント単位」より「系列単位」に寄っている。

## 3. 方針転換の要点

今後は、単一ログから正常ログを作ろうとする方向よりも、
**シーケンス単位で見て、そこから異常を扱う方向**に寄せる。

ここでのシーケンスとは、例えば以下のようなまとまりを指す。

- 親子プロセス関係を含むプロセス列
- ある時刻窓の中にある一連のイベント列
- ある主体が行った行為の連鎖
- 攻撃または異常としてまとまりを持つイベント列

## 4. 新しい主行動フロー

今後のメインの行動フローは次の4段階とする。

1. シーケンスモデルを調査する
2. GitHub から使えそうな実装を導入する
3. 手元データへ適用できる形に合わせる
4. 異常シーケンスの中に、どれくらい正常成分が含まれていそうかを調べる

## 5. 具体的に何を調べるか

### 5.1 シーケンスモデル調査

調査対象は、ログやイベント列を扱えるモデル・手法を優先する。

主な観点:

- 入力がイベント列か、集計特徴量か
- 可変長シーケンスを扱えるか
- 異常検知向けか、生成向けか、分類向けか
- GitHub 上で再現可能な実装があるか
- Windows イベントログや Sysmon に近い形式へ適用しやすいか
- 学習済みモデル前提か、ゼロから学習か
- 正常/異常の混在系列をどう扱う設計か

候補のイメージ:

- Transformer 系
- LSTM / GRU 系
- オートエンコーダ系シーケンスモデル
- 予測誤差ベースの異常検知モデル
- ログ専用表現学習モデル

### 5.2 GitHub 実装の導入

モデルは原則として、まず既存実装を使う。

理由:

- 研究の主眼を「実装そのもの」ではなく「シーケンスとして異常を扱えるか」に置ける
- 比較候補を増やしやすい
- 再現性の説明がしやすい

導入時の確認項目:

- ライセンス
- 最終更新状況
- 必要依存関係
- 入出力形式
- 学習に必要な最小データ量
- 推論だけでも試せるか

### 5.3 手元データへの適用

既存データを、そのままイベント単位で入れるのではなく、シーケンス化して渡すことを前提にする。

想定する前処理:

- イベントの時系列整列
- 主体単位またはプロセス単位の系列化
- 時間窓での分割
- Event ID、Process、User、Path、Network などのトークン化
- 長すぎる系列の切り方の設計
- 学習用・評価用の分割

最初の適用候補:

- apt-persistence の Sysmon / Security
- 必要に応じて ATLASv2 の変換済みデータ

## 6. 中心課題

この方針で一番見たいのは、
**異常シーケンスは本当に全面的に異常なのか、それとも正常行動をかなり含んだ混合列なのか**
という点である。

ここで見るべき問い:

- 異常シーケンスの中で、異常に直接対応するイベントはどのくらいか
- 残りの大半は正常な背景行動ではないか
- モデルは「異常イベント単体」を見ているのか、「異常を含む文脈全体」を見ているのか
- 異常ラベル付き系列でも、内部は正常イベント優勢になっていないか

## 8. 既存方針との関係

以前の「起点アラートから関連ログをたどる」という知見は無駄にならない。
むしろそれは、シーケンス設計の土台として活かせる。

活かせる点:

- どのイベント同士を関連づけるべきか
- どの粒度で系列を切るべきか
- 正常と異常が混ざる箇所はどこか
- 説明可能な連鎖とは何か

一方で、研究の主軸は次のように変わる。

- 以前: 偽陽性候補の単発ログや起点アラートをどう使うか
- 今後: シーケンス全体をどう表現し、異常系列の中の正常成分をどう見るか

## 9. 今やらないこと

当面は次を主目的にしない。

- 単一ログだけを対象にした seed 探し
- いきなり独自モデルをゼロから実装すること
- すべてのデータセットへ一気に広げること

まずは、少数の有望モデルを既存実装から試し、
手元データに載るかどうかを確認する。

## 10. 次の着手順

次にやる作業は以下の順番にする。

1. GitHub で使えそうなシーケンスモデル候補を集める
2. 3件から5件程度に絞って比較表を作る
3. そのうち 1件をローカルに導入する
4. apt-persistence を対象に、最小限のシーケンス化前処理を設計する
5. 異常シーケンスに正常成分がどれくらい混ざるかを見るための観察単位を決める
