# モデルオンリー圧縮フロー詳細 M4/S4評価付き

## 1. この段階で言いたいこと

今回の整理で言えることは 2 つある。

1. `数万 event -> 3000 event` までは、`rule-based` を使わずに pure model で圧縮できた
2. `3000 event -> 100 event` も pure model で試した結果、`M4 / S4` はかなり使えるが、`S3` は 100event まで詰めると attack が落ちやすく、`M6` は difficulty case として残る

このため、現時点の最も自然な標準フローは次である。

- first pass: `10分 sequence-level IsolationForest`
- second pass: `100 event chunk-level IsolationForest`
- third pass: `10 event micro-chunk-level kNN`

ただし、この third pass は全 scenario を完璧にそろえて通すところまではまだ行っていない。  
それでも `M4 / S4` については、`attack を少し含んだ 100event` を pure model で作れているので、ユースケース化の入口としては十分に強い。

### 2.1 学習側

## 3. first pass: 数万 event 規模まで圧縮

ここでは `10分 sequence-level IsolationForest` を使う。  
重要なのは、最初から個別 event に点数を付けているのではなく、まず `sequence` に対して異常スコアを付けている点である。

first pass の結果として残った predicted positive sequence は次。

| scenario | predicted sequences | predicted events | predicted attack events | predicted normal events |
| --- | ---: | ---: | ---: | ---: |
| `S3` | `2` | `42,301` | `5` | `42,296` |
| `M4` | `4` | `75,223` | `20` | `75,203` |
| `M6` | `3` | `69,811` | `0` | `69,811` |
| `S4` | `3` | `67,992` | `13` | `67,979` |

読み:

- `S3 / M4 / S4` は first pass の時点で attack を含む sequence が残っている
- `M6` は first pass から attack が残っておらず、ここが downstream の限界をかなり決めている

## 4. second pass: 100event chunk で 3000event まで圧縮

### 4.1 方法

first pass で残った sequence の内部だけを対象にして、`100 event chunk` に切る。  
その chunk にもう一度異常スコアを付けて、`top30 chunk = 3000 event` を review set とする。

ここでは次を比較した。

- `IsolationForest`
- `LOF`
- `One-Class SVM`
- `SGD One-Class SVM`
- `kNN`

### 4.2 結論

採用したのは `chunk-level IsolationForest`。

理由:

- `M4` と `S4` で `top10 chunk` の時点で attack を残せた
- `S3` も `top30 chunk = 3000 event` なら attack を残せた
- `LOF / OCSVM / SGD-OCSVM` は attack を前に出せなかった
- `kNN` は一部では悪くないが、second pass 全体では `IF` ほど安定しなかった

詳細は [3000event_純モデルsecondpass比較_2026-05-20.md](/c:/Users/komat/OneDrive/Desktop/ATLAS以外のデータセット/docs_active/3000event_純モデルsecondpass比較_2026-05-20.md:1)。

### 4.3 second pass の最終状態

| scenario | 採用モデル | review set | top30 attack events | top30 normal events |
| --- | --- | ---: | ---: | ---: |
| `S3` | `IF` | `3000` | `4` | `2996` |
| `M4` | `IF` | `3000` | `1` | `2999` |
| `M6` | `IF` | `3000` | `0` | `3000` |
| `S4` | `IF` | `3000` | `3` | `2997` |

この段階では `S3 / M4 / S4` は「攻撃を完全には消さずに false positive も読む」状態を作れている。

## 5. third pass: 10event micro-chunk で 100event へ圧縮

### 5.1 方法

second pass の `top30 chunk = 3000 event` を、さらに `10 event micro-chunk` に切る。  
`top10 micro-chunk = 100 event` を最終 review set とする。

まず見たのは、

- `IsolationForest`
- `kNN`

である。

## 6. M4 / S4 の 100event はユースケース化しやすいか

### 6.1 素直な比率

どちらも、最終 `100event` は

- `attack = 1`
- `normal = 99`

だった。

この意味では、**混在しているが、攻撃汚染はかなり薄い**。  
「attack を完全には消していない」ことを確保しつつ、ほぼ normal 主体の review set になっている。

### 6.2 ただし、99 normal が全部ユースケース核ではない

ここが重要で、`99 normal` がそのまま全部「説明しやすい業務ログ」ではない。

`100event` のプロセス分布を見ると、

#### M4

- labels: `normal 99 / attack 1`
- top processes:
  - `repmgr.exe 19`
  - `repwmiutils.exe 18`
  - `sysmon.exe 17`
  - `spoolsv.exe 12`
- event ids:
  - `4663 31`
  - `4658 29`
  - `4656 23`
  - `4688 7`
  - `4690 7`

#### S4

- labels: `normal 99 / attack 1`
- top processes:
  - `repmgr.exe 24`
  - `vmtoolsd.exe 14`
  - `tpautoconnsvc.exe 14`
  - `sysmon.exe 10`
  - `searchprotocolhost.exe 10`
- event ids:
  - `4663 30`
  - `4658 28`
  - `4656 23`
  - `4690 8`
  - `4688 5`

つまり、`normal` は多いが、そのかなりの部分は

- file access 監査
- service / system background
- host background utility

で構成されている。

### 6.3 ユースケースとしての使いやすさに対する意見

ここは私の現時点の率直な評価だと、次のように分けるのが自然。

#### M4

- `100event` 全体としての normal 比率: `99%`
- そのうち「そのままユースケース本文の核にしやすい」割合: **`20%〜35%` くらい**
- そのうち「周辺文脈・補足として使いやすい」割合: **`40%〜60%` くらい**

読み:

- attack 汚染はかなり薄い
- ただし normal の中心は `repmgr / repwmiutils / sysmon / spoolsv` で、業務シナリオそのものというより「周辺運用文脈」に寄る
- なので **“使える normal は多いが、核になる normal は 99 全部ではない”**

#### S4

- `100event` 全体としての normal 比率: `99%`
- そのうち「そのままユースケース本文の核にしやすい」割合: **`15%〜25%` くらい**
- そのうち「周辺文脈・補足として使いやすい」割合: **`45%〜60%` くらい**

読み:

- S4 も attack 汚染はかなり薄い
- ただし `vmtoolsd / tpautoconnsvc / searchprotocolhost` が目立つので、M4 より background 寄り
- したがって **“normal は十分あるが、説明可能な核は M4 よりやや少ない”**

### 6.4 まとめると

- `M4`: **ユースケース化しやすい**
  - normal 比率が高く、attack 汚染は薄い
  - ただし核として使える normal は体感 `1/4` 前後
- `S4`: **ユースケース化はできるが、M4 より background 寄り**
  - normal 比率は同様に高い
  - ただし核の密度は M4 よりやや弱い

なので、優先度としては

1. `M4`
2. `S4`
3. `S3`
4. `M6`

が自然。

## 7. 今後の標準フロー

ここまでを踏まえると、今後の標準フローは次がよい。

1. `Security benign-1to4` で `10分 sequence-level IF`
2. predicted positive sequence のみ残す
3. 内部を `100 event chunk` に切る
4. `chunk-level IF`
5. `top30 chunk = 3000 event`
6. 内部を `10 event micro-chunk` に切る
7. `micro-chunk-level kNN`
8. `top10 micro-chunk = 100 event`

ただし解釈はこう置く。

- `3000event` はかなり安定した pure model 圧縮
- `100event` は `M4 / S4` では使いやすい
- `S3` は 3000event までは強いが 100event はまだ弱い
- `M6` は difficulty case として逆考察に使いやすい
